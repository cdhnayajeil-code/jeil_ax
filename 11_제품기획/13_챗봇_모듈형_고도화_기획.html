13 · 챗봇 모듈형 고도화 기획 — "도구를 모듈로 만들고, 등록부로 관리한다"

관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-09-28 · 상태: Proposed — 사전정리·검토 단계(구현 전) · 제안 ADR-108 관련: 06 ERP연계 · 10 응답렌더링 · 11 요청접수 · 05 FE·BE · 08 보안 · 09 ADR · 모델 설정 SSOT 실제구축준비 자료/06_챗봇_사용모델설정_SSOT.md · CLAUDE.md §1.6·§3.3·§5.4·§13

jeil-chat 에서 "챗봇으로 할 수 있는 일"을 하나하나 모듈(부품)로 만들고, 등록부에서 켜고 끄고 지켜보는 체계로 바꾸는 기획이다. 이 문서는 구현 전에 정해 둘 것(사전정리사항)과 결정·위험(검토사항) 을 모은다. 코드·DB 변경은 §6 로드맵의 각 단계를 백로그 요청(REQ)으로 따로 열어 진행한다.

범위(2026-09-28 관리자 결정) - 챗봇이 하는 일은 조회 · 초안 작성 · 요청 접수 세 가지로 한정한다. 확정·결재·발주·발송 같은 실거래 버튼은 사람이 누른다(CLAUDE.md §1.6). - LLM 은 벤더 중립으로 설계한다. 벤더 확정(OpenAI 유지 / Claude 추가)은 §5-1 검토사항으로 남긴다.

비개발자용 한 줄 요약 — 지금 챗봇의 기능 19가지는 한 파일에 뒤섞여 있다. 그래서 기능 하나를 더하려면 여러 곳을 동시에 고쳐야 하고, 고친 곳과 안 고친 곳이 어긋난다. 앞으로는 기능마다 "설명서(manifest)가 붙은 부품" 으로 만들고, 관리자는 등록부 화면에서 부품별로 켜고 끄며, 누가 언제 어떤 부품을 썼는지 기록을 본다.

0. 결론 먼저

# 제안 한 줄 이유
1 도구 1개 = 모듈 파일 1개(manifest + run) 추가·수정 지점을 한 곳으로 모은다
2 정의는 코드, 운영 스위치는 DB(chat_tool_registry) 배포 없이 켜고 끄기·파일럿 부서 지정. 정의는 코드 리뷰를 거친다
3 시스템 프롬프트 자동 조립(공통 머리말 + 활성 모듈의 prompt_hint) 지금 운영 중인 "도구는 있는데 프롬프트는 모르는" 어긋남을 구조적으로 없앤다
4 권한 밖 도구는 모델에게 보이지도 않게(권한별 tools 주입) 도구가 늘어도 정확도·토큰 비용이 유지되고 노출면이 줄어든다
5 모듈 유형 3종: read(조회) · draft(초안) · request(접수) 유형마다 금지선과 사람 개입 지점을 규격으로 강제한다
6 도구 호출 감사로그(chat_tool_call) 신설 지금은 도구 이름만 남는다. 누가 어떤 조건으로 몇 건을 봤는지 남긴다
7 LLM 어댑터 분리(llm/openai.ts · 추후 llm/anthropic.ts) 벤더 결정을 모듈화 작업과 분리해 뒤로 미룰 수 있다
8 새 뷰 타입은 만들지 않는다 — 뷰 5종(ADR-008) 유지 초안 확인 카드도 record + actions 로 표현한다

1-3. 지금 구조의 한계 (근거 있는 것만)

  1. 도구 하나를 추가하려면 흩어진 곳을 다 고쳐야 한다: TOOLS + runTool 분기 + ERP_TOOL_MODULE + DB 시스템 프롬프트(관리자 콘솔) + 관리자 표시 목록 + (필요 시) SQL 뷰 + 문서. 한 곳이라도 빠지면 조용히 어긋난다.
  2. 이미 어긋나 있다 — DB 시스템 프롬프트(2026-07-09 이후 변경 없음)에 get_erp_item_orders · get_hr_headcount · get_my_access · get_my_requests 안내가 없다. 코드 상수 SYSTEM_PROMPT 에만 있어서 운영에는 반영되지 않는다.
  3. 관리자 콘솔의 도구 목록이 실제와 다르다 — jeil-chat-admin/index.ts:435 gateway.tools 가 3개로 하드코딩돼 있다.
  4. 도구 호출 기록이 얕다 — chat_log.tools_used 에 도구 이름 배열만 남는다. 조건(인자), 결과 건수, 소요시간, 거부 여부를 남기는 곳이 없다(인사 도구만 hr_access_log 가 따로 있음).
  5. 모델 벤더가 코드에 박혀 있다 — 도구 스키마가 OpenAI 형식이고 호출 함수도 하나라서, 벤더를 바꾸거나 추가하면 게이트웨이 전체를 손봐야 한다.
  6. 권한과 무관하게 도구 19개 전부가 모델에게 보인다 — 권한이 없으면 실행 단계에서 막지만(runTool 공통 게이트 :473-487), 모델은 여전히 그 도구를 고르려 한다. 도구가 30~50개로 늘면 선택 정확도와 토큰 비용이 나빠진다.
  7. 배포 단위가 크다 — jeil-chat 은 약 116KB라 MCP 배포 한도를 넘어 CLI 로만 배포된다(11 설계 §17-1).

1-4. 지켜야 할 선행 결정

2. 모듈 표준 규격 (제안 ADR-108)

2-1. 모양

supabase/functions/
├─ _shared/                  ← 인증(verifyEntraUser)·CORS·DB 클라이언트 (3중 복제 해소)
└─ jeil-chat/
   ├─ index.ts               ← 게이트웨이: 인증 → 권한 → 모듈 선택 → LLM 루프 → SSE → 로그
   ├─ llm/                   ← 벤더 어댑터 (openai.ts, 추후 anthropic.ts) — 공통 인터페이스 1개
   ├─ core/                  ← ctx 생성·감사로그·뷰 헬퍼(ViewPayload 5종)·프롬프트 조립
   └─ modules/
      ├─ index.ts            ← 등록 목록(정적 import) — Edge Function 은 동적 로딩이 없다
      ├─ purchase/get_erp_pur_order.ts
      ├─ hr/get_hr_payroll.ts
      └─ …                   ← 도구 1개 = 파일 1개

모듈 파일은 두 가지를 내보낸다.

export const manifest: ToolManifest = { … };           // 설명서 — 사람과 모델, 등록부가 읽는다
export async function run(args, ctx): Promise<ToolResult> { … }   // 실행 — 데이터 + __view

2-4. 등록부 — 정의는 코드, 운영 스위치는 DB

구분 정본 바꾸는 사람 바꾸는 방법
도구 정의(스키마·로직·권한 모듈·민감도) 코드(modules/*.ts) 개발 코드 리뷰 → 배포
운영 상태(켜기/끄기·파일럿 부서·프롬프트 문구 덮어쓰기) DB chat_tool_registry 포털 관리자 관리자 콘솔 「도구 모듈」 탭
  • 권한 모듈·민감도를 DB 에서 바꿀 수 있게 하면 관리 화면 클릭 한 번이 권한 우회가 된다. 그래서 보안에 관한 값은 코드에만 두고, DB 는 더 좁히는 방향(끄기·파일럿 한정)만 할 수 있게 한다.
  • 게이트웨이는 기동 시 modules/index.ts 목록과 chat_tool_registry 를 대사한다. DB 에 없는 모듈은 manifest.status 를 따르고, 코드에 없는 DB 행은 무시하고 경고로 남긴다.

2-5. 요청 한 번의 흐름 (목표 상태)

  1. 인증(_shared/verifyEntraUser) → perm_effective 1회
  2. 사용 가능한 모듈 고르기 = 코드 등록 목록 ∩ enabled ∩ (live 이거나 파일럿 부서 소속) ∩ 권한 보유(gate 모듈)
  3. 고른 모듈만 llm/<vendor> 어댑터로 tools 형식 변환 → 시스템 프롬프트 = DB 공통 머리말 + 고른 모듈의 prompt_hint
  4. 모델이 도구 호출 → 게이트웨이가 한 번 더 권한 확인(방어선 2중) → run(args, ctx) → __view 는 SSE jeilax 로, 요약 데이터만 모델에게
  5. 호출마다 chat_tool_call 한 줄 기록 → 끝나면 chat_log · chat_message 는 지금처럼 저장

권한이 없는 도구를 보여 주지 않는 것(2단계)과 실행 때 다시 막는 것(4단계)을 모두 한다. 앞의 것은 정확도·비용 때문이고, 뒤의 것이 실제 보안선이다(CLAUDE.md §5.4). 단, 권한이 없는 질문에 모델이 "그런 기능은 없다"고 답하면 ADR-011 요청 접수로 이어지지 않는다. 그래서 권한 밖 도구는 이름·한 줄 설명만 프롬프트에 목록으로 알려 주고, 해당 질문이 오면 권한 요청 카드(notice + request)를 띄우게 한다. 이 방식은 §5-3 에서 검토한다.

3. 모듈 유형 3종 — 조회 · 초안 · 접수

유형 할 수 있는 것 하지 않는 것 사람이 하는 일
read 조회 v_erp_* · 포털 테이블 조회, 뷰 5종 반환 ERP 직접 조회, 동적 SQL, 원본 전달 없음
draft 초안 포털 DB chat_draft 에 초안 저장, 해당 업무 화면으로 가는 링크 제공 ERP 쓰기, 확정·결재·발주·메일·Teams 발송 업무 화면에서 검토·수정 후 본인이 확정
request 접수 portal_request(ADR-011) 등 포털 원장에 접수 담당자 대신 처리·승인 담당자가 처리·회신

3-1. 초안·접수의 공통 안전장치 — "확인 카드"

draft · request 는 모델이 부른다고 바로 저장하지 않는다.

  1. 모델이 도구를 호출하면 모듈은 저장하지 않고 요약 카드만 돌려준다(record 뷰 + actions: 「저장」 · 「고치기」 · 「취소」).
  2. 사용자가 「저장」을 누르면 프런트가 챗봇을 거치지 않고 전용 엔드포인트(예: jeil-chat-draft)에 확정 요청을 보낸다. 이때 서버가 권한을 다시 판정하고 저장한다.
  3. 저장된 초안은 업무 화면(예: /work/voucher)에서 불러와 사람이 마무리한다.
  • 이렇게 하면 모델이 스스로 쓰기를 끝낼 방법이 없다. 문서 검색 결과에 숨은 지시문(프롬프트 인젝션)이 있어도 사람의 클릭 없이는 기록되지 않는다.
  • 새 뷰 타입이 필요 없다(record + actions.kind 확장만 — ADR-011 이 request 를 추가한 방식과 같다).

3-2. 1차 후보 (선정 기준: 효용 × 위험 낮음 × 받아 줄 화면이 이미 있음)

5. 검토사항 — 결정이 필요하거나 위험한 것

5-1. LLM 벤더 (미결 · ADR-106 / D-18 / D-59 / REQ-0056)

  • 지금은 OpenAI(gpt-4o-mini 기본)만 호출한다. 화면·기획서에는 Claude 표기가 남아 있다.
  • 이 기획의 입장: 모듈 규격(params = JSON Schema)과 LLM 어댑터를 분리하면 벤더 결정 없이 P0~P3 를 진행할 수 있다. 벤더는 P4 에서 어댑터를 하나 더 붙이는 문제로 줄어든다.
  • 결정할 것: ① 기본 벤더 ② 두 벤더를 함께 쓸지(라우팅 규칙 ai_routing_rule 확장) ③ 도구 호출 형식 차이(병렬 호출·스트리밍 이벤트)를 어댑터가 얼마나 흡수할지 ④ 벤더별 토큰 수 차이를 사용량 계산에 어떻게 반영할지(REQ-0056 열린 질문).

5-2. 배포 단위

  • 모듈로 나눠도 jeil-chat 은 여전히 하나의 번들이다. 크기는 줄지 않고 오히려 늘 수 있다 → MCP 배포는 계속 안 된다.
  • 선택지: (a) CLI 배포(supabase functions deploy)를 표준으로 문서화 (권고) (b) 도메인별로 함수를 쪼개고 게이트웨이가 내부 호출 → 호출 지연·인증 전달 비용이 생겨 비권고.
  • Azure 이관(07 설계) 때는 같은 모듈 구조를 Azure Functions/컨테이너로 옮긴다. 모듈이 ctx.db 만 쓰게 하는 것이 그때 교체 비용을 낮춘다.

5-3. 도구가 많아질 때의 정확도·비용

  • 모델에게 넘기는 도구 설명이 길수록 매 요청 토큰이 늘고 잘못 고르는 비율이 오른다.
  • 권고: 권한별 주입(§2-5)을 기본으로 하고, 30개를 넘으면 도메인 선별(질문을 먼저 분류해 그 도메인 모듈만 주입)을 2단계로 검토한다.
  • 검토 필요: 권한 밖 기능을 모델이 "없다"고 오답하지 않도록 이름만 알려 주는 방식(§2-5 말미)이 토큰·혼동 면에서 괜찮은지 파일럿으로 확인한다.
