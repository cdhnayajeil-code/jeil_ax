# 13 · 챗봇 모듈형 고도화 기획 — "도구를 모듈로 만들고, 등록부로 관리한다"

> 관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-09-28 · 상태: **Proposed — 사전정리·검토 단계(구현 전) · 제안 ADR-108**
> 관련: [06 ERP연계](06_ERP연계_챗봇활용_설계.md) · [10 응답렌더링](10_챗봇_응답렌더링_설계.md) · [11 요청접수](11_챗봇_데이터요청접수_설계.md) · [05 FE·BE](05_프론트엔드_백엔드_설계.md) · [08 보안](08_보안_데이터안정성.md) · [09 ADR](09_ADR_의사결정기록.md) · 모델 설정 SSOT `실제구축준비 자료/06_챗봇_사용모델설정_SSOT.md` · `CLAUDE.md §1.6·§3.3·§5.4·§13`

jeil-chat 에서 **"챗봇으로 할 수 있는 일"을 하나하나 모듈(부품)로 만들고, 등록부에서 켜고 끄고 지켜보는 체계**로 바꾸는 기획이다.
이 문서는 **구현 전에 정해 둘 것(사전정리사항)과 결정·위험(검토사항)** 을 모은다. 코드·DB 변경은 §6 로드맵의 각 단계를 백로그 요청(REQ)으로 따로 열어 진행한다.

**범위(2026-09-28 관리자 결정)**
- 챗봇이 하는 일은 **조회 · 초안 작성 · 요청 접수** 세 가지로 한정한다. 확정·결재·발주·발송 같은 실거래 버튼은 **사람이 누른다**(CLAUDE.md §1.6).
- LLM 은 **벤더 중립**으로 설계한다. 벤더 확정(OpenAI 유지 / Claude 추가)은 §5-1 검토사항으로 남긴다.

> **비개발자용 한 줄 요약** — 지금 챗봇의 기능 19가지는 한 파일에 뒤섞여 있다. 그래서 기능 하나를 더하려면 여러 곳을 동시에 고쳐야 하고, 고친 곳과 안 고친 곳이 어긋난다. 앞으로는 기능마다 **"설명서(manifest)가 붙은 부품"** 으로 만들고, 관리자는 **등록부 화면**에서 부품별로 켜고 끄며, 누가 언제 어떤 부품을 썼는지 기록을 본다.

## 0. 결론 먼저

| # | 제안 | 한 줄 이유 |
|---|---|---|
| 1 | **도구 1개 = 모듈 파일 1개**(`manifest` + `run`) | 추가·수정 지점을 한 곳으로 모은다 |
| 2 | **정의는 코드, 운영 스위치는 DB**(`chat_tool_registry`) | 배포 없이 켜고 끄기·파일럿 부서 지정. 정의는 코드 리뷰를 거친다 |
| 3 | **시스템 프롬프트 자동 조립**(공통 머리말 + 활성 모듈의 `prompt_hint`) | 지금 운영 중인 "도구는 있는데 프롬프트는 모르는" 어긋남을 구조적으로 없앤다 |
| 4 | **권한 밖 도구는 모델에게 보이지도 않게**(권한별 tools 주입) | 도구가 늘어도 정확도·토큰 비용이 유지되고 노출면이 줄어든다 |
| 5 | **모듈 유형 3종**: `read`(조회) · `draft`(초안) · `request`(접수) | 유형마다 금지선과 사람 개입 지점을 규격으로 강제한다 |
| 6 | **도구 호출 감사로그**(`chat_tool_call`) 신설 | 지금은 도구 이름만 남는다. 누가 어떤 조건으로 몇 건을 봤는지 남긴다 |
| 7 | **LLM 어댑터 분리**(`llm/openai.ts` · 추후 `llm/anthropic.ts`) | 벤더 결정을 모듈화 작업과 분리해 뒤로 미룰 수 있다 |
| 8 | **새 뷰 타입은 만들지 않는다** — 뷰 5종(ADR-008) 유지 | 초안 확인 카드도 `record` + `actions` 로 표현한다 |

### 1-3. 지금 구조의 한계 (근거 있는 것만)

1. **도구 하나를 추가하려면 흩어진 곳을 다 고쳐야 한다**: `TOOLS` + `runTool` 분기 + `ERP_TOOL_MODULE` + DB 시스템 프롬프트(관리자 콘솔) + 관리자 표시 목록 + (필요 시) SQL 뷰 + 문서. 한 곳이라도 빠지면 조용히 어긋난다.
2. **이미 어긋나 있다** — DB 시스템 프롬프트(2026-07-09 이후 변경 없음)에 `get_erp_item_orders` · `get_hr_headcount` · `get_my_access` · `get_my_requests` 안내가 없다. 코드 상수 `SYSTEM_PROMPT` 에만 있어서 운영에는 반영되지 않는다.
3. **관리자 콘솔의 도구 목록이 실제와 다르다** — `jeil-chat-admin/index.ts:435` `gateway.tools` 가 3개로 하드코딩돼 있다.
4. **도구 호출 기록이 얕다** — `chat_log.tools_used` 에 도구 **이름 배열**만 남는다. 조건(인자), 결과 건수, 소요시간, 거부 여부를 남기는 곳이 없다(인사 도구만 `hr_access_log` 가 따로 있음).
5. **모델 벤더가 코드에 박혀 있다** — 도구 스키마가 OpenAI 형식이고 호출 함수도 하나라서, 벤더를 바꾸거나 추가하면 게이트웨이 전체를 손봐야 한다.
6. **권한과 무관하게 도구 19개 전부가 모델에게 보인다** — 권한이 없으면 실행 단계에서 막지만(`runTool` 공통 게이트 :473-487), 모델은 여전히 그 도구를 고르려 한다. 도구가 30~50개로 늘면 선택 정확도와 토큰 비용이 나빠진다.
7. **배포 단위가 크다** — jeil-chat 은 약 116KB라 MCP 배포 한도를 넘어 CLI 로만 배포된다(11 설계 §17-1).

### 1-4. 지켜야 할 선행 결정

| 결정 | 이 기획에 주는 제약 |
|---|---|
| ADR-002 | AI 가 SQL 을 만들지 않는다. **등록된 도구만** 호출 → 모듈 등록부가 이 원칙의 실체가 된다 |
| ADR-007 | ERP 데이터는 `public.v_erp_*` 뷰로만. 모듈이 `erp_ro` 원본 테이블이나 운영 MSSQL 에 직접 붙지 않는다 |
| ADR-008 | 뷰는 5종(series/ranking/record/list/notice) 고정. 수치는 모델을 거치지 않는다 |
| ADR-009 | 대화 원문은 본인만 열람·삭제. 관리자용 원문 조회 API 없음 → 감사로그에 원문을 담지 않는다 |
| ADR-010 | 권한 판정은 `perm_effective` 하나. 모듈이 권한을 따로 조회하지 않는다 |
| ADR-011 | 조회 불가 → 요청 원장(`portal_request`). `request` 유형 모듈은 이 원장을 재사용한다 |
| ADR-107 | 권한의 부서 키는 `dept_cd` + 조직도 상속 |

## 2. 모듈 표준 규격 (제안 ADR-108)

### 2-1. 모양

```
supabase/functions/
├─ _shared/                  ← 인증(verifyEntraUser)·CORS·DB 클라이언트 (3중 복제 해소)
└─ jeil-chat/
   ├─ index.ts               ← 게이트웨이: 인증 → 권한 → 모듈 선택 → LLM 루프 → SSE → 로그
   ├─ llm/                   ← 벤더 어댑터 (openai.ts, 추후 anthropic.ts) — 공통 인터페이스 1개
   ├─ core/                  ← ctx 생성·감사로그·뷰 헬퍼(ViewPayload 5종)·프롬프트 조립
   └─ modules/
      ├─ index.ts            ← 등록 목록(정적 import) — Edge Function 은 동적 로딩이 없다
      ├─ purchase/get_erp_pur_order.ts
      ├─ hr/get_hr_payroll.ts
      └─ …                   ← 도구 1개 = 파일 1개
```

모듈 파일은 두 가지를 내보낸다.

```ts
export const manifest: ToolManifest = { … };           // 설명서 — 사람과 모델, 등록부가 읽는다
export async function run(args, ctx): Promise<ToolResult> { … }   // 실행 — 데이터 + __view
```

### 2-2. manifest 필드

| 필드 | 뜻 | 예 |
|---|---|---|
| `id` | 도구 이름(영구 불변, 모델이 부르는 이름) | `get_erp_pur_order` |
| `version` | 모듈 버전(감사로그에 함께 기록) | `1.2.0` |
| `domain` | 업무 영역 | `purchase` · `sales` · `inventory` · `hr` · `finance` · `docs` · `common` |
| `kind` | 유형 | `read` · `draft` · `request` (§3) |
| `title_ko` / `summary_ko` | 사용자·관리자용 이름과 설명 | 「발주 현황」 |
| `description_llm` | 모델용 설명(언제 부르는지) | — |
| `params` | JSON Schema(벤더 중립). 어댑터가 벤더 형식으로 바꾼다 | `{ ym: string }` |
| `perm_module` | 필요한 권한 모듈(`perm_module_catalog` 키). `null` 이면 전원 | `pur_order` |
| `perm_mode` | `gate`(없으면 차단) · `partial`(도구 안에서 판정) · `self`(본인 데이터 고정) | `gate` |
| `sensitivity` | `normal` · `amount`(금액) · `personal`(급여·인사) | `amount` |
| `view` | 반환 뷰 종류(5종 중) | `series` |
| `row_limit` · `timeout_ms` | 결과 상한 · 실행 제한시간 | `200` · `8000` |
| `prompt_hint` | 시스템 프롬프트에 자동으로 들어갈 한두 줄 | 「발주 금액·건수 질문은 이 도구를 먼저」 |
| `owner` | 업무 담당 부서(내용 검수 책임) | 구매팀 |
| `status` | 코드 쪽 기본 상태 | `dev` · `pilot` · `live` · `off` |

### 2-3. ctx — 게이트웨이가 모듈에 넘기는 것

| 항목 | 내용 | 규칙 |
|---|---|---|
| `upn` · `dept_cd` | 호출자 | 모듈이 인자로 다른 사람을 지정할 수 없다(`self` 모듈) |
| `scope` | `perm_effective` 결과(요청당 1회) | **모듈이 권한을 다시 조회하지 않는다** |
| `db` | service_role 클라이언트 | `public.v_erp_*` · 포털 테이블만. 원본 `erp_ro` 직접 조회 금지 |
| `audit(evt)` | 감사로그 기록 함수 | 모듈은 건수·필터 요약만 넘긴다 |
| `view` 헬퍼 | series/ranking/record/list/notice 생성기 | 새 뷰 타입 생성 불가(타입으로 막는다) |
| `signal` | 중지 신호 | 사용자가 중지하면 DB 조회도 끊는다 |

### 2-4. 등록부 — 정의는 코드, 운영 스위치는 DB

| 구분 | 정본 | 바꾸는 사람 | 바꾸는 방법 |
|---|---|---|---|
| 도구 정의(스키마·로직·권한 모듈·민감도) | **코드**(`modules/*.ts`) | 개발 | 코드 리뷰 → 배포 |
| 운영 상태(켜기/끄기·파일럿 부서·프롬프트 문구 덮어쓰기) | **DB** `chat_tool_registry` | 포털 관리자 | 관리자 콘솔 「도구 모듈」 탭 |

- 권한 모듈·민감도를 DB 에서 바꿀 수 있게 하면 **관리 화면 클릭 한 번이 권한 우회**가 된다. 그래서 보안에 관한 값은 코드에만 두고, DB 는 **더 좁히는 방향(끄기·파일럿 한정)만** 할 수 있게 한다.
- 게이트웨이는 기동 시 `modules/index.ts` 목록과 `chat_tool_registry` 를 대사한다. DB 에 없는 모듈은 `manifest.status` 를 따르고, 코드에 없는 DB 행은 무시하고 경고로 남긴다.

`chat_tool_registry`(안)

| 컬럼 | 뜻 |
|---|---|
| `tool_id` (PK) | manifest.id |
| `enabled` | 전체 켜기/끄기(긴급 차단 스위치) |
| `stage` | `pilot` · `live` |
| `pilot_dept_cds` | 파일럿 부서(`dept_cd` 배열, ADR-107 조직도 상속) |
| `prompt_hint_override` | 프롬프트 문구 조정(선택) |
| `note` · `updated_by` · `updated_at` | 변경 기록(`perm_audit` 에도 한 줄) |

### 2-5. 요청 한 번의 흐름 (목표 상태)

1. 인증(`_shared/verifyEntraUser`) → `perm_effective` 1회
2. **사용 가능한 모듈 고르기** = 코드 등록 목록 ∩ `enabled` ∩ (live 이거나 파일럿 부서 소속) ∩ 권한 보유(`gate` 모듈)
3. 고른 모듈만 `llm/<vendor>` 어댑터로 tools 형식 변환 → 시스템 프롬프트 = DB 공통 머리말 + 고른 모듈의 `prompt_hint`
4. 모델이 도구 호출 → 게이트웨이가 **한 번 더 권한 확인**(방어선 2중) → `run(args, ctx)` → `__view` 는 SSE `jeilax` 로, 요약 데이터만 모델에게
5. 호출마다 `chat_tool_call` 한 줄 기록 → 끝나면 `chat_log` · `chat_message` 는 지금처럼 저장

> 권한이 없는 도구를 **보여 주지 않는** 것(2단계)과 **실행 때 다시 막는** 것(4단계)을 모두 한다. 앞의 것은 정확도·비용 때문이고, 뒤의 것이 실제 보안선이다(CLAUDE.md §5.4).
> 단, 권한이 없는 질문에 모델이 "그런 기능은 없다"고 답하면 ADR-011 요청 접수로 이어지지 않는다. 그래서 **권한 밖 도구는 이름·한 줄 설명만 프롬프트에 목록으로 알려 주고**, 해당 질문이 오면 권한 요청 카드(`notice` + `request`)를 띄우게 한다. 이 방식은 §5-3 에서 검토한다.

## 3. 모듈 유형 3종 — 조회 · 초안 · 접수

| 유형 | 할 수 있는 것 | 하지 않는 것 | 사람이 하는 일 |
|---|---|---|---|
| `read` 조회 | `v_erp_*` · 포털 테이블 조회, 뷰 5종 반환 | ERP 직접 조회, 동적 SQL, 원본 전달 | 없음 |
| `draft` 초안 | 포털 DB `chat_draft` 에 초안 저장, 해당 업무 화면으로 가는 링크 제공 | ERP 쓰기, 확정·결재·발주·메일·Teams **발송** | 업무 화면에서 검토·수정 후 **본인이 확정** |
| `request` 접수 | `portal_request`(ADR-011) 등 포털 원장에 접수 | 담당자 대신 처리·승인 | 담당자가 처리·회신 |

### 3-1. 초안·접수의 공통 안전장치 — "확인 카드"

`draft` · `request` 는 모델이 부른다고 바로 저장하지 않는다.

1. 모델이 도구를 호출하면 모듈은 **저장하지 않고** 요약 카드만 돌려준다(`record` 뷰 + `actions`: 「저장」 · 「고치기」 · 「취소」).
2. 사용자가 「저장」을 누르면 프런트가 **챗봇을 거치지 않고** 전용 엔드포인트(예: `jeil-chat-draft`)에 확정 요청을 보낸다. 이때 서버가 권한을 다시 판정하고 저장한다.
3. 저장된 초안은 업무 화면(예: `/work/voucher`)에서 불러와 사람이 마무리한다.

- 이렇게 하면 **모델이 스스로 쓰기를 끝낼 방법이 없다.** 문서 검색 결과에 숨은 지시문(프롬프트 인젝션)이 있어도 사람의 클릭 없이는 기록되지 않는다.
- 새 뷰 타입이 필요 없다(`record` + `actions.kind` 확장만 — ADR-011 이 `request` 를 추가한 방식과 같다).

### 3-2. 1차 후보 (선정 기준: 효용 × 위험 낮음 × 받아 줄 화면이 이미 있음)

| 후보 | 유형 | 받는 화면·원장 | 효용 | 위험 | 권고 |
|---|---|---|---|---|---|
| 결의전표 초안(적요·계정 제안) | draft | `/work/voucher` 템플릿·작성 서식 | 높음 | 계정 오제안 → 사람이 확정하므로 통제 가능 | **1차** |
| 데이터·권한 요청을 대화로 접수 | request | `portal_request` | 중간 | 낮음(이미 있는 원장) | **1차** |
| 협력사 메시지 문구 초안 | draft | 협력사 포털 메시지(`sp_message`) | 중간 | 사외 발송이라 표현 검수 필요 | 2차 |
| 구매요청 초안 | draft | 구매 운영페이지 | 중간 | ERP 입력 화면 연계 미정 | 2차 |
| 메일·Teams 문구 초안 | draft | 복사해서 쓰기(발송 연동 없음) | 중간 | 낮음 | 2차(저장 없이 텍스트만이면 모듈 불필요) |

### 3-3. `chat_draft`(안)

|---|---|

| `target` | 받는 화면·원장 키(예: `voucher`) |

## 5. 검토사항 — 결정이 필요하거나 위험한 것

### 5-1. LLM 벤더 (미결 · ADR-106 / D-18 / D-59 / REQ-0056)
- 지금은 OpenAI(gpt-4o-mini 기본)만 호출한다. 화면·기획서에는 Claude 표기가 남아 있다.
- **이 기획의 입장**: 모듈 규격(`params` = JSON Schema)과 LLM 어댑터를 분리하면 **벤더 결정 없이 P0~P3 를 진행할 수 있다.** 벤더는 P4 에서 어댑터를 하나 더 붙이는 문제로 줄어든다.
- 결정할 것: ① 기본 벤더 ② 두 벤더를 함께 쓸지(라우팅 규칙 `ai_routing_rule` 확장) ③ 도구 호출 형식 차이(병렬 호출·스트리밍 이벤트)를 어댑터가 얼마나 흡수할지 ④ 벤더별 토큰 수 차이를 사용량 계산에 어떻게 반영할지(REQ-0056 열린 질문).

### 5-2. 배포 단위
- 모듈로 나눠도 jeil-chat 은 여전히 **하나의 번들**이다. 크기는 줄지 않고 오히려 늘 수 있다 → MCP 배포는 계속 안 된다.
- 선택지: (a) CLI 배포(`supabase functions deploy`)를 표준으로 문서화 **(권고)** (b) 도메인별로 함수를 쪼개고 게이트웨이가 내부 호출 → 호출 지연·인증 전달 비용이 생겨 비권고.
- Azure 이관(07 설계) 때는 같은 모듈 구조를 Azure Functions/컨테이너로 옮긴다. 모듈이 `ctx.db` 만 쓰게 하는 것이 그때 교체 비용을 낮춘다.

### 5-3. 도구가 많아질 때의 정확도·비용
- 모델에게 넘기는 도구 설명이 길수록 매 요청 토큰이 늘고 잘못 고르는 비율이 오른다.
- 권고: **권한별 주입(§2-5)을 기본**으로 하고, 30개를 넘으면 **도메인 선별**(질문을 먼저 분류해 그 도메인 모듈만 주입)을 2단계로 검토한다.
- 검토 필요: 권한 밖 기능을 모델이 "없다"고 오답하지 않도록 이름만 알려 주는 방식(§2-5 말미)이 토큰·혼동 면에서 괜찮은지 파일럿으로 확인한다.

### 5-4. 보안
| 위험 | 현재 | 대응 |
|---|---|---|
| 행 수준 보안 부재 | `erp_ro` 모듈별 RLS 없음 — 차단은 게이트웨이에서만(ADR-010 잔여) | 모듈이 늘수록 게이트 우회 가능성이 커진다 → 민감 모듈부터 DB 함수(RPC) 경유 + RPC 안에서 권한 재판정(인사 `hr_payroll_get` 방식) |
| 토큰 audience 미검증 | ADR-009 잔여 · ADR-104 | `_shared` 분리(P0) 때 함께 처리 |
| 프롬프트 인젝션 | 문서 검색 결과가 모델 입력에 들어간다 | `draft`·`request` 는 확인 카드 + 별도 엔드포인트로만 확정(§3-1). 문서 모듈이 같은 라운드에서 쓰기 모듈을 부를 수 없게 막는 방안 검토 |
| 민감 데이터 노출 | 인사만 별도 접근기록 | `sensitivity=personal` 모듈은 로그 요약 최소화, 결과 캐시 금지, 대화 저장 시 표시 정책 확인 |
| 관리 화면 권한 | 관리자 게이트 3갈래(REQ-0031) | 「도구 모듈」 탭은 게이트 정리(REQ-0031) 뒤에 붙인다 |

### 5-5. 초안 데이터 보존
- `chat_draft` 보존기간: 제안은 **미확정 초안 30일 후 삭제, 업무 화면이 가져간 초안은 7일 후 삭제**(원본은 업무 화면 쪽에 있음).
- 대화(세션)를 삭제하면 그 대화에서 나온 **미확정 초안도 함께 지운다** — ADR-009 soft delete 30일과 맞출지 결정 필요.
- 팀 공유 작업 폴더(ADR-009 개정)의 대화에서 만든 초안은 **만든 사람만** 본다(공유하지 않는다) — 이 원칙이 맞는지 확인 필요.

### 5-6. 관리 화면 위치
- (a) 04 포털의 관리자 콘솔에 「도구 모듈」 탭 추가 **(권고 — 모델 설정·사용량 탭과 같은 자리)**
- (b) `app/` 에 새 관리 화면
- 어느 쪽이든 모듈 목록은 **표준 그리드**(§13, `app/lib/grid.js`), 상단 조회조건은 **조회바**(§16)를 쓴다. 보여 줄 열: 모듈 · 도메인 · 유형 · 권한 모듈 · 민감도 · 상태 · 파일럿 부서 · 최근 30일 호출·거부·오류 · 평균 소요시간.

### 5-7. 그 밖의 확인
- **Entra 보안그룹 RBAC**: 현재 판정은 `perm_effective` 뿐이다. 모듈화가 판정 방식을 바꿀 이유는 없다 → **기존 방식 유지 권고**.
- **사용량 한도(U-2·U-3)를 모듈 단위로 걸지**: 예) 문서 검색은 하루 N회. 1차는 전체 한도만, 모듈 한도는 사용 기록(`chat_tool_call`)이 쌓인 뒤 판단.
- **도구 라운드 상한**(`MAX_ROUNDS=4`): 초안 모듈은 조회 → 초안처럼 여러 라운드를 쓰기 쉽다. 파일럿에서 상한이 모자라는지 측정한다.
- **요청접수 잔여**(ADR-011 P3 — Teams 실가동, SLA 배지): `request` 유형 모듈과 순서를 맞춘다.

## 7. 새 모듈을 추가하는 절차 (표준화 이후 목표)

1. 업무 담당 부서와 **질문 예시 5개 · 기대 답**을 정한다(백로그 REQ 로 등록).
2. 데이터가 없으면 `public.v_erp_*` 뷰 또는 RPC 를 `실제구축준비 자료/이관/sql/NN_*.sql` 로 만든다(ERP 연계는 `10_ERP_DB연계/` 갱신).
3. `modules/<domain>/<tool>.ts` 작성 — manifest 모든 필드를 채운다. 뷰는 5종 중 하나.
4. `modules/index.ts` 에 한 줄 등록.
5. 모듈 테스트(가짜 ctx: 권한 있음/없음/빈 결과) 통과.
6. 배포 → 등록부에서 **파일럿 부서만 켠다** → 호출 기록·거부율 확인.
7. live 전환 → 문서(이 문서 부록, 06 ERP연계, CHANGELOG) 갱신.

> 목표: **코드 2곳(모듈 파일 + 등록 한 줄) + 등록부 1행.** 프롬프트와 관리자 목록은 자동으로 따라온다.
