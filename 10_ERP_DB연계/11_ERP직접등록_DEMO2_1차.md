## 1. 한 장 요약

> **상태 — 4건째 투입 성공·AX001 기준 2건째, 전송=확정 자동화(C-13) 완료(2026-08-20)**: 1차 투입(2026-08-19 오후, `DRAFT-20260819-0005`→**`AG202608190006`**) 이후 화면 [🚀 ERP 전송] 버튼 E2E(2026-08-20, `DRAFT-20260820-0007`→**`AG202608200001`**)·AX001 전환 재성공(2026-08-20, `DRAFT-20260819-0006`→**`AG202608190007`**)을 거쳐, **AX001 기준 2건째 성공**(2026-08-20, `DRAFT-20260820-0008`→**`AG202608200002`**, 라인 3/3 완전일치)까지 확인됐다. 같은 날 **「전송 성공 = 확정」을 일원화**(결정 C-13)해 화면의 ERP 결의전표번호 수기 입력칸·[확정 기록] 버튼을 제거했다 — 전표번호는 ERP가 채번해 자동 회기입되므로 사람이 옮겨 적을 이유가 없어졌고, RPC `gl_apply_record`가 성공 시 초안 상태를 `submitted→posted`로 자동 전이한다. 잔여는 **U-F**(AX001 계정매핑 등재 권장)·2차 이상 케이스 확대·운영(`JEILMNS`) 전환 재심의(§6)뿐이다. 상세는 §7 변경이력.

**무엇** — 포털에서 작성·제출한 결의전표 초안을, 사람이 ERP에 재입력하는 대신 **적용기(관리자 PC 배치)가 DEMO2에 직접 투입**해 ERP 표준 엔진으로 전표(TG류)를 생성한다. ERP 계정=MS 계정 1:1(C-3)이므로 **전표 등록자는 포털 제출자의 ERP 계정 그대로**다.

**전표번호(핵심 요구)** — AI가 만드는 전표는 **전용 접두어 `AG` 대역**으로 채번한다.
ERP 표준 채번기(`usp_a_tempgl_no_auto_gen 'AG'` — `B_AUTO_NUMBERING` 기존 미사용 유형 재활용)를 쓰므로 **중복이 원천 차단**되고, TG(수기·기존 자동화) 대역과 완전히 분리되어 ①AI 전표만 골라 조회·회수 가능 ②사고 시 식별 즉시 ③운영 채번과 충돌 0. 포털 측에는 **적용 원장(`gl_erp_apply_log`)**이 모든 시도(리허설 포함)와 발급 번호를 기록·관리한다(성공 커밋의 초안·번호 유니크 제약).

**흐름(1차)**

```
[포털] 초안 작성·검증 7종·제출(submitted)          ← 기존 그대로
   ▼
[적용기] gl_apply_demo2.py  (관리자 PC · --dry-run 리허설 → 확정)
   ①포털 RPC로 초안 회수 ②멱등 3중 확인 ③JNL/EVENT 분개코드 조회(fail-closed)
   ④AG·BT 채번 ⑤A_BATCH/A_BATCH_GL/A_BATCH_GL_ITEM 투입(관리항목 슬롯 평탄화)
   ⑥표준 엔진 usp_a_create_gl_by_batch_01 호출 ⑦라인 완전대조(계정+차대+금액)
   ⑧대조 통과 시에만 COMMIT → ⑨포털 원장 기록 + gl_draft 회기입(AG번호)
   ▼
[DEMO2] A_TEMP_GL 에 AG전표 생성  →  [포털 화면] 「ERP 적용」 열에 DEMO AG번호 표시
```

### 3.1 멱등·중복 방지 3중 (요구: "전표번호 관리·중복 방지")

| 층 | 장치 |
|---|---|
| ERP | 투입 전 `A_BATCH`·`A_TEMP_GL` 에서 `REF_NO(=draft_no)` 선조회 — 존재 시 중단(REF_NO 는 DB 유니크 아님 — 실사 확인) + AG 채번 후 존재 재확인 |
| 포털 원장 | `gl_erp_apply_log` 성공 커밋에 (대상DB, 초안번호)·(대상DB, AG번호) **유니크 인덱스** — 이중 적용을 DB가 거부 |
| 채번기 | ERP `B_AUTO_NUMBERING` 직렬 채번(행 잠금) — AG 번호 자체가 중복 불가 |

### 3.2 분개코드 결정(실사 확정 구조)

`A_JNL_ACCT_ASSN`(거래유형·계정·차대 → `JNL_CD`) → `A_JNL_FORM`(거래유형·JNL_CD → `EVENT_CD`) 2단 조회.
조회 실패 시 실증 폴백 표(부가세대급금 A/A · 미지급금(거래처) AP · 미지급금(법인카드) AP2/CARDC), 그래도 없으면 **중단**(fail-closed — 임의 분개 금지, "분개는 AX가 완성하되 코드는 ERP 설정이 정답").

### 3.3 검증(엔진 호출 후, COMMIT 전)

① `A_TEMP_GL` 전표 생성 확인 ② **투입 라인 ↔ 생성 라인 완전대조**(계정+차대+금액 다중집합 — 엔진이 라인을 재정렬하므로 순번 매칭 금지, 리허설 정정 3) ③ 불일치 시 대차 자동보정 개입으로 판정·ROLLBACK. 관리항목 슬롯 순서는 엔진이 재배치(정정 2 — 코드만 정확히).

## 4. 실행 절차

### 4.1 화면 [🚀 ERP 전송] 방식 (v1.2 신설 — 실사용 테스트 경로)

회계 담당자가 화면에서 버튼을 눌러 전송하고, 사내 중계가 자동 투입한다.
**포털은 여전히 ERP에 직접 쓰지 않는다** — 버튼은 `erp_apply_status='ready'` 마킹만 하고, 투입은 중계가 수행(기회검토 채택 구조: 사내 pull).

```
① 관리자 PC에서 중계를 켠다(감시 모드 — 15초 간격, Ctrl+C 종료)
   ! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --watch
② 회계 담당자: 결의전표 입력 화면 → 「ERP 전송」 탭(v1.5, 구 「회계 담당자」 탭) → 제출된 초안 선택
   → [🚀 ERP 전송 (DEMO2)] 클릭 → 확인
③ 중계가 자동 처리(멱등 확인 → 분개코드 조회 → AG·BT 채번 → A_BATCH 투입
   → 표준 엔진 → 라인 완전대조 → 대조 통과 시 COMMIT)
④ 화면이 4.5초 간격 폴링으로 결과를 자동 감지 → 「ERP 적용」 열에 AG전표번호 표시
   (실패 시 '적용 실패' + 사유. 대기 중 취소는 [전송 취소])
```

상태머신: `null` → **`ready`**(버튼) → **`applied`**(성공, AG번호 회기입) 또는 **`failed`**(실패, 사유 기록).
중계를 상시 켜두지 않을 때는 버튼으로 대기만 걸고, 나중에 `--queue`(대기 건 일괄 처리, 1회 상한 5건)로 처리해도 된다.

### 4.2 CLI 단건 방식 (리허설·정밀 검증용)

```
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --list                      # 적용 대상 확인
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-... --dry-run  # 리허설(ROLLBACK)
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-...            # 확정(COMMIT+회기입)
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-... --cleanup  # 정리(삭제·상태 해제)
```

> 새 케이스(처음 쓰는 계정 조합)는 **먼저 `--dry-run`으로 검증**한 뒤 화면 전송을 쓰는 것을 권장한다.
> 화면 전송 경로는 리허설 없이 바로 확정 투입되지만, 라인 대조 불일치 시 자동 ROLLBACK되므로 안전 경계는 동일하다.

## 6. 운영(JEILMNS) 전환 조건 — 이 문서 범위 밖
