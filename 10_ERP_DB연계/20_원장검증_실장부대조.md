> **AX 로 만든 전표가 사람이 손으로 만든 전표와 장부상 똑같은가.**

## 0. 19번과 무엇이 다른가

| | 19번 세트 | **20번 세트(이 문서)** |
|---|---|---|
| 묻는 것 | **가드가 잘 막는가** | **장부에 똑같이 반영되는가** |
| 전표 출처 | 설계해서 만든 것 | **실제 승인 전표를 복제** |
| 보는 곳 | 전표 안(투입 라인 대조) | 전표 **밖** — 채무·부가세·선급·선수·미결 원장 |
| 판정 | 통과/차단 | **원본과 한 줄도 어긋나지 않는가** |

릴레이가 투입 직후 하는 라인 대조는 *전표 안*만 본다.
**회계가 실제로 쓰는 것은 전표가 아니라 그 전표가 만들어 낸 원장이다.**
채무 잔액이 서고, 부가세 신고자료가 잡히고, 선급이 정산 대기에 올라가는 — 그 결과를 본다.

### 왜 실제 전표를 복제하나

발명한 전표로는 이 비교를 할 수 없다. **대조할 원본이 없기 때문이다.**
DEMO2 에 이미 승인돼 있는 수기 전표를 골라 계정·차대·금액·관리항목을 그대로 복제하면,
같은 분개가 두 경로(수기 / AX)로 들어간 셈이 되고 **원장 결과를 나란히 놓고 뺄 수 있다.**

### 1.1 결과 (2026-08-26 전송)

**7건 전건 일치 · 차이 0.**

```
[V1] AG202608260003 ↔ TG202505200022   부가세 과세표준 200,000 · 세액 20,000 / 채무 220,000
[V2] AG202608260005 ↔ TG202505210011   부가세 2,119,680/211,968 · 채무 2,331,648 · 선급 2,119,680
[V3] AG202608260004 ↔ TG202505230003   채무 114,480 (부가세 0행 — 원본과 같음)
[V4] AG202608260006 ↔ TG202505310074   채권 AR202608260001 (채무·부가세 0행 — 원본과 같음)
[V5] AG202608260007 ↔ TG202505210004   서브원장 대상 없음 · 미결은 승인 후(원본 1행 1,860,000)
[V6] AG202608260001 ↔ TG202505230013   선수 2행 1,571,004  ← 6원·7원 라인 반올림 없음
[V7] AG202608260002 ↔ TG202505210013   서브원장 0 (원본과 같음)
```

**AX 경로가 수기 경로와 장부상 구별되지 않는다** — 7건 전건에서 확인됐다.

> **V4·V5 는 처음에 막혔다가(§2) 부서를 현행으로 바꿔 다시 보냈다.**
> V4 영업팀(`5100`·폐지) → **사업운영팀(`6110`)**, V5 CM2파트(`6630`·폐지) → **사업관리팀(`6120`)**
> — 둘 다 현행 조직이고 상위가 사업부문(`6700`)이라 원 전표 성격에 맞다.
> 코스트센터도 함께 바꿨다(`C016110`·`C016120`).
> **부서가 달라도 대조는 유효하다** — 비교 대상은 계정·차대·금액·관리항목·원장 금액이고
> 부서는 거기 들어가지 않는다.

`V3` 에서 **`43000514 → ADJMNT/DZ`** 가 또 확인됐다 — 원본이 생산팀(`C017100`) 소속이라
직접 코스트센터 경로를 자연스럽게 탔다.

> 사전점검은 7/7 통과였지만 V4·V5 는 실제 전송에서 막혔다.
> **사전점검이 못 보던 구간이 있었다는 뜻이고, 그것이 이 세트의 최대 수확이다(§2).**

## 2. ★ 새로 찾은 결함 — 없어진 부서로는 전표를 만들 수 없다

V4(부서 `5100`)·V5(부서 `6630`)가 **서브원장 생성 단계에서 `A05191`** 로 거부됐다.

> `A05191` = **조직개편과 부서정보가 맞지 않습니다** (ERP 메시지 마스터 `B_MESSAGE`)

### 무엇이 문제였나

`ORG_CHANGE_ID` 는 조직개편 버전이고 DEMO2 의 현행은 **20264** 다(운영은 `20261` — 별개 DB라 번호가 다르다).
릴레이는 「그 부서가 속한 **가장 최신** 조직」을 골랐는데, 없어진 부서는 그 값이 현행보다 과거다.

| 부서 | 소속 조직 | 릴레이가 고른 값 | 결과 |
|---|---|:--:|---|
| 3200 · 6700 · 7100 · 2300 | … 20251, **20264** | 20264 = 현행 | ✅ |
| **5100** | … 20244, 20251 | 20251 | 🚫 `A05191` |
| **6630** | 20244 **뿐** | 20244 | 🚫 `A05191` |

현행에 남아 있는 부서는 「최신 = 현행」이라 우연히 맞아떨어졌다.
**없어진 부서에서만 어긋난다** — 그래서 여태 드러나지 않았다.

### 더 나쁜 점 — 만들었다가 되돌린다

거부는 **전표를 다 만든 뒤** 서브원장 단계에서 온다. 롤백되므로 ERP 에 흔적은 남지 않지만,
**전표번호(AG)는 소모**되고 사용자는 한참 뒤에야 실패를 안다.
사전점검(`--precheck`)도 못 잡았다 — 쓰기 직전에서 멈추므로 그 SP 를 부르지 않기 때문이다.

### 조치 — 쓰기 전에 막는다

`check_dept_org()` 를 신설해 **거래유형 확인 직후**(채번·투입 이전)에 현행 조직 소속을 본다.
이제 사전점검에서도 잡히고, ERP 에는 아무것도 들어가지 않는다.

```
부서 5100 는 현재 조직에 없습니다 (조직개편 20251 까지만 쓰던 부서입니다)
→ 전표 상단에서 지금 쓰는 부서로 바꾸세요
```

> **운영 전환에 미치는 영향**: 폐지 부서로 전표를 넣을 수 없다는 것은 정상 동작이다.
> 문제는 **그 사실을 알려 주는 시점과 문구**였고, 그것을 고쳤다.
> 과거 전표 재현·소급 정산처럼 폐지 부서가 필요한 업무는 ERP 화면 소관으로 남는다.

### 2.1 화면도 고쳤다 — 다만 **코스트센터가 아니라 부서**였다

릴레이가 막아도 **입력 화면이 폐지 부서를 계속 보여주면** 사용자는 보내고 나서야 안다.
그래서 `gl_master_get()` 을 고쳤는데, **처음 생각한 것과 정반대 지점이었다.**

**처음 가설(틀림)**: 「부서가 폐지면 그 부서의 코스트센터도 막아야 한다」
→ 코스트센터 91개 중 55개가 잘린다. 그래서 실사용을 재 봤다.

| 잘릴 코스트센터 | 최근 사용 | 라인 |
|---|---|---:|
| `C015100` 영업팀 | **2026-08-24** | 323 |
| `C016710` 구매파트 | **2026-08-20** | 184 |
| `C017600` 방산제약사업팀 | 2026-03-31 | 61 |
| … 외 6개 | | 합계 675 |

**폐지 부서의 코스트센터를 지금도 쓴다.** 걸렀다면 현업 9개(675라인)를 끊을 뻔했다.

**실제 경계는 헤더 부서였다.** 같은 기준으로 재면 정반대가 나온다.

| | 최근 사용 |
|---|---|
| 폐지 부서를 **코스트센터**로 | **2026-08-24**(계속 쓴다) |
| 폐지 부서를 **헤더 부서**로 | **2026-03-31**(조직개편 이후 0건) |

ERP 가 `A05191` 로 검사하는 것은 **헤더 부서 하나뿐**이고, 코스트센터는 과거 것도 계속 쓴다.

**조치**: `gl_master_get()` 의 **부서 목록만** 현행 조직으로 제한했다. 코스트센터는 그대로 둔다.

| | 전 | 후 |
|---|--:|--:|
| 부서 | 90 | **35** |
| 코스트센터 | 91 | **91**(불변) |

현행 부서 35개는 전부 코스트센터를 갖고 있어 누락이 없다.

> **정정**: 앞서 「중간DB 미러가 한 세대 뒤처져 있다(20261 vs 20264)」고 적었으나 **틀렸다.**
> 미러는 **운영(`JEILMNS`)** 을, 이 검증은 **DEMO2** 를 본 것이라 조직번호가 다를 뿐이다.
> 미러는 2026-08-26 00:58 에 동기화된 최신 상태다.

> **남은 것(별건)**: 사용자-부서 매핑 90명 중 **41명이 폐지 부서**를 가리킨다
> (`2200 원가회계팀`·`5000 영업부문`·`6100 PM팀` 등). 그 사람들은 부서를 직접 골라야 한다 —
> 다만 그 부서로는 어차피 전송이 막히므로, 보내고 실패하는 대신 **입력할 때** 드러나는 편이 낫다.
> 매핑 현행화는 인사·조직 데이터 소관이다.

## 3. ★ 통제 대조 — 「수동으로 못 만드는 전표는 AX 로도 만들 수 없다」

원장이 맞는 것만으로는 부족하다. **AX 가 수동입력보다 느슨하면 통제 우회로가 된다.**
그래서 검증 축을 하나씩 실측으로 맞춰 봤다.

| 축 | 수동입력 | AX | 판정 |
|---|---|---|---|
| 계정 범위 | **제한 없음** — 수기 전표 12,557건이 거래유형 공란이고, 쓴 계정 321종 중 **52%가 매핑 밖** | 마스터 전량 노출 | **동일**(둘 다 자유) |
| 폐지 계정 | 못 씀 | ETL 이 `DEL_FG='Y'` 를 애초에 안 싣는다 | **동일** |
| 반제 방향 | ERP SP 가 막음(`119712`) | 가드 G5 가 **먼저** 막음 | **동일** |
| 부서 ↔ 조직 | ERP 가 막음(`A05191`) | 가드가 **먼저** 막음(§2) | **동일** |
| 부가세 차대 | **ERP 안 막음** | G1 이 막음 | **AX 가 엄격** |
| 차대 균형 | **ERP 안 막음**(`113119` 는 `GL_INPUT_TYPE='GL'` 한정) | G2 가 막음 | **AX 가 엄격** |
| 법인카드 미지급금 | 씀(`AN005` 5,387건) | 금지 | **AX 가 엄격**(이중계상 방지) |
| 마이너스 라인 | 씀(939전표) | **불가**(`CHECK item_amt > 0`) | **AX 가 좁음**(§6) |
| 외화 | 씀(900전표) | **불가**(통화·환율 필드 없음) | **AX 가 좁음**(§6) |
| **필수 관리항목** | **막음** | **릴레이는 안 막았다** 🚨 | **← 갭이었다**(§3.3 정정) |

### 3.1 찾은 갭 — 필수 관리항목을 엔진이 검사하지 않는다

미지급금(거래처) 대변에 **거래처·만기일을 통째로 빼고** 넣어 봤다.

```
[엔진] rc=1 / MSG_CD=(없음)          ← 통과
[연결번호] 2:21100901/AP→AP202608260004
[채무] A_OPEN_AP 1행                ← 거래처 없는 채무가 섰다
```

수동입력 화면은 `A_ACCT_CTRL_ASSN` 의 `DR_FG`/`CR_FG='Y'` 항목이 비면 **저장을 막는다.**
그런데 배치 엔진(`usp_a_create_gl_by_batch_01`)은 **검사하지 않고 그대로 만든다.**

**거래처 없는 채무는 반제도 지급도 할 수 없다.** 장부에는 서 있는데 실무에서 쓸 수 없는 데이터다.

### 3.2 조치 — 가드 G6 신설

투입 전에 계정×차대별 필수 관리항목을 대조한다. 기존 AX 전표 전건을 소급 점검했고 **누락 0건**이라
막던 것을 새로 막는 부작용은 없다.

```
2번 줄 미지급금(거래처) 대변 — 필수 관리항목이 비어 있습니다 — 거래처, 만기일
→ 이 항목들을 채우세요 — 비우면 원장이 만들어져도 쓸 수 없습니다
```

> **가드 현황**: G1 부가세 차대 · G2 차대 균형 · G5 반제 방향 · **G6 필수 관리항목**
> · 부서↔조직 · 금지계정(법인카드).
> 이 중 **G1·G2·G6 은 ERP 배치 엔진이 검사하지 않는 구간**이다.

### 3.3 정정 — 「AX 가 안 막았다」는 부정확했다

위 시험은 **포털 DB 에 직접 INSERT** 해서 만든 것이라 화면·서버 검증을 **건너뛴** 상태였다.
실제로는 이미 두 층이 막고 있었다.

| 층 | 상태 |
|---|---|
| 화면 | 필수(*) 표시·진행률 있음. **저장 전 차단은 없었다** → 이번에 추가 |
| 서버(`op save`) | **이미 하드 차단**(`ctrl_aware=true` → `400 ctrl_required`) |
| 릴레이 | **없었다** → 가드 G6 로 추가 |

정확히는 **「릴레이가 안 막았다」**이고, 화면 경로로 저장한 전표는 애초에 필수 항목을 갖추고 있었다.
그래도 릴레이 가드는 필요하다 — 저장 경로가 무엇이든 **ERP 투입 직전이 마지막 관문**이고,
엔진이 검사하지 않는다는 사실은 그대로이기 때문이다.

**이제 세 층이 같은 기준(`A_ACCT_CTRL_ASSN` 의 `DR_FG`/`CR_FG='Y'`)을 쓴다.**

## 4. 가드 재검증 — 실제 승인 전표 1,500건에 그대로 돌렸다

가드가 잘못된 전표를 막는 것만으로는 부족하다. **정상 업무를 막지 않아야** 한다.
그건 테스트 전표 몇 건으로는 알 수 없어서, **ERP 에 이미 승인돼 있는 수기 전표**에 그대로 돌렸다.
회계가 승인한 전표가 곧 '정상'의 정의다. (도구 `etl/verify_guards.py`, 읽기 전용)

**대상**: 승인 완료 수기 전표 **1,500건 · 15,293라인** (2025-04-02 ~ 2025-06-19)

| 차단 사유 | 전표 | 비율 | 판정 |
|---|--:|--:|---|
| 부서 ↔ 현행 조직 | 578 | 38.5% | **시점 차이** — 아래 참조 |
| 금지계정(법인카드) | 423 | 28.2% | 설계상 범위 밖(카드 채널 담당) |
| 음수 라인 | 130 | 8.7% | 포털 기능 제약(§6) |
| G5 반제 방향 | 129 | 8.6% | 반제 전용화면 소관 |
| 외화 | 61 | 4.1% | 포털 기능 제약(§6) |
| **G1 부가세 차대** | **1** | **0.1%** | 실제 위반 1건(`TG202505090011`) |
| **G2 차대 균형** | **0** | **0%** | — |
| **G6 필수 관리항목** | **0** | **0%** | — |

**핵심: G1·G2·G6 이 정상 업무를 사실상 막지 않는다.** 1,500건에서 걸린 것은 단 1건이고
그것도 **진짜 위반**이다(부가세대급금이 대변에 있는 전표 — `A_VAT` 가 생기지 않는다).

차단의 대부분은 **가드가 아니라 설계상 경계**다 — 법인카드·반제·음수·외화.
이미 알고 있던 것들이고 19번·20번에 각각 근거가 있다.

### 4.1 '부서 38.5%' 는 DEMO2 의 시점 차이다

전표는 2025-04~06 것인데 DEMO2 의 조직은 그 뒤 개편분(`20264`)이다.
**과거 전표를 미래 조직으로 재는 셈**이라 나온 수치다.

```
통과 515 / 1500 (34%)
└ '부서' 하나 때문만: 307건 → 그 몫을 빼면 822 / 1500 (54%)
```

운영에서는 오늘 만드는 전표가 현행 부서를 쓴다 —
실측으로 **폐지 부서를 헤더로 쓴 마지막 전표가 2026-03-31**, 조직개편 이후 0건이다(§2.1).

### 4.2 재검증이 잡은 도구 버그

처음 돌렸을 때 **G2 가 33건** 나왔다. 사례를 열어 보니 차이가 41억·3.4억이었다.
원인은 가드가 아니라 **검증 도구**였다 — 외화 전표의 `ITEM_AMT` 는 외화 금액인데
그대로 더했다. 원화(`ITEM_LOC_AMT`)로 바꾸니 **0건**이 됐다.

> 포털은 KRW 만 다루므로 **릴레이 G2 에는 이 문제가 없다.**
> 다만 「실측 33건」을 그대로 믿었다면 없는 문제를 고치려 들었을 것이다.

## 5. 무엇을 대조하나

`verify_ledger.py` 가 AX 전표(`AG…`)와 원본(`TG…`)을 나란히 놓고 비교한다.

| # | 대상 | 비교 방식 |
|:--:|---|---|
| ① | 전표 라인 | 계정·차대·금액을 **다중집합**으로 — 엔진이 순서를 바꾸므로 순서는 보지 않는다 |
| ② | 관리항목 | (계정·차대·코드·값) 다중집합. **날짜형은 제외** — 복제할 때 오늘로 옮겼다 |
| ③ | 부가세 `A_VAT` | 건수 · 과세표준 · 세액 |
| ④ | 채무 `A_OPEN_AP` | 건수 · 금액 · 거래처 수 |
| ⑤ | 선급 `F_PRPAYM` | 건수 · 금액 |
| ⑥ | 선수 `F_PRRCPT` | 건수 · 금액 |
| ⑦ | 미결 `A_OPEN_ACCT` | 건수 · 금액 · 관리값(사번) — **승인 후에만 생긴다**(`GL_NO` 기준) |

미결은 승인 시점에 서므로, AX 쪽이 아직 승인 전이면 **차이가 아니라 「아직」** 으로 표시한다.

## 6. 복제 규칙 — 무엇을 그대로 두고 무엇을 옮기나

| | 처리 |
|---|---|
| 계정 · 차대 · **금액** | **원본 그대로.** 비교 대상이 바로 이것이다 |
| 거래처(BP) · 사번(EM) · 프로젝트(PC) · 발주(PO) | **원본 그대로** |
| 전표일자 | **오늘로 이동** — 닫힌 회계기간에는 넣을 수 없다 |
| 날짜형 관리항목(계산서일 `V2`·만기일 `C1`·`XC1`) | 전표일자에 맞춰 이동 (그래서 대조에서 제외) |
| 적요 | `ax검증_Vn <원본적요> (원본 TG…)` — 추적 가능하게 |

### 민감값을 저장소에 두지 않는다

거래처·사번·계좌·프로젝트 값은 **코드에 없다.** 실행할 때 원본 전표에서 읽어 온다.
저장소에 남는 것은 **원본 전표번호뿐**이다(`CLAUDE.md §1`). 화면 출력도 앞 2자리만 보인다.

> **주의**: 같은 분개가 DEMO2 에 두 번 들어간다(원본 + 복제). 비용이 이중 계상된다.
> **DEMO2 는 테스트 DB 이므로 의도된 것**이지만, 운영에서는 절대 이렇게 하지 않는다.

운영 전환 전 결정이 필요하다(19번 §4.1). §3 표의 「AX 가 좁음」 두 줄이 이것이다.

## 8. 사용법

```bash
python 10_ERP_DB연계/etl/seed_ledger_cases.py --plan    # 무엇을 복제할지 보기
python 10_ERP_DB연계/etl/seed_ledger_cases.py --load    # 포털에 적재(제출됨)
python 10_ERP_DB연계/etl/gl_apply_demo2.py  --precheck  # 보내기 전 점검(ERP 무투입)
#  → 화면 [ERP 전송] 탭에서 보내기 → ERP 화면에서 승인
python 10_ERP_DB연계/etl/verify_ledger.py               # 장부 대조
python 10_ERP_DB연계/etl/verify_guards.py               # 가드 재검증(실전표 전량, 읽기 전용)
python 10_ERP_DB연계/etl/seed_ledger_cases.py --purge   # 정리(적용된 건은 보존)
```

`verify_ledger.py` 는 **읽기 전용**이고 차이가 있으면 종료코드 1을 돌려준다 — 자동화에 걸 수 있다.

### 판정

| 결과 | 뜻 |
|---|---|
| `✅ 라인·관리항목·원장 전부 일치` | AX 경로가 수기 경로와 **장부상 구별되지 않는다** |
| `❌ <원장>: 원본 N행 … ↔ AX M행 …` | 그 원장에서 어긋났다 — 금액·건수·거래처를 확인 |
| `⏳ 미결 … 승인 후에 생깁니다` | 차이가 아니다. ERP 에서 승인하면 채워진다 |
