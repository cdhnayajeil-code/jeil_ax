AX 전표 — 거래유형 체계 적정성 검토

발신 ERP_DB 작업환경 (최동혁) · 수신 JEIL_AX 프로젝트 / 회계팀 작성 2026-08-25 · 근거 JEILMNS_DEMO2 실측 + SP 소스 (READ-ONLY) 배치 제안 10_ERP_DB연계/16_AX전표_거래유형체계_적정성검토.md 질문 "거래항목·거래유형은 타모듈 자동분개용으로 보이는데, 결의전표 수기입력을 재현하려는 AX 가 이걸 쓰는 게 맞는가"

0. 결론

관찰이 정확하다. 거래유형·거래항목은 타모듈 자동분개 기준정보이고, 결의전표 수기입력과는 무관하다. 실제로 수기입력 전표 12,085건은 거래유형이 전부 공란이다.

그럼에도 AX 가 AX001 을 쓰는 것은 구조적으로 불가피하고, 결과적으로 문제가 없다.

질문 답
거래유형·거래항목이 수기입력과 무관한가 맞다. 수기 12,085건 전부 TRANS_TYPE 공란
AX 는 왜 거래유형을 만들었나 화면이 아니라 엔진(SP) 을 쓰기 때문. A_BATCH 경유 SP 는 거래유형이 없으면 120110 오류로 실패한다 — 선택의 여지가 없었다
타모듈 연동 형태로 적용된 것인가 맞다. 다만 그것이 결과를 다르게 만들지는 않는다
이대로 가도 되는가 된다. 최종 산출물이 수기와 동일함을 실측 확인. 단 §6 관리사항 3건

1. 두 체계가 겹쳐 보이는 이유

ERP 안에는 전표를 만드는 방식이 두 가지 있고, 서로 다른 기준정보를 쓴다.

체계 A — 자동분개 (타모듈 → 회계)

재고·구매·영업·자금·인사가 업무를 처리하면 회계전표가 자동으로 만들어진다. 이때 "차/대변에 어떤 계정이 오는가"를 시스템이 스스로 결정해야 한다. 그 기준정보가 이것이다.

기준정보 테이블 메뉴 역할
거래항목 A_JNL_ITEM 거래항목등록 (A2106MA1) 분개 시 차/대변 계정코드를 결정하기 위한 항목
거래유형 A_ACCT_TRANS_TYPE 거래유형등록 (A2105MA1) 업무별 거래 단위. 전표구분(결의/회계)·계정합·생성순서
분개형태 A_JNL_FORM — 거래유형 × 거래항목 × 차대
계정배정 A_JNL_ACCT_ASSN — 위 조합에 어떤 계정을 배정할지

거래항목등록 화면 설명문이 이를 그대로 말한다.

"업무별로 발생할 수 있는 거래유형에 대하여 분개 시 차/대변에 발생되는 계정코드를 결정하기 위한 항목을 사전에 설정하는 화면"

체계 B — 수기입력 (결의전표 화면)

사용자가 계정을 직접 고른다. 시스템이 계정을 결정할 일이 없으므로 위 기준정보가 필요 없다.

실측

구분 전표수 TRANS_TYPE
결의전표 수기입력 12,085 전부 공란
법인카드 연동 5,387 AN005
타모듈 연동 4,044 M0001·S0001·FN001 …

수기입력에 거래유형을 쓴 전표는 한 건도 없다. 관찰이 맞다.

2. 🔑 거래항목(JNL_CD)은 전표에 남지 않는다

이것이 이해의 열쇠다.

테이블 JNL_CD 컬럼 의미
A_BATCH_GL_ITEM (투입) 있음 엔진에 넘기는 입력 파라미터
A_TEMP_GL_ITEM (결의전표) 없음 —
A_GL_ITEM (회계전표) 없음 —

거래항목은 전표를 만드는 순간에만 쓰이고 전표에는 흔적이 남지 않는다. 만들어진 결의전표만 놓고 보면 수기 전표와 거래항목 측면에서 구별 자체가 불가능하다.

그래서 "거래항목등록 메뉴가 결의전표입력과 관계없어 보인다"는 관찰이 정확한 것이다. 실제로 관계가 없다.

3. 그런데 왜 AX 는 거래유형이 필요했나

AX 릴레이는 화면이 아니라 엔진(SP) 을 호출한다. 화면 로직을 재현할 수 없기 때문이다.

수기입력   화면 ──────────────────────────→ A_TEMP_GL 직접 INSERT
                                              (거래유형 불필요)

AX 릴레이  A_BATCH 3종 ──→ usp_a_create_gl_by_batch_01 ──→ A_TEMP_GL
                            (거래유형 필수)

엔진이 거래유형을 요구하는 지점

USP_A_MAKE_VAT_ACCT_01 첫머리다.

SELECT @CTRANS_TYPE = MIN(TRANS_TYPE) FROM A_BATCH_GL_ITEM WHERE BATCH_NO = @BATCH_NO
IF @@ERROR <> 0 OR @@ROWCOUNT < 1 BEGIN SET @MSG_CD = '120110' GOTO ERROR_RETURN END

SELECT @CTRANS_TYPE = A.TRANS_TYPE, @TRANS_REVERSE_FG = A.REVERSE_FG
FROM   A_ACCT_TRANS_TYPE A WHERE A.TRANS_TYPE = @CTRANS_TYPE
IF @@ERROR <> 0 OR @@ROWCOUNT < 1 BEGIN SET @MSG_CD = REF00 + '120110' … GOTO ERROR_RETURN END

120110 = "거래유형 데이터가 존재하지 않아 저장에 실패했습니다."

이어 usp_a_create_gl_01 이 거래유형에서 결의/회계 분기(GL_POSTING_FG)·계정합·생성순서를 읽는다. 거래유형이 없으면 결의전표로 떨어뜨릴지 회계전표로 떨어뜨릴지조차 정할 수 없다.

컬럼 정의로도 확인된다

테이블 TRANS_TYPE NULL 허용 FK
A_BATCH_GL_ITEM 투입 허용 있음
A_TEMP_GL 결의전표 허용 없음
A_GL 회계전표 허용 없음

NULL 을 넣어도 FK 는 통과하지만 엔진이 120110 으로 막는다. usp_a_create_gl_direct 등 A_BATCH 경유 SP 는 전부 같은 구조다.

결론 — AX 가 A_BATCH 경유 엔진을 쓰기로 한 순간 거래유형은 구조적 필수였다. 임의 선택이 아니라 제약이었다.

4. 그래서 결과가 달라지는가 — 실측

판정 기준은 하나다. 완성된 전표가 수기와 같은가.

항목 수기입력 AX (AX001) 판정
A_TEMP_GL_ITEM 61컬럼 기준 누락 0개 (전수 대조) 동일
관리항목 A_TEMP_GL_DTL 12,037전표 보유 15전표 보유 동일
서브원장 (A_OPEN_AP·A_VAT·F_PRPAYM) 생성 생성 (개선 후) 동일
연결번호 SUBSYS_NO 채움 채움 동일
정식장부 전기 · 연결번호 승계 정상 정상 동일
입력검증 (usp_a_check_acct) 적용 적용 (개선 후) 동일
JNL_CD 거래항목 전표에 없음 전표에 없음 동일
TRANS_TYPE 공란 AX001 유일한 차이

그 유일한 차이는 어디에 영향을 주는가

A_TEMP_GL.TRANS_TYPE 을 참조하는 DB 개체 35개를 전수 확인했다.

계열 개체 개수
전표 생성 usp_a_create_gl_* · usp_a_create_ap/ar_* · *_BATCH_* · USP_INTERFACE_KO174 · *_POSTING 35
조회 · 리포트 · 집계 — 0

TRANS_TYPE 은 전표를 만들 때만 쓰이고, 만들어진 뒤에는 아무도 보지 않는다. 조회 화면·리포트·시산표·재무제표 어디에도 영향이 없다.

오히려 자산이다

TRANS_TYPE='AX001' 덕분에 AX 채널로 들어온 전표를 한 줄로 골라낼 수 있다. 수기 전표는 공란이라 구분이 안 된다. 감사·통계·사후 추적 관점에서 이건 손실이 아니라 이득이다.

5. 방향성 판정 — 이대로 가도 된다

근거 1 — 결의전표 거래유형은 이미 20종이 운영 중이다

GL_POSTING_FG='T'(결의전표) 거래유형 중 실사용 실적이 있는 것들이다.

거래유형 이름 업무 결의전표수
AN005 법인카드연계 회계 5,387
AG001 멀티반제 회계 1,698
M0001 매입확정 구매 1,547
S0002 국외매출 영업 305
S0001 국내매출 영업 230
FN001 어음할인 자금 79
AS001 유형자산취득 회계 53
AX001 AX자동전표 — 15
그 외 12종 1~35

결의전표를 거래유형으로 만드는 것은 예외가 아니라 표준이다. AX001 은 그 계열의 하나다.

근거 2 — 엔진을 쓰기 때문에 공짜로 얻는 것들

얻는 것 직접 INSERT 로 갈 경우
관리항목 자동 전개 (계정별 슬롯 배치) 직접 구현
부가세 라인 분리 (ACCT_TYPE VP/VR) 직접 구현
대차 보정 · 본지점 · 환차 처리 직접 구현
입력검증 usp_a_check_acct (반제방향·조직·사업장) 직접 구현
서브원장 생성 + 연결번호 채번 직접 구현
마감·폐쇄계정 체크 직접 구현

엔진을 버리면 이 전부를 재구현해야 한다. 그리고 그것은 ERP 벤더 로직을 복제하는 일이다.

근거 3 — 운영 선례가 이미 같은 구조다

AG001(멀티반제) 는 A_BATCH 경유 + 거래유형 + 결의전표 로 1,698건이 운영 중이다. 전표번호는 TG…, 채널 식별은 REF_NO(UX…). AX 가 하려는 것과 구조가 같다.

6. 관리해야 할 것 3건

이대로 가되, 아래는 인지하고 관리해야 한다.

① AX001 은 자동분개 매핑이 비어 있다

계층 AX001 AG001 AN005
분개형태 A_JNL_FORM 0 18 90
계정배정 A_JNL_ACCT_ASSN 0 14 76
통제배정 A_JNL_CTRL_ASSN 0 25 158

의도된 상태다. AX 는 포털이 계정을 완결해 보내므로(MAKE_ACCT_FG='Y') 매핑을 타지 않는다.

다만 회계팀이 거래유형등록 화면에서 AX001 을 보면 "설정이 안 된 거래유형" 으로 보인다. 운영 인수인계 문서에 "AX001 은 외부가 계정을 직접 지정하므로 분개형태·계정배정이 없는 것이 정상" 을 명시해야 한다.

② MAKE_ACCT_FG='Y' 에 의존한다

포털이 MAKE_ACCT_FG='N'(엔진이 계정 결정) 으로 보내면 매핑 0건이라 REF01 110423 으로 실패한다. 릴레이는 항상 'Y' 로 고정해야 하며, 이 전제가 문서화돼 있어야 한다.

③ 거래항목(JNL_CD)은 무검증 통과 파라미터다

전표에 남지 않고, 매핑도 없으므로 어떤 값을 넣어도 통과한다(A_JNL_ITEM FK만 만족하면 됨). 실제로 AX 테스트 전표는 AN005식(계정코드 자기참조 43000501, EVENT_CD='IZ')과 S0003식(A·AP)을 섞어 넣었는데 아무 경고 없이 통과했다.

→ 릴레이가 넣는 JNL_CD 규칙을 한 가지로 고정하고 문서화해야 한다. ITGC 관점에서 "통제 없는 자유 입력 필드"로 지적될 수 있다.

9. 한 장 요약

                    거래항목 · 거래유형
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
   체계 A 자동분개                      체계 B 수기입력
   (타모듈 → 회계)                      (결의전표 화면)
        │                                   │
   계정을 시스템이 결정                 계정을 사용자가 결정
   → 기준정보 필수                      → 기준정보 불필요
        │                                   │
   A_BATCH 경유 엔진                    A_TEMP_GL 직접 INSERT
        │                                   │
        │                              TRANS_TYPE 공란 (12,085건)
        │
   ┌────┴────┐
   │         │
 타모듈    AX 릴레이  ← 업무는 체계 B 를 재현하지만
                        수단은 체계 A 를 쓴다
                        → 거래유형 AX001 이 구조적 필수
                        → 결과물은 체계 B 와 동일

업무 목적은 수기입력 재현이 맞다. 다만 그것을 구현하는 수단이 엔진일 뿐이고, 수단이 요구하는 형식(거래유형)을 갖췄다고 해서 결과가 타모듈 전표가 되지는 않는다.
