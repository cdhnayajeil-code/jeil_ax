# 06. 결의전표 입력(초안) — 향후 추진계획

> **작성일: 2026-07-31**(v1.0) · 관리: 최동혁 · 전담 에이전트: `erp-db-link-manager`
> 결의전표 초안 입력 파일럿의 **남은 일**만 다룬다. 완료된 구축 내역은 `00_현재상태_스냅샷 §4`, 작업 이력은 `02_진행상태 §3`에 있다.
> 비밀값(접속 IP/ID/비밀번호) 기록 금지 — 서버 지칭은 별칭 **"ERP운영DB"** 만 사용.

## 3. 실행 단계

### ✅ S1. 회계 마스터 실적재 — **완료(2026-08-03)**

> 실행 결과: `acct_master` 691/691 · `cost_center` 133/133(유실 0) · `batch_run` success 2건 · `erp_load_scope` 2건 `loaded` 기록 · 연동 현황 뷰 11→13종 확장 · 화면 마스터 미적재 배너 해소.
> **발견 1건**: `project_fg`가 691행 전량 NULL이라 서버 검증 5번(프로젝트 필수 계정)이 무력 상태 — A5·유니포인트 확인 대상.
> 아래는 실행 기록(재실행 시 참고).

관리자가 직접 실행한다(에이전트 자동 실행 차단 — 운영데이터 반출).

```bash
# 1) 검증 (이미 통과: 691행 / 133행) — 재확인용
python 10_ERP_DB연계/etl/etl_run.py --job acct_master --dry-run
python 10_ERP_DB연계/etl/etl_run.py --job cost_center --dry-run

# 2) 실적재
python 10_ERP_DB연계/etl/etl_run.py --job acct_master
python 10_ERP_DB연계/etl/etl_run.py --job cost_center
```

**완료 기준**
- `erp_ro.acct_master_s` 691행 내외 · `erp_ro.cost_center_s` 133행
- `etl_meta.batch_run`에 success 2건, `rows_read = rows_upserted`(유실 0)
- 화면 새로고침 시 "계정과목 마스터가 아직 적재되지 않았습니다" 배너가 사라지고 계정 드롭다운이 채워짐
- `erp_load_scope`의 `accounting/acct_master`·`cost_center`를 **`loaded`로 기록**(관리자 콘솔 「미연계 항목 현황」)

### S2. 전표형태·등록자 형식 확정 — *선행: A2*

`A_TEMP_GL` 최근 건에서 확인할 것:

| 확인 항목 | 왜 | 반영 위치 |
|---|---|---|
| `INSRT_USER_ID` 형식 | 이메일형인지 사번형인지 — 이메일형이면 현재 자동매핑 그대로 확정 | `gl_erp_user` RPC(변경 불필요 예상) |
| `GL_TYPE` 실제 코드값·의미 | 화면 전표형태 드롭다운 | `pages/자금_결의전표_입력_2026.html`의 `fType` 옵션 |
| `GL_INPUT_TYPE` 값 | 수기입력 구분 코드가 필요한지 | 필요 시 `gl_draft.gl_type` 옆에 컬럼 추가 |
| `CONF_FG` 초기값 | 결의 직후 미승인 표기 | 참고용(포털은 저장하지 않음) |

**완료 기준**: 드롭다운이 ERP 실제 코드로 교체되고, 등록자 형식이 이메일형이 아닐 경우 매핑 로직이 보정됨.

### S3. 권한 부여 — *선행: A3·A4*

관리자 콘솔(`04_챗봇_포털_데모UI.html` → 관리자 → 권한 상세)에서:
1. `accounting` 모듈을 `dept_erp_scope`에 신설·부여 (자금팀·내부회계관리팀 + 파일럿 대상 부서)
2. 파일럿 대상자가 부서 밖이면 **개인 예외**(`perm_grant`)로 부여
3. ERP 확정 권한은 별도 부여 불필요 — 기존 `finance` 모듈 보유자(자금팀·내부회계관리팀)가 회계 담당자 탭을 자동으로 본다

**완료 기준**: 대상자 로그인 시 포털 메인에 「결의전표 입력(초안)」 카드가 보이고, 비대상자에겐 보이지 않음. URL 직접 접근도 차단(`_access-gate.js`).

### S4. 계정 선택지 정리 — *선행: A5*

691개 전체를 그대로 두면 실무자가 고르지 못한다. A5에서 받은 경비 계정 후보로 좁힌다.

- 방법 ①(권장·간단): 화면에서 `bs_pl_fg`(손익)·계정 후보 목록으로 필터 — 코드 수정만, DB 무변경
- 방법 ②: `erp_ro.acct_master_s`에 `pilot_use` 플래그 컬럼 추가 후 관리자가 관리
- 마감월은 `gl_period_lock`에 등재(예: `2026-06` 이전 전량 잠금)

**완료 기준**: 드롭다운이 실무에서 쓰는 계정 위주로 정리되고, 마감된 월 선택 시 저장이 거부됨.

### S5. 엔드투엔드 테스트 1건 — *선행: S1·S3 (S2·S4 권장)*

**실제 전표 1건을 끝까지 흘려본다.** 이것이 파일럿의 본체다.

| 순서 | 행위자 | 내용 | 확인 |
|---|---|---|---|
| 1 | 파일럿 대상자 | 경비 지출결의 초안 작성 (차변 여비교통비 / 대변 미지급금) | 등록자가 본인 ERP ID로 자동 표기 |
| 2 | 〃 | 차변·대변을 일부러 다르게 입력 후 제출 시도 | **차단**되고 차액이 표시됨 |
| 3 | 〃 | 금액 맞춘 뒤 임시저장 → 제출 | 초안번호 발급, 상태 `제출됨` |
| 4 | 회계 담당자 | 「회계 담당자」 탭에서 초안 확인, 값 복사 | ERP 입력용 요약이 정확히 표시 |
| 5 | 〃 | **ERP 결의전표 화면에 동일 값 입력·저장** | ERP에 정상 등록 |
| 6 | 〃 | 저장된 `TEMP_GL_NO`를 포털에 회기입 → 확정 | 상태 `확정됨`, 작성자 화면에도 전표번호 표시 |
| 7 | 관리자 | 대사 — 포털 초안 vs ERP 전표 | 금액·계정·등록자·적요 일치 |

**추가로 반드시 볼 것(서버 검증 우회 시도)**: 화면을 거치지 않고 API에 ①차대 불일치 ②존재하지 않는 계정코드 ③타인 UPN을 담아 호출 → **전부 거부**되는지. 프론트 검증만으로는 불충분하다(CLAUDE.md §5.4).

**완료 기준**: 7단계 전부 통과 + 우회 시도 전건 차단 + `gl_draft_log`에 조회·저장·제출·확정이 남아 있음.

### S6. 파일럿 회고·확대 판단 — *선행: S5*

전표 5~10건을 처리해 본 뒤 판단한다. **자동으로 확대하지 않는다.**

점검 질문:
- 실무자가 ERP 화면보다 쉽다고 느끼는가? (아니라면 이 기능의 존재 이유가 없다)
- 회계 담당자의 **이중 작업**이 감당 가능한가? (포털 확인 + ERP 재입력 — 이게 파일럿의 최대 약점)
- 전표번호 회기입이 실제로 지켜지는가? 누락 시 어떻게 발견되는가?
- 어떤 케이스가 추가로 필요한가? (법인카드·세금계산서 매입 등)

## 4. 확대 로드맵 (파일럿 이후 — 미확정)

| 단계 | 내용 | 선결 조건 | 비고 |
|---|---|---|---|
| **E1** | 케이스 확대 — 법인카드 사용, 세금계산서 매입 | 파일럿 성공 + 회계 규칙 추가 확정 | 부가세(`VAT_TYPE`) 계산 로직 필요 — 난이도 상승 |
| **E2** | 대상자 확대 (부서 단위 → 전사) | S6 회고 통과 + 회계팀 수용 가능 판단 | 회계 담당자 부하가 병목 — E3 없이는 한계 |
| **E3** | **ERP 자동 등록** (쓰기 API) | **유니포인트 협의 필수** + 경영 승인 | 이중 작업을 없애는 유일한 길. 현재 절대규칙상 불가(§1.2) — 별도 과제로 승격 필요 |
| **E4** | 그룹웨어 전자결재 연동 | E3 + 그룹웨어 API 확인 | 참조번호 수기 입력 → 결재 문서번호 자동 연결 |
| **E5** | 전표 조회(내가 올린 전표의 ERP 승인 상태) | `A_TEMP_GL` 조회 개방 승인 | 현재는 의도적 미연계(`erp_load_scope`에 등재) |

> **E3이 핵심 갈림길이다.** 파일럿은 "포털 입력 + 사람이 ERP 재입력"이라 회계 담당자 일이 오히려 늘 수 있다. 실무 확대를 원하면 E3(쓰기 API) 협의를 언제 시작할지가 실질적인 의사결정 지점이다.

## 5. 리스크·주의점

| 리스크 | 영향 | 현재 대비책 | 잔여 |
|---|---|---|---|
| **이중 입력** — 같은 건이 ERP에 두 번 등록 | 회계 오류 | DB 제약(`posted`면 전표번호 필수) + 동일 전표번호 중복 거부 + 미기입 초안 목록 경고 | 회기입 자체를 잊는 것은 못 막는다 → S6에서 운영 규칙 필요 |
| **회계 담당자 부하** | 파일럿 실패 원인 1순위 | ERP 입력용 요약·복사 버튼으로 재입력 부담 완화 | 근본 해소는 E3(쓰기 API) |
| **잘못된 계정 선택** | 분개 오류 | 계정 유효성 서버 검증, 프로젝트 필수 계정 강제 | 계정 **선택의 적절성**은 기계가 판정 못 함 → A5 필요 |
| 마감월 전표 입력 | ERP 거부·재작업 | `gl_period_lock` 구조 완비 | 마감 기준 미등재(A5) — 현재 제한 없음 |
| 회계 데이터 민감도 | 정보 노출 | RLS 전면차단·Edge Function 단일 경로·전 접근 감사 | 금액이 담기는 첫 포털 쓰기 기능 → 실사용 직전 `/security-review` 권장 |
| ERP 접속이 관리자 개인 계정 | 회계 확대 시 차단 요인 | — | 전용 읽기계정 `jeilax_ro` 발급(P1 유니포인트 협의) |

## 6. 미결정 사항 (결정되면 이 문서 갱신)

1. **부가세 처리** — 파일럿 경비 케이스는 부가세 미사용으로 두었다. 세금계산서 매입(E1)으로 넘어가면 `VAT_TYPE`·`VAT_AMT` 계산 규칙 확정 필요.
2. **프로젝트 필수 계정 범위** — 현재 `A_ACCT.PROJECT_FG='Y'`를 그대로 따른다. 실무와 다르면 조정.
3. **초안 보존기간** — `gl_draft`·`gl_draft_log` 보존 정책 미정. 개인정보 보존기간 점검(CLAUDE.md §11-E)과 함께 정리 필요.
4. **확정 권한 분리** — 현재 ERP 확정은 `finance` 모듈 보유자 전체다. 특정 담당자만으로 좁힐지 판단 필요.
5. **E3(쓰기 API) 착수 시점** — 유니포인트 협의 의제에 언제 올릴지.
