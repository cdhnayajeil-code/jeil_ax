09. 결의전표 파일럿 — 종합 인수인계

작성: 2026-08-03(v1.0, 이후 v1.1 · 2026-08-05 / v1.2 · 2026-08-11 / v1.3 · 2026-08-18 / v1.4 · 2026-08-18 / v1.5 · 2026-08-19 / v1.6 · 2026-08-20) · 관리: 최동혁 · 전담 에이전트: erp-db-link-manager 결의전표 초안 입력 파일럿의 전체 그림과 재개 절차를 한 문서에 모았다. 시간이 지나거나 담당이 바뀐 뒤 여기부터 읽으면 바로 이어서 진행할 수 있게 쓴다. 세부는 06(추진계획)·07(연동 종합)·08(처리 프로세스)에 있고, 이 문서는 진입점 + 재개 체크리스트다. 비밀값(접속 IP/ID/비밀번호) 기록 금지 — 서버 지칭은 별칭 "ERP운영DB" 만 사용.

1. 30초 요약

무엇을 만들었나 — 전 직원이 ERP 화면에서 각자 입력하던 결의전표를, 케이스 1개(일반 경비 지출결의)에 한해 사내 포털에서 ERP와 같은 형태로 입력받는 기능. 포털은 검증된 초안까지만 만들고, ERP 등록은 회계 담당자가 직접 한다.

지금 어디까지 왔나 — 코드·DB·화면 배포 완료, 회계 마스터 적재 완료, 코드 체계 실측 확정 완료. 라이브에서 관리자 계정으로 동작한다. 2026-08-05 템플릿 플랫폼(케이스별 분개 형태를 등록해 두고 골라 쓰는 구조)을 얹었다 — 구조는 완성, 등재된 템플릿은 0건(§3.4). 2026-08-10~11 별도 트랙(반복전표 자동화)의 분석·기획이 추가됐다 — ERP 2026년 수기 결의전표 2,287건을 전수 분석해 반복 패턴 156개(964건·42.2%)를 확인하고, 이를 템플릿 플랫폼 v2로 잇는 10_반복전표_자동화_기획.md(v1.1)를 신설했다. 이 트랙은 아래 S5 E2E 테스트와 독립적이며, 진행하려면 승인 게이트 B1(관리항목 마스터 적재)·B2(시드 검수+회계 규칙 확정)·B2-1(마감 기준)이 먼저 필요하다. 상세는 10_반복전표_자동화_기획.md §8. 2026-08-18 「전표복사」 기능 신설·배포 + 결의전표 원장 미러링 결정(C-10) — 같은 날 오후 실적재까지 완료 — 본인이 ERP에 입력한 결의전표를 조회·미리보기·복사해 초안을 시작하는 탭을 추가했고, 이를 뒷받침하기 위해 A_TEMP_GL 3종(헤더·라인·관리항목)을 중간DB에 미러링하는 결정을 내렸다(C-7 확장, §2 C-10). 코드·DDL·화면 배포, ERP운영DB dry-run 검증(3,224·16,865·42,371행)에 이어 관리자가 직접 실행해 실적재까지 완료했다 — gl_slip_s 3,226행·gl_slip_item_s 16,879행·gl_slip_ctrl_s 42,422행, 민감 관리항목 마스킹·조회 RPC 소유 필터 실측 확인(상세 §3.2). 잔여는 야간배치 스케줄 편입뿐이다. 2026-08-18(저녁) char 패딩 결함 해소 + 검색 팝업·디자인 개선 배포(v5.1) — 결의전표 입력 화면에서 관리항목·거래처가 표시되지 않는 문제의 원인이 ERP char 컬럼의 트레일링 스페이스임을 발견해 해소했다(3중 대응: 미러 5테이블 trim 마이그레이션 + ETL RTRIM + 화면·서버 trim 방어). 같은 배포에서 계정과목·거래처 검색 팝업, 관리항목 참조검색(품목·거래처)이 신설됐다. 상세는 §3.1·§5 참조. 2026-08-20 부가세 자동계산 도입(결정 C-14, B2 개정) + 총액배분 고도화·결함 3건 수정·정보구조 개편 — 결의전표 입력 화면에 4건이 배포됐다. 부가세는 화면에서 자동계산하도록 범위를 넓혔다(서버는 검증만, 사용자 수정값 미override) — 세율은 운영전표 실측 근거(A·B·L 유형 10% 자동, K·C 0%, I 수입·H 통관은 과세표준에 관세가 섞여 자동계산 제외). 원천징수는 계속 범위 밖이라 U-1은 부가세 부분만 해소하고 원천징수 부분은 미결로 남는다(§8). 같은 배포에서 템플릿 총액 배분을 세금계산서형 우선분리로 고도화하는 과정에서 결함 3건(균등분할로 총액 축소·영세율 균등분할 누락·반올림 오판)을 테스트가 사전 검출해 즉시 수정했고, 전표 시작 경로 4곳을 「전표 시작 바」로 통합(전표복사 탭 제거, 5→4탭)하는 정보구조 개편도 함께 배포됐다(jsdom 테스트 100건 이상 통과). 상세는 §2 C-14·§8. 2026-08-19 신규 트랙 "ERP 직접등록 — 1차(DEMO2)" 개시(결정 C-11) — 이 파일럿의 "초안은 포털, 확정은 ERP"(C-1) 구조 중 회계 담당자의 ERP 재입력 단계를, 데모 DB JEILMNS_DEMO2 한정으로 자동화 실증하는 별도 트랙이 시작됐다. 운영(JEILMNS) 쓰기는 여전히 금지(C-1 유지) — 전용 채번 대역(AG)·적용기·포털 원장·Edge Function v5.2·화면까지 구축을 마쳤고 DEMO2 읽기전용 실사도 완료했으나, 실제 투입은 관리자 직접 실행 대기다. 이 트랙은 아래 S5 E2E 테스트·반복전표 자동화 트랙과 모두 독립적이며, 신규 문서 11_ERP직접등록_DEMO2_1차.md(v1.0)에 전체 내용이 있다. §2 C-11 참조.

다음에 할 일 딱 하나 — 전표 1건 E2E 테스트(S5). 지금 바로 실행 가능하다(반복전표 자동화 트랙과 무관하게 그대로 유효).

남은 승인 — A5(회계 규칙) 하나뿐. 계정 691개를 실무용으로 좁히는 문제라 테스트에는 지장 없다.

3.4 템플릿 플랫폼 (2026-08-05 신설)

왜 만들었나 — 전 직원이 691개 계정에서 매번 고르는 것은 현실적이지 않다. 케이스별로 "어떤 계정을 차/대변에 쓰고 금액을 어떻게 나누는가"를 미리 등록해 두고, 사용자는 템플릿을 고르고 총액만 입력한다.

요소 내용
공개 범위 org(전사) · dept(부서) · user(개인). 전사·부서 템플릿은 관리자·회계 담당자만 생성·수정 — 잘못된 분개가 전사로 퍼지는 것을 막는다
금액 방식 total(총액 1칸 → 규칙대로 배분) · manual(라인별 직접 입력)
배분 규칙 input(사용자 입력) · pct(총액×비율) · fixed(고정액) · balance(차액 자동, 방향당 1줄)
화면 동작 카드 선택 → 총액 입력 → [템플릿 적용] → 헤더 빈 칸만 채우고 라인 전체 교체. 「선택 행에 차액 채우기」 버튼 별도 제공
역방향 「현재 전표를 템플릿으로」 — 작성 중인 라인을 템플릿 편집기로 가져온다(금액은 규칙으로 전환, 실적 금액 미저장)
사용 기록 use_cnt·last_used_at — 실제로 쓰이는 템플릿을 가려내는 근거(케이스 정리 시 사용)
ERP 케이스 연결 erp_case_cd 필드 — ERP_DB 기준 케이스 확정 시 여기에 코드를 채운다(현재 공란)

중요 — 템플릿을 적용해도 검증은 면제되지 않는다. 적용 결과는 save 의 서버 재검증(차대일치·계정유효·금액·마감월·프로젝트필수)을 그대로 통과해야 한다. 템플릿 저장 시에도 계정코드는 마스터 대조를 거친다.

등재된 템플릿: 0건(구조만 완성). 실제 케이스는 A5 회계 규칙 확보 후 등록한다 — 승인 없는 계정 조합을 임의로 만들어 두지 않는다.

5. 지금 상태에서 반드시 알아야 할 것 4가지 (+ 해소된 결함 1건)

⚠ 5.1 프로젝트 필수 검증이 무력하다

계정과목 691행 전량 project_fg가 NULL이다. 서버 재검증 7종 중 5번(프로젝트 필수 계정 강제)이 어떤 계정에도 걸리지 않는다. ERP 원천이 비어 있는지, 프로젝트 필수 여부를 다른 컬럼·다른 체계로 관리하는지 확인이 필요하다(A5·유니포인트 대상). 테스트에서 이 항목이 통과해도 정상 판정으로 오해하지 말 것.

⚠ 5.2 마감월 통제가 비어 있다

gl_period_lock 등재 0건 → 어떤 결의일자도 막히지 않는다. 구조는 완비돼 있고 A5에서 기준을 정해 등재하면 즉시 동작한다.

⚠ 5.3 회기입을 "잊는 것"은 막지 못한다

ERP에 등록해 놓고 포털에 전표번호를 적지 않으면 초안은 submitted로 남는다. 화면이 경고 표시는 하지만 근본 해소는 운영 규칙(S6에서 정할 사항).

⚠ 5.4 남아 있는 테스트 데이터

DRAFT-20260803-0001(적요 "123", 1원, 전표번호 "1")이 posted 상태로 남아 있다. 형식 검증 신설 이전에 만들어진 건이라 현재 규칙(TG+12자리)에 맞지 않는다.

✅ 5.5 (해소됨) ERP char 패딩이 관리항목·거래처 표시를 무력화했던 결함 — 2026-08-18 저녁 해소

gl_slip 미러 실적재 직후(2026-08-18 오후) §3.2에서는 "ERP ctrl_cd·dr_cr_fg의 char 패딩(트레일링 스페이스)은 화면·RPC가 흡수하므로 조치 불필요한 특성"이라고 오판했다. 같은 날 저녁 실제로 화면에서 관리항목·거래처가 표시되지 않는 문제로 드러났다 — 원인은 세 곳이었다: ①acct_ctrl_assn_s 1,002행 중 978행의 계정코드 패딩으로 계정별 관리항목 매칭이 전부 miss(관리항목 필드가 아예 생성되지 않고, 서버 필수검증도 무력화됨) ②전표 라인 bp_cd 1,773행 패딩으로 거래처마스터 조인이 실패해 거래처명이 안 보임 ③gl_input_type 패딩으로 입력경로 필터가 오작동. 조치 3중으로 해소했다: ①마이그레이션 gl_pad_trim_v1 — 미러 5테이블(acct_ctrl_assn_s·ctrl_item_s·gl_slip_s/gl_slip_item_s/gl_slip_ctrl_s)을 일회성 trim(사전 중복검증 0건) + gl_ctrl_master_get·gl_slip_list·gl_slip_get RPC를 btrim 적용해 재정의 ②ETL 추출 SQL에 RTRIM 적용(5개 job: gl_slip·gl_slip_item·gl_slip_ctrl·ctrl_item·acct_ctrl_assn, 향후 적재분도 패딩 없이 들어오도록 근본 조치) ③화면·Edge Function에도 trim 방어 추가. 검증: 거래처 조인 11,734/11,734 전량 성공, 계정×관리항목 요건 조인 42,466건 정상. 교훈: char 타입 원천 컬럼을 미러링할 때는 trim을 기본값으로 적용할 것 — "소비 측 코드가 흡수하니 괜찮다"는 판단은 소비 측 전체 경로를 실제로 확인하지 않으면 위험하다(이번에도 일부 경로만 trim 처리돼 있었다). posted는 화면에서 폐기할 수 없으므로 정리하려면 DB에서 직접 삭제해야 한다(감사 로그는 보존 권장).

7. 확대 시 반드시 짚을 갈림길 — E3

단계 내용 선결 조건
E1 케이스 확대(법인카드·세금계산서 매입) 파일럿 성공 + 회계 규칙. 부가세 로직 필요
E2 대상자 확대(부서→전사) S6 통과. 회계 담당자 부하가 병목
E3 ERP 자동 등록(쓰기 API) 유니포인트 협의 + 경영 승인. 운영(JEILMNS)에서는 여전히 절대규칙상 불가(C-1 유지) — 2026-08-19 결정 C-11로 데모 DB(JEILMNS_DEMO2) 한정 1차 실증 트랙이 개시됐다(신규 문서 11_ERP직접등록_DEMO2_1차.md). 이 1차 실증의 결과가 향후 E3(운영 전환) 재심의의 입력이 되며, 운영 전환 자체는 별도 기회검토의 착수 게이트 G-1~G-8 통과가 선행돼야 한다
E4 그룹웨어 전자결재 연동 E3(운영 전환) + 그룹웨어 API
E5 내 전표의 ERP 승인 상태 조회 A_TEMP_GL 조회 개방 승인

현재 구조는 "포털 입력 + 회계 담당자가 ERP 재입력"이라 회계팀 일이 오히려 늘어난다. 파일럿(1~2명)은 감당되지만 부서·전사로 넓히면 회계 담당자가 병목이 된다. 실무 확대를 원한다면 E3 협의를 언제 의제에 올릴지가 실질적인 의사결정 지점이다 — 그 첫 단추가 데모 DB 1차 실증(C-11, 11 문서)이다.
