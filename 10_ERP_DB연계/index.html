현재 위치(2026-09-22): 발주통합 LIST — REQ-0070 판정 완료 + RLS InitPlan·행추정·lateral 성능 수정(62.9초→459ms) + 전량 즉시수신 전환 — 관리자가 pur_order --full 백필(4,618행)을 직접 실행해 신규 11컬럼을 판정했다: 담당자=등록자(insrt_user_id)·외주=품번 ROS 접두(799건)·입고처는 개념이 달라 「입고창고」로 개명(sl_cd)·결재번호는 ref_no 전건 공백으로 여전히 미확인. 이 판정본(뷰 v2)을 배포한 직후 라이브가 statement timeout(사내계정 62.9초)으로 죽어 조사한 결과 원인은 뷰가 아니라 erp_ro의 RLS였다 — ①정책의 auth.jwt()/is_internal() 직접호출을 (select …)로 감싸 InitPlan화 ②pur_order_s 행추정 23행(실제 4,619행) 붕괴를 비교식을 서브쿼리 안으로 넣어 보정 ③계약내역 lateral 조인의 미인덱스 전수스캔을 distinct on으로 해시 조인화 — 3중 수정으로 459ms까지 단축(최초 적용은 발주통합 LIST가 쓰는 9종이었으나, 같은 날 관리자 지시로 잔여 8종bp_master_s·dept_master_s·inventory_d·item_group_s·purchase_m·sales_orders_m·table_dict·usr_erp_module_s도 마저 적용해 erp_ro 17/17 전부 InitPlan 모양 통일, REQ-0040 done — 성능개선이 아닌 예방 목적, table_dict는 GRANT 자체가 없어 기존 사양 그대로). 값 10지표는 적용 전후 동일, ERP 공개 뷰 25종 전수 회귀 오류 0. 후속으로 「1차 1,000행+전량 받기」 2단계 분할수신을 없애고 조건 전량을 즉시 받도록 화면을 바꿨다(라이브 실측 1차 0.31초/전량 5,609행 2.17초, 종전 17초). 직전 "ERP 권한(Role) 조직별 현황" 구축(REQ-0057) + 전사 열람·표시 개방 + 장부화면 접근분리(REQ-0065) — 신규 운영페이지 /work/erp-roles(조직도+구성원/Role 매트릭스+권한정리, 2026-09-18 구축)로 조직 35부서·활성계정 98명(외부 인력 포함)의 ERP 역할·메뉴 권한을 조회하고, 팀장·부서장이 불필요 권한을 직접 표시하는 「권한정리」 창구(role_cleanup)를 신설했다. 이후 며칠간 관리자 직접 지시로 부서 단위 「권한확인 완료」·메뉴명 정비(mv_menu_name)·사용 안내 문서·조회바 표준화가 이어졌고, 2026-09-21에는 게이트 자체를 세 차례 손봤다(전사 열람 개방 → 권한정리 표시·저장 전사 개방 → 장부 화면만 관리자로 재분리). 이 위에는 계정 통합관리·대사(REQ-0018)가 ERP 계정을 정본으로 확정해 가동 중이고, 연동 러너 단일 통합(jeil_runner r1.4, 서버 실행 파일 1개로 축소)이 데이터 업데이트·퇴사 처리·결의전표 전송을 한 프로그램으로 묶었다. 그 아래 단계(결의전표 파일럿·"ERP 직접등록 DEMO2" 누적 5건 투입 성공·반복전표 자동화·관리항목 참조 마스터 전면 연결(ctrl_ref 27종)·연동 현황 뷰 22종 확장 등)는 그대로 유지된다. 상세는 02 진행상태 §1(전체 흐름)·00 현재상태 스냅샷 §4(연계 현황 표) 참조 · 결정 대기: 발주통합 LIST 결재번호(PU…) 원천 조사(관리자 ERP 읽기전용, ref_no 후보 소진으로 채번 이력 직접 추적만 남음), REQ-0068·0069 본 문서 소급 등재 여부, 유니포인트 협의(P1, 읽기전용 계정·뷰 스펙), 자금(F 모듈) 경영 승인, 정본 SQL 50·51의 라이브 정합 승격 여부(REQ-0065 조사 중 발견), 그룹웨어 겸직 정보 확장 방법(벤더 뷰 확장 vs 스크레이프), ENTRA_CLIENT_SECRET 조기 회전 여부(정기 만료 2026-12-09)
