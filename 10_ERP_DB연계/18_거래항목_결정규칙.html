18. 거래항목(JNL_CD) 결정 규칙 — 결정 C-15

AX 릴레이가 ERP에 넣는 거래항목·이벤트코드를 무엇으로 정하는가. 결정 2026-08-25 · 관리: 최동혁 · 전담 에이전트 erp-db-link-manager 선행: 16_AX전표_거래유형체계_적정성검토(ERP_DB 발신) · 12_AX001_계정매핑_등재요청(성격 전환)

0. 결론

계정 성격(A_ACCT.SUBSYS_TYPE) 하나로 결정한다. 예외·특례 없다. ERP 마스터를 건드리지 않고, 회계팀 등재를 기다리지 않는다.

이 결정으로 차단돼 있던 계정 6종이 전부 해소됐다.

1. 왜 규칙으로 정해도 되는가 — 실측 근거

1.1 JNL_CD·EVENT_CD 는 전표에 남지 않는다

테이블 JNL_CD EVENT_CD
A_BATCH_GL_ITEM (투입 배치) 있음 있음
A_TEMP_GL_ITEM (결의전표 라인) 없음 없음
A_GL_ITEM (정식전표 라인) 없음 없음
A_TEMP_GL_DTL (관리항목) 없음 없음

투입 배치에만 있고 전표로 넘어가지 않는다. 회계 결과에 영향이 없다.

1.2 제약도 최소다

항목 제약
JNL_CD A_JNL_ITEM FK 하나뿐 — 마스터에 있는 코드면 통과
EVENT_CD 제약 없음 — FK도 없다

1.3 AX001 매핑 0건은 의도된 상태다

A_JNL_ACCT_ASSN·A_JNL_FORM 모두 0건이지만 설계가 그렇다 — 포털이 계정을 완결해 보내므로(MAKE_ACCT_FG='Y') 매핑 경로를 타지 않는다(16번 §6①).

따라서 「회계팀이 매핑을 등재해야 풀린다」는 전제가 틀렸다. 12번 문서는 이 전제 위에 작성됐고, 성격을 「등재 요청」에서 「코드 규칙 확정」으로 바꾼다.

2. 결정 규칙

계정의 SUBSYS_TYPE 만 보고 정한다.

계정 성격 의미 JNL_CD EVENT_CD
TP 매입부가세 A A
TR 매출부가세 A A
AP 채무 AP (공란)
AR 채권 AR (공란)
PP 선급금 PP (공란)
PR 선수금 PR (공란)
OC · OD 미결 GLITEM (공란)
(없음) 비용·수익 등 서브원장 무관 ADJMNT IZ / DZ

EVENT_CD 가 값을 갖는 자리는 둘뿐이다.

  • 부가세 → A(기존 채널과 동일)
  • 서브원장 무관 계정 → 코스트센터 직간접(DI_FG I→IZ · D→DZ)

나머지는 공란이다. 어차피 전표에 남지 않고 제약도 없으므로 의미 없는 값을 만들지 않는다.

2.1 우선순위 — 매핑이 등재되면 그쪽이 이긴다

① A_JNL_ACCT_ASSN 매핑 조회      ← 등재돼 있으면 ERP 정의가 정답
② 계정 성격 단일 규칙(위 표)      ← 현재는 항상 여기로 온다(AX001 매핑 0건)
   → 표의 코드가 마스터에 없으면 중단(fail-closed). 임의 대체하지 않는다

①을 남겨 둔 이유 — 나중에 회계팀이 AX001 매핑을 등재하면 코드 변경 없이 자동 전환된다. ERP 정의가 생기면 그것이 우선이라는 원칙은 유지한다.

3. 무엇이 달라졌나

3.1 종전 — 3단계 혼합

단계 방법 문제
① 매핑 A_JNL_ACCT_ASSN AX001은 0건이라 항상 미스
② 자기참조 계정코드와 같은 JNL_CD A_JNL_ITEM에 77건만 등재(비용계정 473건) — 등재된 계정만 우연히 통과
③ 코드형 폴백 계정별 하드코딩 표 7종 표에 없으면 차단

세 방식이 섞여 있었다. 같은 전표 안에서 자기참조(43000501)와 코드형(A·AP)이 함께 나갔고, 어느 것도 검증받지 않았다 — 16번 §6③이 「통제 없는 자유 입력 필드」로 지적한 상태다.

3.2 지금 — 성격 단일 규칙

계정 성격 하나로 결정된다. 설명이 한 줄로 끝난다.

"AX는 계정의 서브시스템 구분에 따라 §2 표대로 거래항목을 넣는다."

4. 검증

4.1 막혀 있던 실전표

초안 금액 결과
DRAFT-20260824-0015 22,508,030 · 9라인 ✅ 통과 — 분개코드 9줄 전건 해석, 채무 3행·부가세 1행 생성
DRAFT-20260820-0012 10,000 🚫 여전히 차단 — 다만 사유가 달라졌다(아래)

4.2 ★ DRAFT-20260820-0012 는 계정 문제가 아니었다

분개코드는 이제 풀린다(21100902→GLITEM). 그런데 입력 가드가 잡았다.

[차단] 1번 줄 21100902 DR — 미지급금(개인)(OC) 미결 반제 — 미결반제 전용화면에서 처리해야 한다

21100902(미지급금-개인)를 차변에 넣었다 = 미결 반제다. 결의전표로 반제하면 미결원장 잔액이 정리되지 않으므로 전용화면에서 해야 한다.

전표 자체가 잘못돼 있었다. 종전에는 「계정 미등재」로 기록됐지만 실제로는 다른 문제였고, ERP도 119712로 막았을 건이다. 가드가 먼저 잡아 정확한 사유를 남긴 사례다. 12번 문서의 「막힌 전표 2건」 기록은 이 사실로 정정한다.

4.3 T2 개방 확인

설계서 T2(개인경비, 범위의 24.6%)가 발생 방향으로는 통과한다.

차) 53014307 판)지급수수료  → ADJMNT/IZ (성격:일반)
대) 21100902 미지급금(개인) → GLITEM/-  (성격:OC)
가드: ✅ 통과

OC 계정은 SUBSYS_NO 가 비어야 정상이고 승인 후 A_OPEN_ACCT 에 생성된다(설계서 §4).

5. 회계팀에 남는 것 — 등재 요청은 사라졌다

# 항목 성격
1 AX001 은 분개형태·계정배정이 없는 것이 정상 인수인계 문구. 거래유형등록 화면에서 「설정 안 된 거래유형」으로 보인다(16번 §6①)
2 MAKE_ACCT_FG='Y' 전제 포털이 계정을 완결해 보낸다. 'N' 이면 매핑 0건이라 110423 실패(16번 §6②)
3 21100902 대변 사용 적정성 배치 이력은 차변(반제)뿐이다. 대변(발생)에 써도 되는지는 회계 판단 — 거래항목과 무관하게 남는 질문

1·2는 문서로, 3은 확인 요청이다. ERP 마스터 변경 요청은 없다.

7. 이 결정이 흔들리는 경우

조건 대응
회계팀이 AX001 매핑을 등재 자동 전환 — ①단계가 이긴다. 코드 변경 불필요
ERP 업그레이드로 JNL_CD 가 전표에 남게 됨 재검토 필수. 이 결정의 전제가 무너진다
표의 코드가 마스터에서 삭제됨 fail-closed 로 중단된다 — 조용히 다른 코드를 쓰지 않는다
새 서브시스템 유형 등장 JNL_DEFAULT(ADJMNT)로 처리된다. 부적절하면 표에 행을 추가한다
