Q. 거래항목·거래유형은 타모듈 자동분개용으로 보이는데, 결의전표 수기입력을 재현하려는 AX 가 이걸 쓰는 게 맞는가?
A. 관찰이 정확하다. 무관한 기준정보가 맞다. 그럼에도 AX 가 쓰는 것은 구조적으로 불가피하고, 결과적으로 문제가 없다.

질문답
거래유형·거래항목이 수기입력과 무관한가맞다. 수기 12,085건 전부 TRANS_TYPE 공란
AX 는 왜 거래유형을 만들었나화면이 아니라 엔진(SP) 을 쓰기 때문. A_BATCH 경유 SP 는 거래유형이 없으면 120110 오류로 실패한다 — 선택의 여지가 없었다
타모듈 연동 형태로 적용된 것인가맞다. 다만 그것이 결과를 다르게 만들지는 않는다
이대로 가도 되는가된다. 최종 산출물이 수기와 동일함을 실측 확인. 단 관리사항 3건

업무 목적은 수기입력 재현이 맞다. 다만 그것을 구현하는 수단이 엔진일 뿐이고, 수단이 요구하는 형식(거래유형)을 갖췄다고 해서 결과가 타모듈 전표가 되지는 않는다.

ERP 안에는 전표를 만드는 방식이 둘이다

거래항목등록 화면 설명문이 이를 그대로 말한다 — "업무별로 발생할 수 있는 거래유형에 대하여 분개 시 차/대변에 발생되는 계정코드를 결정하기 위한 항목을 사전에 설정하는 화면"

🔑 거래항목(JNL_CD)은 전표에 남지 않는다

이것이 이해의 열쇠다.

테이블JNL_CD 컬럼의미
A_BATCH_GL_ITEM (투입)있음엔진에 넘기는 입력 파라미터
A_TEMP_GL_ITEM (결의전표)없음—
A_GL_ITEM (회계전표)없음—
거래항목은 전표를 만드는 순간에만 쓰이고 전표에는 흔적이 남지 않는다. 완성된 결의전표만 놓고 보면 수기 전표와 거래항목 측면에서 구별 자체가 불가능하다. "거래항목등록 메뉴가 결의전표입력과 관계없어 보인다"는 관찰이 정확한 이유다.

AX 는 화면이 아니라 엔진을 쓴다

화면 로직을 재현할 수 없으므로 SP 를 호출한다. 그 순간 제약이 생긴다.

수기입력   화면 ──────────────────────────→ A_TEMP_GL 직접 INSERT
                                              (거래유형 불필요)

                            (거래유형 필수)

엔진이 거래유형을 요구하는 지점

USP_A_MAKE_VAT_ACCT_01 첫머리다.

SELECT @CTRANS_TYPE = MIN(TRANS_TYPE) FROM A_BATCH_GL_ITEM WHERE BATCH_NO = @BATCH_NO
IF @@ERROR <> 0 OR @@ROWCOUNT < 1 BEGIN SET @MSG_CD = '120110' GOTO ERROR_RETURN END

SELECT @CTRANS_TYPE = A.TRANS_TYPE, @TRANS_REVERSE_FG = A.REVERSE_FG
FROM   A_ACCT_TRANS_TYPE A WHERE A.TRANS_TYPE = @CTRANS_TYPE
IF @@ERROR <> 0 OR @@ROWCOUNT < 1 BEGIN SET @MSG_CD = REF00 + '120110' … GOTO ERROR_RETURN END
120110 = "거래유형 데이터가 존재하지 않아 저장에 실패했습니다."

이어 usp_a_create_gl_01 이 거래유형에서 결의/회계 분기(GL_POSTING_FG)·계정합·생성순서를 읽는다. 거래유형이 없으면 결의전표로 떨어뜨릴지 회계전표로 떨어뜨릴지조차 정할 수 없다.

NULL 을 넣어도 FK 는 통과하지만 엔진이 120110 으로 막는다. usp_a_create_gl_direct 등 A_BATCH 경유 SP 는 전부 같은 구조다.
결론 — AX 가 A_BATCH 경유 엔진을 쓰기로 한 순간 거래유형은 구조적 필수였다. 임의 선택이 아니라 제약이었다.

TRANS_TYPE 은 전표를 만들 때만 쓰이고, 만들어진 뒤에는 아무도 보지 않는다. 조회 화면·리포트·시산표·재무제표 어디에도 영향이 없다.
오히려 자산이다 — TRANS_TYPE='AX001' 덕분에 AX 채널로 들어온 전표를 한 줄로 골라낼 수 있다. 수기 전표는 공란이라 구분이 안 된다. 감사·통계·사후 추적 관점에서 이건 손실이 아니라 이득이다.

근거 3 — 운영 선례가 이미 같은 구조다

AG001(멀티반제)는 A_BATCH 경유 + 거래유형 + 결의전표로 1,698건이 운영 중이다. 전표번호는 TG…, 채널 식별은 REF_NO(UX…). AX 가 하려는 것과 구조가 같다.

이대로 가되, 인지하고 관리할 것 3건

① AX001 은 자동분개 매핑이 비어 있다

계층AX001AG001AN005
분개형태 A_JNL_FORM01890
계정배정 A_JNL_ACCT_ASSN01476
통제배정 A_JNL_CTRL_ASSN025158

의도된 상태다. AX 는 포털이 계정을 완결해 보내므로(MAKE_ACCT_FG='Y') 매핑을 타지 않는다.

다만 회계팀이 거래유형등록 화면에서 AX001 을 보면 "설정이 안 된 거래유형" 으로 보인다. 운영 인수인계 문서에 "AX001 은 외부가 계정을 직접 지정하므로 분개형태·계정배정이 없는 것이 정상" 을 명시해야 한다.

② MAKE_ACCT_FG='Y' 에 의존한다

포털이 MAKE_ACCT_FG='N'(엔진이 계정 결정)으로 보내면 매핑 0건이라 REF01 110423 으로 실패한다. 릴레이는 항상 'Y' 로 고정해야 하며, 이 전제가 문서화돼 있어야 한다.

③ 거래항목(JNL_CD)은 무검증 통과 파라미터다

전표에 남지 않고 매핑도 없으므로 어떤 값을 넣어도 통과한다(A_JNL_ITEM FK만 만족하면 됨). 실제로 AX 테스트 전표는 AN005식(계정코드 자기참조 43000501, EVENT_CD='IZ')과 S0003식(A·AP)을 섞어 넣었는데 아무 경고 없이 통과했다.

릴레이가 넣는 JNL_CD 규칙을 한 가지로 고정하고 문서화해야 한다. ITGC 관점에서 "통제 없는 자유 입력 필드"로 지적될 수 있다.
