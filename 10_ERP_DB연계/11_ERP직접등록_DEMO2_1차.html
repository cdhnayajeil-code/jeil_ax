11. 결의전표 ERP 직접등록 — 1차(DEMO2) 기획·구축

작성: 2026-08-19(v1.0 → v1.1 오후 → v1.2 저녁 → v1.3 · 2026-08-20 전송 E2E 성공) · 관리: 최동혁 · 전담 에이전트: erp-db-link-manager 결정 C-11(2026-08-19 관리자 지시): AI(포털) 생성 결의전표의 ERP 직접 투입을 데모 DB JEILMNS_DEMO2 한정으로 1차 테스트한다. 운영(JEILMNS) 쓰기는 여전히 금지(C-1 유지) — 운영 전환은 기회검토의 착수 게이트 G-1~G-8 통과 + 재심의가 선행돼야 한다. 근거·선행: 사내 OneDrive ERP_DB/회계/260819_AX_결의전표_ERP연동_기회검토/(기회검토 본문 + test_demo2 리허설 킷 — 투입 레시피 리허설 검증 완료)

1. 한 장 요약

상태 — 1차 투입 성공(2026-08-19 오후, 관리자 직접 실행): 대상 초안 DRAFT-20260819-0005(총무팀, 275,000원, 쿠콘 7월분 스크래핑 수수료 — 부가세 포함 3라인)을 --dry-run(리허설) → 확정 순으로 적용해 DEMO2에 AG202608190006(BATCH BT202608190007) 전표가 정상 생성됐다. 분개코드 자동 해석 성공(11103301→A/A · 53014307→SPC20 · 21100901→AP, A_JNL_ACCT_ASSN+A_JNL_FORM 2단 조회), 엔진 rc=1·오류 없음, 전표 생성 CONF_FG=U, 라인 대조 3/3 완전일치(대차 자동보정 미개입) 확인 후 COMMIT. 포털 회기입도 검증됐다 — gl_draft.erp_apply_status='applied'·AG번호·시각 자동 기록, 적용 원장 gl_erp_apply_log 2행(#1 dry-run/rolled_back, #2 commit/success), 적용 대상 목록에서 자동 제거돼 이중 적용 차단이 실제로 작동함을 확인했다. 특기(정상 특성, 조치 불필요): 채번 갱신(B_AUTO_NUMBERING)도 트랜잭션에 포함돼 리허설 롤백 시 번호가 반환되고, 같은 번호가 확정 실행에서 재사용됨(번호 낭비 없음). 잔여는 2차 이상 케이스 확대·운영 전환 재심의(§6)뿐이다. 상세는 §7 변경이력.

무엇 — 포털에서 작성·제출한 결의전표 초안을, 사람이 ERP에 재입력하는 대신 적용기(관리자 PC 배치)가 DEMO2에 직접 투입해 ERP 표준 엔진으로 전표(TG류)를 생성한다. ERP 계정=MS 계정 1:1(C-3)이므로 전표 등록자는 포털 제출자의 ERP 계정 그대로다.

전표번호(핵심 요구) — AI가 만드는 전표는 전용 접두어 AG 대역으로 채번한다. ERP 표준 채번기(usp_a_tempgl_no_auto_gen 'AG' — B_AUTO_NUMBERING 기존 미사용 유형 재활용)를 쓰므로 중복이 원천 차단되고, TG(수기·기존 자동화) 대역과 완전히 분리되어 ①AI 전표만 골라 조회·회수 가능 ②사고 시 식별 즉시 ③운영 채번과 충돌 0. 포털 측에는 적용 원장(gl_erp_apply_log)이 모든 시도(리허설 포함)와 발급 번호를 기록·관리한다(성공 커밋의 초안·번호 유니크 제약).

흐름(1차)

   ④AG·BT 채번 ⑤A_BATCH/A_BATCH_GL/A_BATCH_GL_ITEM 투입(관리항목 슬롯 평탄화)

3.1 멱등·중복 방지 3중 (요구: "전표번호 관리·중복 방지")

층 장치
ERP 투입 전 A_BATCH·A_TEMP_GL 에서 REF_NO(=draft_no) 선조회 — 존재 시 중단(REF_NO 는 DB 유니크 아님 — 실사 확인) + AG 채번 후 존재 재확인
포털 원장 gl_erp_apply_log 성공 커밋에 (대상DB, 초안번호)·(대상DB, AG번호) 유니크 인덱스 — 이중 적용을 DB가 거부

3.2 분개코드 결정(실사 확정 구조)

A_JNL_ACCT_ASSN(거래유형·계정·차대 → JNL_CD) → A_JNL_FORM(거래유형·JNL_CD → EVENT_CD) 2단 조회. 조회 실패 시 실증 폴백 표(부가세대급금 A/A · 미지급금(거래처) AP · 미지급금(법인카드) AP2/CARDC), 그래도 없으면 중단(fail-closed — 임의 분개 금지, "분개는 AX가 완성하되 코드는 ERP 설정이 정답").

3.3 검증(엔진 호출 후, COMMIT 전)

① A_TEMP_GL 전표 생성 확인 ② 투입 라인 ↔ 생성 라인 완전대조(계정+차대+금액 다중집합 — 엔진이 라인을 재정렬하므로 순번 매칭 금지, 리허설 정정 3) ③ 불일치 시 대차 자동보정 개입으로 판정·ROLLBACK. 관리항목 슬롯 순서는 엔진이 재배치(정정 2 — 코드만 정확히).

4. 실행 절차

4.1 화면 [🚀 ERP 전송] 방식 (v1.2 신설 — 실사용 테스트 경로)

회계 담당자가 화면에서 버튼을 눌러 전송하고, 사내 중계가 자동 투입한다. 포털은 여전히 ERP에 직접 쓰지 않는다 — 버튼은 erp_apply_status='ready' 마킹만 하고, 투입은 중계가 수행(기회검토 채택 구조: 사내 pull).

① 관리자 PC에서 중계를 켠다(감시 모드 — 15초 간격, Ctrl+C 종료)
   ! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --watch
② 회계 담당자: 결의전표 입력 화면 → 「회계 담당자」 탭 → 제출된 초안 선택
   → [🚀 ERP 전송 (DEMO2)] 클릭 → 확인
③ 중계가 자동 처리(멱등 확인 → 분개코드 조회 → AG·BT 채번 → A_BATCH 투입
   → 표준 엔진 → 라인 완전대조 → 대조 통과 시 COMMIT)
④ 화면이 4.5초 간격 폴링으로 결과를 자동 감지 → 「ERP 적용」 열에 AG전표번호 표시
   (실패 시 '적용 실패' + 사유. 대기 중 취소는 [전송 취소])

상태머신: null → ready(버튼) → applied(성공, AG번호 회기입) 또는 failed(실패, 사유 기록). 중계를 상시 켜두지 않을 때는 버튼으로 대기만 걸고, 나중에 --queue(대기 건 일괄 처리, 1회 상한 5건)로 처리해도 된다.

4.2 CLI 단건 방식 (리허설·정밀 검증용)

! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --list                      # 적용 대상 확인
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-... --dry-run  # 리허설(ROLLBACK)
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-...            # 확정(COMMIT+회기입)
! python "10_ERP_DB연계/etl/gl_apply_demo2.py" --draft DRAFT-... --cleanup  # 정리(삭제·상태 해제)

새 케이스(처음 쓰는 계정 조합)는 먼저 --dry-run으로 검증한 뒤 화면 전송을 쓰는 것을 권장한다. 화면 전송 경로는 리허설 없이 바로 확정 투입되지만, 라인 대조 불일치 시 자동 ROLLBACK되므로 안전 경계는 동일하다.

5. 미결·주의 (실사 2026-08-19)

# 항목 내용
U-A 조직정보 승계 소스 최근 배치의 INTERNAL_CD='11' vs B_ACCT_DEPT 최신 '181' 불일치. 적용기는 AX 테스트 잔재(REF_NO 'AX%'·'DRAFT-%')를 승계 소스에서 제외하고 최근 정상 배치를 따름 — 의미 확정은 유니포인트 협의
U-B S0003 허용 계정 범위 — 경비정산 커버리지 부족(2026-08-20 실증) S0003 매핑 38행은 무역·수입 수수료·운반비·세금과공과 중심이라 일반 경비(복리후생비·여비교통비 등)를 담지 못한다. 실측: 43000501(제)복리후생비(식대))·53010701(판)복리후생비(식대))는 AN005(법인카드연계)에만 매핑, 그 AN005는 대변이 21100907(미지급금-법인카드) 고정이라 대변 가변인 경비정산에 쓸 수 없다 → 실제 급식대 전표가 fail-closed 로 거부됨(DRAFT-20260819-0006). 결론: 기회검토 §4대로 경비정산용 신규 거래유형(TRANS_TYPE) 신설이 필요하다(유니포인트 협의 대상, 마스터 등록=자료직접변경요청서 표준절차). 그 전까지 1차 테스트 범위는 S0003 허용 계정 케이스로 한정한다
U-C DEMO2 잔재 AXTEST-* 3건(그중 1건은 <<SLIP_NO>> 미치환 이상행) — --cleanup 또는 수동 정리 권장
U-D DEMO2 = 2025-06-25 스냅샷 이후 신설 계정 14건 부재 — 해당 계정 초안은 DEMO2 투입 실패 가능(정상)
U-E 부가세 헤더 VAT 는 부가세대급금(11103301) 라인 합으로 산출. 포털 화면은 아직 세액 필드 미전송 — 케이스 확대 시 보강

6. 운영(JEILMNS) 전환 조건 — 이 문서 범위 밖

기회검토 결론 그대로: 착수 게이트 G-1~G-8(벤더 서면 확인·경영 승인·전용 서비스계정·스케줄러/실행호스트·법인카드 재가동 안정화·A5 등) + DML 감사 리포트 Type D 신설 + 준자동(사람이 ERP에서 트리거) 권고. 1차(DEMO2) 실증 결과는 그 재심의의 입력이다.
