0. 결론 — 좋은 소식과 남은 구멍

좋은 소식

서브원장 개선(USP_A_CREATE_TEMP_GL_SUBSYS 호출 추가)이 입력검증까지 자동으로 켰다.

그 SP 안에 이런 호출이 들어 있다.

/* 보조부생성 가능 계정인지 CHECK한다. */
EXEC @rtn_value = dbo.usp_a_check_acct @GL_NO, 'T', @MSG_CD OUTPUT
IF (ISNULL(@rtn_value,0) <> 1) GOTO ERROR_RETURN

usp_a_check_acct 가 화면이 하던 계정 검증을 그대로 수행한다. 릴레이가 SP 를 부르는 순간 스크린샷의 119712 오류도 AX 경로에서 똑같이 발생하고, 같은 트랜잭션이므로 전표 생성까지 롤백된다.

시점 검증 상태
개선 전 (SP 미호출) ❌ 전면 우회 — 반제 방향이든 뭐든 무제한 통과
개선 후 (SP 호출) ✅ 자동 적용 — AP/AR/PP/PR/SS/OC 반제방향 차단

남은 구멍 — AX 측에서 막아야 할 것

ERP 자체가 검증하지 않는 항목이 있다. 여기는 릴레이가 직접 방어해야 한다.

# 항목 ERP 검증 실측
G1 부가세(TP/TR) 반제방향 ❌ 없음 수동입력분에 위반 8라인 실재
G2 차대 균형 (결의전표) ❌ 없음 113119 은 GL_INPUT_TYPE='GL' 한정
G3 폐쇄계정 사용 △ 엔진 단계 생성 시 110104
G4 마감기간 ✅ 있음 121291

1. 스크린샷 오류의 정체

[119712] [11100901 : CR] 계정은 본 화면에서 반제할 수 없습니다.
          [채권] 반제처리화면에서 반제 처리하십시오.
항목 값
메시지 원문 %1 계정은 본 화면에서 반제할 수 없습니다. %2 반제처리화면에서 반제처리하십시오.
발생 SP usp_a_check_acct (B_MESSAGE 조회 + 소스 확인)
계정 11100901 외상매출금 · BAL_FG='DR' · SUBSYS_TYPE='AR'
입력 CR (대변) — 계정 기본차대의 반대
의미 AR 계정을 대변에 넣는 것 = 채권 반제. 결의전표 화면에서 하면 안 되고 채권반제 전용화면에서 해야 한다

왜 막는가

반제를 결의전표로 처리하면 채권원장(A_OPEN_AR)의 잔액이 정리되지 않는다. 전표상 채권은 줄었는데 원장에는 그대로 남아 미수채권이 실제보다 부풀려진다. 전용 반제화면은 원장의 특정 채권 건을 지정해 잔액을 차감한다.

3. 반제방향 차단 규칙표

usp_a_check_acct 는 라인마다 아래를 확인한다.

SELECT @OBJECT_ID FROM A_OBJECT
 WHERE GL_INPUT_TYPE = @GL_INPUT_TYPE       -- 'TG'
   AND SUBSYS_TYPE   = @SUBSYS_TYPE         -- 계정의 서브시스템
   AND (DR_CR_FG = 'DC' OR DR_CR_FG = @DR_CR_FG)
IF @@ROWCOUNT = 0 → 119712 오류

GL_INPUT_TYPE='TG' 의 A_OBJECT 정의가 곧 규칙표다.

4. 🔴 검증 공백 G1 — 부가세 반제방향

usp_a_check_acct 소스에 TP/TR 전용 검증 블록이 없다. 있는 것은 입력경로를 '*' 로 바꾸는 처리뿐이고, 그것도 TG/GL 이 아닐 때만 동작한다.

-- 부가세는 공통입력경로를 쓴다.
IF (@SUBSYS_TYPE = 'TP' OR @SUBSYS_TYPE ='TR')
   AND (@GL_INPUT_TYPE <> 'TG' AND @GL_INPUT_TYPE <> 'GL')
   SET @GL_INPUT_TYPE = '*'
-- ↑ 이후 TP/TR 에 대한 A_OBJECT 매칭 검증이 없다

실측 — 위반이 실제로 존재한다

GL_INPUT_TYPE='TG' 전체를 규칙에 걸어 스캔했다.

생성경로 위반유형 위반라인 위반전표
수동입력 서브원장 반제방향 8 7
계정 서브시스템 기본차대 입력차대 위반라인
11103301 부가세대급금 TP DR CR 7
21102301 부가세예수금 TR CR DR 1

AP·AR·PP·PR·SS·OC 위반은 0건이다 — 검증이 실효적으로 작동하고 있다는 뜻이다. 부가세만 뚫린다.

금액대와 일자로 보아 부가세 신고 후 대급금·예수금 상계 전표다. 업무상 필요한 처리로 보인다. 다만 A_VAT 는 A_OBJECT 매칭 실패로 생성되지 않는다 — 원장 없이 전표만 남는다.

AX 관점 — 이 케이스는 회계팀의 결산 처리다. AX 포털이 만들 전표는 아니다. 그러나 릴레이가 이 조합을 받으면 ERP 가 막아주지 않으므로 그대로 통과한다. AX 측에서 차단하는 것이 안전하다.

5. 검증 공백 G2 — 차대 균형

113119 (차대변금액 불일치) 검증은 조건이 이렇다.

AND GL_INPUT_TYPE IN ('GL')     -- ← TG 는 대상이 아니다

결의전표(TG)는 차대 균형이 SP 단계에서 검증되지 않는다. 엔진의 USP_A_RETURN_BALANCE_01 이 보정을 시도하나 실측상 개입 0건이다.

실측 확인

수동입력 12,085건 중 헤더 차대(DR_AMT ≠ CR_AMT)가 다른 전표 209건이 있으나, 원화합계(DR_LOC_AMT/CR_LOC_AMT)는 209건 전부 일치한다 — 외화전표이며 위반이 아니다.

AX 관점 — 실질 위반은 없지만 ERP 가 막아주지 않는 구간이다. 릴레이는 투입 전 원화 기준 차대 균형을 자체 검산해야 한다.

7.2 AX 측에서 추가로 막아야 할 것

# 가드 규칙 사유
G1 부가세 반제방향 차단 TP 계정은 DR 만, TR 계정은 CR 만 허용 ERP 미검증 · 실측 위반 8라인 존재
G2 차대 균형 검산 원화 기준 차변합 = 대변합 ERP 가 TG 는 검증 안 함
G3 폐쇄계정 사전 차단 A_ACCT.DEL_FG='Y' 계정 거부 엔진이 막지만 사전 차단이 메시지가 명확
G4 마감기간 사전 차단 B_CALENDAR.TEMP_GL_FG='C' 거부 〃
G5 반제방향 사전 차단 §3 규칙표대로 사전 거부 ERP 가 막지만 포털 단계에서 걸러야 사용자에게 의미 있는 안내 가능

G5 가 중요하다. ERP 가 막아주더라도 그 시점은 릴레이 실행 중이다. 사용자는 포털에서 이미 결재까지 올린 뒤 "적용 실패"만 보게 된다. 포털 입력 단계에서 막는 것이 사용자 경험상 맞다.

7.3 포털 사전검증 쿼리

릴레이 투입 전 또는 포털 저장 시 실행할 수 있다.

-- 반제방향 위반 검사 (G1 · G5 통합)
-- @lines = 포털이 만든 라인 (계정, 차대)
SELECT L.ACCT_CD, L.DR_CR_FG, A.SUBSYS_TYPE, A.BAL_FG,
       CASE
         WHEN A.SUBSYS_TYPE IN ('OC','OD') AND L.DR_CR_FG <> A.BAL_FG
              THEN '미결 반제 — 미결반제화면에서 처리'
         WHEN A.SUBSYS_TYPE IN ('TP','TR') AND L.DR_CR_FG <> A.BAL_FG
              THEN '부가세 반대차대 — AX 자체 차단'
         WHEN A.SUBSYS_TYPE NOT IN ('OC','OD','TP','TR')
              AND NOT EXISTS (SELECT 1 FROM A_OBJECT O
                               WHERE O.GL_INPUT_TYPE='TG'
                                 AND O.SUBSYS_TYPE = A.SUBSYS_TYPE
                                 AND (O.DR_CR_FG='DC' OR O.DR_CR_FG = L.DR_CR_FG))
              THEN '반제방향 입력 — 전용 반제화면에서 처리'
         ELSE NULL
       END AS 차단사유
FROM   @lines L
JOIN   A_ACCT A ON A.ACCT_CD = L.ACCT_CD
WHERE  ISNULL(A.SUBSYS_TYPE,'') <> '';
-- 차단사유가 NULL 이 아닌 행이 하나라도 있으면 투입 금지

간단한 형태로는 계정 화이트리스트 + 허용 차대를 포털에 심는 것으로도 충분하다.
