21. 퇴사 처리 일괄 적용 — 기획

작성일 2026-09-07 · v0.5(그룹웨어 자동화 실증 완료 — 3축 중 2축 자동화) · 관리: 최동혁 · 요청: 관리자 계정 통합관리 화면(/admin/accounts)에서 퇴사 처리를 한 번에 걸어 ERP·그룹웨어·MS 세 시스템에 일괄 적용하는 기능의 기획. 테스트 계정 test@jeilm.co.kr 로 3축 실측한 결과를 근거로 한다. 관련: 00_현재상태_스냅샷(v0.43) · 이관/sql/34·36·37 · 화면 app/admin-accounts.html

1. 한 줄 결론

ERP·그룹웨어 두 축은 자동화가 실증됐다(v0.5). 남은 것은 MS 한 축이다.

v0.1 에서 "3축 모두 쓰기 불가"라고 썼는데 틀렸다. 관리자 확인으로 ERP 퇴사 처리가 Power Automate 흐름 + SharePoint 목록으로 이미 운영 중임을 확인했다(§3.2). 포털은 목록에 등재만 하면 되고 ERP 쓰기는 그 흐름이 한다 — 포털이 ERP MSSQL 을 직접 건드리지 않으므로 CLAUDE.md §1.2 도 지켜진다. 원천을 안 보고 "불가"로 단정했던 것이 오류였다.

그룹웨어도 v0.5 에서 해결됐다 — DB 쓰기 권한은 여전히 없지만 관리자 화면을 Playwright 로 조작해 테스트 계정을 실제로 사용중지 처리했다(§5.4). 남은 것은 MS 한 축(Graph 403)뿐이다.

2. 무엇을 만들려는가

관리자가 대사 화면에서 퇴사자를 고르고 [퇴사 처리] 를 누르면, 세 시스템에 같은 처리가 일괄 적용된다.

축 퇴사 처리의 정의(현행 운영 실측)
ERP(UNIERP) 인사 퇴사 처리 + 계정 USE_YN='N' + usr_nm 에 (퇴사) 접미
그룹웨어(ONUL Ware) 직원관리에서 사용여부 → 사용중지(내부 useState 0→1) + 퇴사일 기입
MS(Entra) accountEnabled=false + 표시이름 앞에 [퇴사](또는 (퇴사)) 접두

세 축의 "퇴사 표현"이 서로 다르고 필드도 다르다. 공통 필드는 없고, 축마다 별도 조작이 필요하다.

3. 실측 — 3축 쓰기 가능 여부 (2026-09-07, test@jeilm.co.kr)

관리자가 세 시스템에 등록해 둔 테스트 계정으로 직접 확인했다.

축 계정 존재 읽기 쓰기 근거
ERP ✅ usr_nm='admin_test id', 사용, 역할 2건 ✅ ✅ 기존 자동화 경로 있음(§3.2) 포털 직접 쓰기는 여전히 금지(§1.2)이나, SharePoint 등재 → Power Automate 경로로 우회 가능
그룹웨어 ✅ 로그인ID test@jeilm.co.kr, 사용중, 총무팀 ✅ 뷰 SELECT ❌ 권한 없음 DB 사용자 onul_member — 뷰 UPDATE=0, DB INSERT=0, 권한은 CONNECT 뿐
MS(Entra) ✅ 테스트계정, 활성 ✅ User.Read.All ❌ 403 PATCH /users → Insufficient privileges to complete the operation.

⚠ 오판 주의 — Graph 에 값이 같은 무변경 PATCH 를 보내면 204 가 떨어진다. 이걸 보고 "쓰기 권한 있다"고 판단했다가 실제 값 변경에서 403 을 받았다(2026-09-07 실제 발생). 권한 확인은 반드시 값이 바뀌는 요청으로 한다.

3.2 ERP 퇴사처리 기존 자동화 — 실물 확인 (2026-09-07, Power Automate 조회)

관리자 소유 흐름 3종이 있고, 그중 ERP퇴사처리 자동화 쿼리(2025-05-21 생성, 상태 On)가 실제 처리기다.

SharePoint 목록 「ERP 퇴사처리 RPA」 항목 수정/등록 (1분 폴링, GetOnUpdatedItems)
   └ 사이트 https://jeilmns.sharepoint.com/sites/test  · 목록 GUID 505ea3f8-1568-47b9-a194-3cdd46b71f74
        ↓ 데이터 수집 → 각각에 적용
        ↓ 조건: 진행구분 == '-'   (미처리인 건만)
        ├ SQL 쿼리 실행(V2) — ExecutePassThroughNativeQuery_V2 (connector shared_sql)
        └ 진행구분·처리내용 업데이트 (SharePoint 되쓰기)

실행되는 SQL(2건):

-- 1. 사용자 정보 업데이트
UPDATE Z_USR_MAST_REC
   SET USR_NM = CASE WHEN USR_NM NOT LIKE '%(퇴사)%' THEN USR_NM + '(퇴사)' ELSE USR_NM END,
       USR_VALID_DT = '{퇴사일자}',
       UPDT_DT      = GETDATE(),
       USE_YN       = 'N'
 WHERE USR_ID = '{사용자 ID}';

-- 2. 역할 정보 삭제
DELETE FROM Z_USR_MAST_REC_USR_ROLE_ASSO
 WHERE USR_ID = '{사용자 ID}';

목록 컬럼: 사용자 ID(Title=이메일) · 사용자명(부서_이름) · 진행구분(-/완료) · 퇴사일자 · 처리내용(흐름이 되쓰는 결과) · 마지막출근 · 비고

나머지 두 흐름: ERP 퇴사처리 당일 알림 (매일 09:00)(Scheduled, 활성 · 최근 4일 연속 성공) · ERP 퇴사처리_RPA 마지막출근일 기준 업데이트_되풀이(Activity suspended — 중지 상태).

⚠ DELETE 는 되돌릴 수 없다. 역할 배정을 통째로 지우고 무엇이 있었는지 남기지 않는다. 오적용하면 복구는 ERP 에서 수동 재부여뿐이다. 대사 미러(erp_ro.usr_role_s)에 직전 스냅샷이 남아 있으므로, 포털이 등재하기 전에 역할 목록을 케이스에 기록해 두는 것을 설계에 넣는다.

3.3 ERP 축 실증 테스트 — test@jeilm.co.kr (2026-09-07, 관리자 승인 후 실행)

목록에 항목을 등재해 실제로 ERP 가 바뀌는지 끝까지 확인했다.

단계 결과
① 목록 등재(사용자 ID·사용자명·퇴사일자, 진행구분 비움) 흐름 실행됨(526ms, Succeeded) — 그러나 SQL 은 건너뜀
② 진행구분을 - 로 변경 흐름 즉시 재실행 → 처리 완료
③ ERP 반영 확인(미러 재적재) usr_nm 테스트 계정 → 테스트 계정(퇴사) · USE_YN Y → N · 역할 2건 → 원천에서 삭제됨
④ SharePoint 되쓰기 진행구분 완료 · 처리내용 test@jeilm.co.kr / admin_test id 퇴사 처리완료
⑤ 대사 화면 반영 recon_type = 계정비활성

🔑 진행구분을 비워 두면 아무 일도 일어나지 않는다. 신규 항목의 기본값은 빈 값이고, 흐름 조건은 진행구분 == '-' 이라 조건 불일치로 조용히 지나간다(실패로도 안 뜬다). 포털이 등재할 때 진행구분을 반드시 - 로 채워야 한다. 선택지는 대기 · - · 완료 3종.

원복 필요: 테스트 계정은 현재 ERP 에서 퇴사 처리된 상태다. 역할 2건 (7.사업관리_프로젝트등록권한(영업포함 전체) · 0.공통_설정권한)은 DELETE 되어 되돌아오지 않는다 — 필요하면 관리자가 ERP 에서 수동 재부여해야 한다(목록 항목 「비고」에도 역할명을 남겨 뒀다).

3.4 곁가지로 드러난 결함 3건 (이 기능의 전제)

① 그룹웨어는 이메일이 비어 있을 수 있다 — 매칭 키가 깨진다. 그룹웨어 뷰 517행 중 이메일이 있는 건 471행. 이메일 없이 사용중인 계정이 7건이고, 수집기가 email LIKE '%@%' 로 걸러 미러에 넣지 않는다. 그래서 대사가 이들을 "그룹웨어 없음"으로 오판한다.

로그인ID 이름 부서 비고
ks.ryu 유계상 생산팀 실제 재직자 — 대사에서 has_gw=false 로 잘못 표시 중
test@jeilm.co.kr 테스트 계정 총무팀 이번 테스트 계정 — 이래서 미러에 없었다
acct5·6·7·10 재무5·6·7·10 재무팀 공용 계정
jeil8060 조회용 총무팀 공용 계정

→ 대책: 그룹웨어 축의 보조키로 로그인ID 를 함께 싣는다(이메일이 없으면 로그인ID로 매칭). test@jeilm.co.kr 처럼 로그인ID 자체가 이메일 형태인 경우가 있어 실효가 있다. 이 보정 없이는 일괄 처리가 대상을 못 찾는다.

② ERP usr_nm 이 규칙에서 벗어난 계정이 있다. 파싱 규칙은 부서명_이름[(휴직)|(퇴사)] 인데 테스트 계정은 admin_test id 였다. 일괄 처리는 이 필드에 (퇴사) 를 붙이는 조작이므로, 형식이 깨진 계정은 예외 처리가 필요하다.

③ usr_role 미러에 삭제 잔재가 남는다 — 권한 회수 검증이 거짓말을 한다. §3.3 테스트에서 ERP 원천의 역할이 1,723 → 1,721 건으로 줄었는데(=테스트 계정 2건 DELETE), 미러는 여전히 1,723 건이고 삭제된 2건이 그대로 남아 있었다(그 행만 synced_at 이 옛 실행 시각). usr_role job 이 증분 upsert 만 하고 원천에서 사라진 행을 지우지 않기 때문으로, usr_master 에서 이미 겪은 것과 똑같은 함정이다(§14 reconcile 로 해소한 그 결함). 퇴사 처리의 핵심 확인 항목이 "권한이 회수됐는가" 인데, 미러가 옛 역할을 계속 보여주면 대사가 "권한이 아직 살아 있다"고 잘못 말한다. → 대책: usr_role 도 전량 스냅샷으로 바꾸거나 usr_master 처럼 정합(reconcile) 후처리를 붙인다.

3.5 화면 — 계정·조직 통합관리 플랫폼 (2026-09-08 신설)

퇴사 처리는 계정 대사와 부서 매핑을 함께 봐야 하는 일인데, 두 화면이 따로 있어 어느 쪽에도 자리가 없었다. 그래서 셸 화면 /admin/identity 를 만들고 그 안에 모듈로 넣었다.

모듈 내용 구현
🏠 현황판 현재 인원·조치 대상·퇴사 미정리 KPI + 모듈 진입 신규
🔗 계정 대사 4축 대사(기존 화면) /admin/accounts?embed=1
👥 사용자·부서 매핑 대사(기존 화면) /admin/user-dept?embed=1
🚪 퇴사 처리 축별 자동화 상태 · 잔여 조치 대상 · 실행 방법 신규

두 기존 화면은 단독 주소도 그대로 유지한다(북마크 보존). ?embed=1 일 때만 자기 머리말·꼬리말을 감추고 셸이 껍데기를 그린다. 모듈은 처음 열릴 때만 로드해 Edge Function 콜드스타트가 겹치지 않게 했다.

「잔여 조치 대상」은 대사 데이터에서 인사상 퇴사인데 어느 축이든 계정이 살아 있는 사람을 뽑는다 (has_hr && !hr_active && (has_erp || has_gw || has_ms), 공용·설비 계정 제외). 축별로 무엇이 남았는지까지 보여주므로, 처리 후 「데이터 업데이트」를 돌리면 목록에서 자동으로 빠진다.

4. 설계 — 2단계

4.1 Phase 1 — 퇴사 처리 오케스트레이터 (권한 없이 지금 가능)

시스템이 대신 실행하지는 않지만, 무엇을 어디서 어떻게 해야 하는지 지시하고, 사람이 처리한 결과를 대사로 자동 검증해 체크를 켜 준다. 오늘 8명을 손으로 정리하며 겪은 누락·중복·"어디까지 했더라"를 없애는 것이 목적이다.

[대사 화면] 대상 선택 → [퇴사 처리 시작]
      │
      ├─ 포털DB에 케이스 생성 (offboarding_case: 이메일·성명·퇴사일·요청자·요청시각)
      │
      ├─ 축별 작업 3건 생성 (offboarding_task: erp / gw / ms)
      │     각 작업에 "그 시스템에서 할 일"을 구체 절차로 표시
      │
      ├─ 사람이 각 시스템에서 처리
      │
      └─ 다음 「데이터 업데이트」 후 → 대사 결과로 축별 완료 자동 판정 → 체크 자동 점등
            · ERP 완료  : usr_master_s.use_yn=false  AND usr_nm LIKE '%(퇴사)%'
            · 그룹웨어 완료: acct_groupware.status='미사용'  (또는 원천 useState=1)
            · MS 완료   : acct_ms.account_enabled=false AND display_name LIKE '%퇴사%'

화면에 그대로 띄울 절차(오늘 실측으로 확정한 것):

  • 그룹웨어 — 관리자 > 기본정보관리 > 직원관리 → 기준일자를 퇴사일 이전으로 변경(이걸 안 하면 검색해도 안 나온다) → 우측 상단 검색 → 카드 클릭 → 수정 → 사용여부 → 사용중지 → 수정 저장
  • ⚠ 사용중지를 누르면 퇴사일이 오늘 날짜로 자동 덮어쓰기된다. 저장 전에 실제 퇴사일로 되돌릴 것
  • ⚠ 같이 나타나는 메일 삭제여부 체크박스는 절대 건드리지 않는다(메일계정·메일정보 일괄 삭제)
  • MS — Entra 관리센터 > 사용자 > 로그인 차단 + 표시이름에 [퇴사] 접두
  • 표기 형식이 [퇴사] 320건 / (퇴사) 26건으로 섞여 있다 → [퇴사] 로 통일 권고
  • ERP — 인사 퇴사 처리 후 계정 비활성 + usr_nm 에 (퇴사) (유니포인트 표준 프로세스 확인 필요)

Phase 1 만으로 얻는 것: 누락 방지(3축 체크리스트), 진행 상황 가시화, 처리 이력(감사), 그리고 "했다고 생각했는데 안 된 것"을 대사가 잡아낸다. 오늘 그룹웨어 퇴사자 13명 중 9명이 계정 사용중으로 남아 있던 것이 정확히 이 유형이다.

4.2 Phase 2 — 실제 자동 실행 (권한 확보 후, 축별 독립 승격)

인터페이스(케이스·작업·검증)는 Phase 1 그대로 두고, 작업의 실행 방식만 수동 → 자동 으로 바꾼다.

축 필요한 것 난이도 비고
ERP Graph 응용 권한 Sites.ReadWrite.All(또는 목록 한정 Sites.Selected) — 포털이 SharePoint 목록 「ERP 퇴사처리 RPA」에 항목을 등재하면 끝. 기존 흐름이 1분 내 처리 가장 낮음 — 새로 만들 것이 없다 ERP MSSQL 은 건드리지 않는다. 등재 실패·흐름 미실행은 진행구분이 -로 남아 화면에 드러난다
MS 응용 권한 User.ReadWrite.All + 테넌트 관리자 동의. accountEnabled 변경에는 User Administrator 디렉터리 역할이 추가로 필요할 수 있음(부여 후 재실측) 낮음 실행 위치: 러너 또는 Edge Function
그룹웨어 벤더(ONUL Ware) 협의 — ①관리 API ②쓰기 전용 저장프로시저 ③(최후) 러너 측 UI 자동화 중 — 유일하게 협의가 필요 DB 직접 UPDATE 는 앱 로직·이력을 우회하므로 권장하지 않음

축별 독립 승격이 핵심이다. 셋이 다 열릴 때까지 기다리지 않는다. Sites.ReadWrite.All 하나만 열려도 ERP 축이 완전 자동이 되고, 그룹웨어·MS 는 Phase 1 지시서로 남는다.

4.3 목표 흐름 (ERP 축 자동화 시)

포털 [퇴사 처리]
  ├ ① 케이스 생성 + 현재 ERP 역할 목록을 스냅샷으로 기록(DELETE 대비)
  ├ ② SharePoint 「ERP 퇴사처리 RPA」에 항목 등재
  │     사용자 ID = 이메일 · 사용자명 = 부서_이름 · 퇴사일자 · 진행구분 = '-'
  ├ ③ (1분 내) 기존 흐름이 ERP 반영 → 진행구분 '완료' + 처리내용 기록
  ├ ④ 그룹웨어·MS 는 Phase 1 지시서로 사람이 처리(권한 열리면 자동으로 승격)
  └ ⑤ 다음 「데이터 업데이트」 대사가 3축 완료를 자동 확인

사용자명(부서_이름) 을 포털이 만들어 넣어야 한다. ERP usr_nm 형식과 같아야 하며, 형식이 깨진 계정(§3.4②)은 등재 전에 걸러 관리자에게 확인받는다.

5.2 자동화 설계

도구: Playwright(Python) — 러너 호스트(DESKTOP-1UUKNSM, 이미 ETL·그룹웨어 DB 접근이 되는 곳)에서 headless 실행. Chrome MCP 가 아니라 Playwright 를 쓰는 이유는 무인 실행·재시도·증적 저장이 필요하기 때문이다.

Playwright 를 쓰면 유리한 점 — 모달 처리 이 화면은 7~9단계에서 confirm/alert 를 띄운다. 브라우저 자동화에서 모달은 흔한 실패 지점인데, Playwright 는 page.on("dialog", ...) 로 정식 처리한다. (오늘 Chrome MCP 로 할 때는 window.alert· window.confirm 을 덮어써서 우회해야 했다 — 임시방편이라 무인 운영에는 부적합하다.)

5.3 안전장치 (화면 자동화라서 더 엄격하게)

  1. 3중 대조 후 진행 — 로그인ID·이름·퇴사일이 모두 맞을 때만 12단계로 간다. 하나라도 어긋나면 중단.
  2. dry-run 기본 — 저장 직전까지만 수행하고 화면 상태를 리포트. --apply 를 줘야 실제 저장.
  3. 증적 스크린샷 — 처리 전·후를 파일로 남긴다(감사 로그, CLAUDE.md §6).
  4. 1건씩 순차, 실패 시 전체 중단 — 부분 성공 상태로 방치하지 않는다.
  5. 저장 후 재검증 — 퇴사자 조회에서 사용중지를 확인해야 성공으로 친다.
  6. 금지 조작 하드코딩 차단 — 삭제 버튼·메일 삭제 체크박스는 코드에서 아예 다루지 않는다.
  7. UI 변경 감지 — 선택자를 못 찾으면 즉시 중단하고 Phase 1 지시서로 폴백. 조용히 잘못 누르는 것보다 멈추는 게 낫다.

  6. 드라이런 — 자동 실행 단계에서도 "무엇이 바뀔지"를 먼저 보여주고 실행한다.
