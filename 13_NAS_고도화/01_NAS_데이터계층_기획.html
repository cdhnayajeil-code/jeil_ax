01 · NAS 데이터 계층 기획 (v3) — ERP 는 Supabase, 누적은 NAS, 둘은 역방향 큐로

관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-09-30(NAS 가 사내 내부망·내부 방화벽 안이라는 사실 반영 · 1단계 구현·검증 완료) · 상태: Draft v3 — 안 D 채택 · N1 구현·라이브 검증 완료(REQ-0097) · 실제 NAS 경로 적재만 남음 선행: 00_NAS연계_타당성검토 · 의사결정용 도식 자료: 02_의사결정_브리핑(/docs/nas/decision) 관련: 11_제품기획/14_부서에이전트_운영기획.md(ADR-109) · 11_제품기획/13_챗봇_모듈형_고도화_기획.md(ADR-108) · 12_에이전트관리/02_개발가이드.md · 10_ERP_DB연계/etl/(러너) · CLAUDE.md §1·§4·§5·§17

개정 이력

판 일자 전제 권고
v1 2026-09-29 밖 → NAS 경로를 열 수 없다고 가정 안 A — NAS = 아웃바운드 전용 창고(보관·백업)
v2 2026-09-29 관리자 답변: 터널 보안 승인 가능 · 사외 사용 필요 · 문서는 NAS 에 새로 정리 · IT담당 직접 운영 · 목적: "Supabase = ERP 정합성, NAS = 대용량·누적 데이터" 안 B — NAS = 누적 데이터 정본 + 보안 터널 + NAS 데이터 API
v3 2026-09-30 관리자 확인: NAS 는 사내 내부망·내부 방화벽 안(DMZ 아님). 터널은 포트를 열지 않아도 외부 세션이 내부존에서 종단되어 보안 승인 + 세그먼트·VLAN 검토가 따라오고, 공인 대역이라 룰 실수 한 줄이 곧 노출이다. 게다가 터널 주소(D-107)는 회사 도메인 네임서버 이관을 물고 있다 안 D — 역방향 큐(인바운드 0 · 방화벽 룰 추가 0건). 터널은 N3(문서 검색) 실측 뒤 조건부

비개발자용 한 줄 요약 — ERP 숫자·권한처럼 정확해야 하고 매번 읽는 것은 지금처럼 Supabase 에, 대화기록·생성 자료·부서 문서처럼 크고 계속 쌓이는 것은 사내 NAS 에 둔다. 둘은 사내 NAS 쪽에서 밖으로만 연결해 「할 일」을 받아 오는 방식(역방향 큐)으로 잇는다. 밖에서 NAS 로 들어오는 길을 만들지 않으니 방화벽을 건드릴 일이 없고, 재택·출장 중에도 쓸 수 있다(직원 브라우저는 포털만 보기 때문이다).

0. 결론 먼저

# 제안 한 줄 이유
1 데이터 배치 원칙: ERP 중간DB·권한·에이전트 설정 = Supabase / 대화기록 장기분·생성 자료·부서 문서·색인·첨부 원본·백업 = NAS 정본 정합성 데이터와 누적 데이터의 성격이 다르다. Free 500MB·자동 백업 없음의 한계도 함께 푼다
2 연결 = 역방향 큐(안 D) — 사내 워커가 밖으로만 연결해 큐를 집어가고 데이터도 RPC 로 받아 간다 인바운드 0 · 방화벽 룰 추가 0건 · 터널·도메인·신규 벤더 계정 불필요. 사외 사용은 그대로(브라우저는 포털만 본다)
3 에이전트 두뇌(게이트웨이)는 Supabase 하나 유지(ADR-109) — NAS 는 데이터 보관만 권한 판정·턴 기록·비용 집계가 갈라지지 않는다
4 outbox 를 쓰지 않는다 — 워커가 커서로 증분 pull 하고, 원본은 그대로 둔다 행은 ack 전까지 Supabase 에 남아 유실이 구조적으로 불가능하다. 게이트웨이 무변경(Edge Function 배포 0건)
5 문서 색인은 NAS 안에서 — 조각 텍스트를 클라우드 DB 에 쌓지 않는다 데이터 주권 · D-95 쟁점을 "LLM 전송"으로 좁힘
6 NAS 가 유일한 원본이 되므로 디스크 이중화·외부 사본·UPS·메모리 16GB 가 선결 장비 한 대 고장 = 데이터 손실을 막는 최소 조건

  • 공개 경로가 하나도 없다. 터널 URL·Access 토큰·포털 JWT 가 전부 불필요해졌다. DSM·SMB·SSH 는 물론 워커 자체도 밖에서 닿을 수 없다.

3. NAS 워커(nas_worker.py) — 구현 완료(REQ-0097 · 2026-09-30)

서버가 아니라 큐 소비자다. 포트를 열지 않고, 주소도 없고, 받을 인증도 없다.

항목 설계(실구현)
형태 10_ERP_DB연계/etl/nas_worker.py(워커 n1.0) — 기존 러너에 편입(§17.2): 서브커맨드 jeil_runner nas · 작업 종류 nas_sync(group nas · 상한 60분) · 능력 표식 nas. EXE 는 계속 하나이고(§17.1), NAS 에서는 EXE 가 아니라 Python 소스로 돈다
하는 일 ① 심박(nas_runner_ping) ② 큐 1건 선점(nas_request_claim) ③ 소스별로 nas_export_page 를 반복 호출해 JSONL 로 기록 ④ 파일이 제자리에 놓인 뒤 nas_export_commit ⑤ 건수·SHA256·사유를 nas_request_finish 로 되쓴다
평가 반영 턴은 id 커서라 한 번 내보내면 다시 보지 않는다 → 나중에 달린 평가(rating)는 별도 소스 agent_turn_rating(뷰 v_agent_turn_rating · 커서 rated_at)으로 따라간다(정본 SQL 84 · 2026-10-02). 본문은 싣지 않고 id 로 잇는다
무엇을 내보내는가 코드가 아니라 DB 허용 목록(etl_meta.nas_export_source)이 정한다 — 워커에 테이블 이름·SQL 을 심지 않는다. 백업 등 새 용도는 행 추가로 늘린다(§13.3·§16.3 과 같은 원칙)
출력 증분 대화기록/<소스>/<연도>/<소스>_<날짜>_<시각>.jsonl(새 행 0건이면 파일을 만들지 않는다) · 전량 ERP스냅샷/<날짜>/<소스>.jsonl.gz(하루 한 장) · 회차마다 _manifest/<날짜>/<run_id>.json(소스별 건수·SHA256·커서 범위·암호화 여부)
정합 보장 임시 파일 → os.replace 원자 교체 · 파일이 놓인 뒤에만 커서 전진(중단되면 같은 지점부터) · 전량 스냅샷은 시작 전 건수와 대조해 어긋나면 실패로 닫는다 · 전순서는 행 전체(jsonb) 기준(단일 컬럼 정렬 + OFFSET 은 같은 값이 여럿일 때 페이지 경계에서 행을 조용히 빠뜨린다)
NAS 루트 --root > NAS_DATA_ROOT > .claude/nas.path(절대경로 1줄 · 저장소에 적지 않는다 §1.1). 못 찾으면 요청을 선점하지 않는다(§17.6 — 집어놓고 실패시키면 사람이 다시 눌러야 한다)
문서 색인 N3 — NAS 내부 SQLite FTS5 또는 pg_trgm(파일럿 실측 후 선택) · 변경분만 재색인 · 민감 패턴 파일 제외. 검색 왕복은 같은 큐에 롱폴링/Realtime 을 얹는다
백업 N1-c — 같은 exporter 에 소스만 추가한다. pg_dump 대신 JSONL(HTTPS 443) 인 이유는 5432/6543 직결이 내부 방화벽 확인에 묶이고, DB 가 NAS 를 부를 수단(pg_net)이 아예 없기 때문이다
비밀값 검증 단계에서는 작업PC 의 기존 .env(SUPABASE_URL·SUPABASE_SERVICE_ROLE_KEY)를 쓴다. NAS 컨테이너로 옮길 때는 service_role 을 두지 않고 전용 좁은 키로 바꾼다(브리지 Edge Function 또는 custom role 토큰) — 다음 단계 선행 조건
암호화 현재 미적용 — 이 호스트에 cryptography 모듈이 없다. 조용히 건너뛰지 않고 manifest·요청 결과에 사유를 남긴다(§17.6). 보완은 NAS 폴더 권한(시스템·관리자 전용) + Hyper Backup 암호화
오류 처리 어떤 예외가 나도 요청을 running 에 방치하지 않는다(except (Exception, SystemExit) — need() 가 SystemExit 을 던진다) · DB 에 되쓰는 문자열은 _redact() 로 계정·IP·UNC 경로를 가린다

4. 게이트웨이 쪽 변경 — N1 에서는 하나도 없다

항목 설계
Edge Function 무변경 · 배포 0건. agent_turn insert 경로(core/agent_api.ts)와 cleanupTurns() 를 건드리지 않는다
outbox 쓰지 않는다. 원본을 지우지 않으니 필요가 없다 — 워커가 커서로 증분 pull 하면 행은 ack 전까지 Supabase 에 남아 유실이 구조적으로 불가능하다. (v2 의 「pg_cron 1분 주기로 NAS 전송」은 실현 불가였다: 이 프로젝트에 pg_net·extensions.http 가 없어 DB 가 스스로 NAS 를 부를 수단이 아예 없다)
agent_turn 보존 이번에는 바꾸지 않는다(관리자 결정: 복사만·삭제 없음). Supabase 14일 + NAS 나머지로 가는 전환은 커서·행수·해시가 여러 회차 일치하는 것을 본 뒤 별건으로 한다
DB 변경 정본 SQL 이관/sql/82_nas_export_queue.sql(+_rollback.sql) — 표 4종 + RPC 10종 신설. 라이브 적용 완료(마이그레이션 nas_export_queue_v1, 2026-09-30). 기존 객체는 하나도 고치지 않았다
N3 에서 추가될 것 도구 모듈 modules/nas/: search_company_docs · read_company_doc(ADR-108 규격 · extra.ts 등록 · 기존 search_my_documents 와 결과 형식 통일 — {기준시각, 검색어, 반환수, 목록[{이름,수정일,링크,발췌}], 안내, __view}) · 관리 화면 과거기록 조회 · 장애 시 「사내 보관소 점검 중」 뷰(§16.6 — 지어내지 않는다)
주의(N3) 도구 실행에 엔진 타임아웃이 없다(core/engine.ts 에 타임아웃 코드 0건) → NAS 왕복 도구는 모듈 안에서 직접 상한을 걸어야 한다. 그러지 않으면 워커가 죽었을 때 대화가 매달린다

5. 보안 · ITGC

# 항목 설계
1 노출면 0개 — 공개 호스트·터널 URL·열린 포트가 없다. DSM/SMB/SSH 비노출. ⚠ PoC 워커 포트 8765 는 아직 열려 있다(2026-09-30 작업PC 에서 접속 성공) — HTTP·무인증이라 API 키 적용 전 폐쇄가 필요하다(D-98 미조치)
2 인증 Access 토큰·포털 JWT 2중이 불필요해졌다. 대신 워커가 가진 Supabase 키 + service_role 전용 RPC 화이트리스트로 판정한다. 검증은 작업PC 의 기존 키를 쓰되, NAS 컨테이너에는 service_role 을 두지 않는다(전용 좁은 키로 전환 — 다음 단계 선행)
3 권한 내보낼 수 있는 것은 허용 목록의 public 관계뿐이다 — rel_schema = 'public' CHECK 로 급여(erp_secure)는 등재 자체가 불가능하다. 허용 목록 밖 소스는 빈 결과가 아니라 예외(0건 성공으로 읽히면 조용히 틀린다 — 2026-08-31 refValid silent-pass 교훈). N3 문서 권한은 폴더의 부서코드(ADR-107) ∩ 사용자 권한

8. 비교안(요약)

안 내용 판단
A (v1) NAS = 아웃바운드 전용 창고 — 밤마다 가져가 보관·백업만 「밤 배치」라서 누적 정본에 ✕ 를 받았다. 안 D 가 이 안의 확장형이다(배치 → 실시간 pull)
B (v2) 터널 + NAS 데이터 API + outbox 철회. NAS 가 내부망이라 세션이 내부존에서 종단되고, 도메인·보안 승인이 따라온다. outbox 의 pg_cron push 는 pg_net 이 없어 실현 불가였다
C (PoC) NAS 에서 Agent SDK 실행 — 브라우저가 터널로 직접 연결 두뇌 이원화(ADR-109 충돌) → 장시간 작업만 조건부 편입(N4)
D 역방향 큐 — 사내 워커가 밖으로만 연결해 큐를 집어가고 데이터도 RPC 로 받아 간다 채택 · N1 구현·검증 완료. 인바운드 0 · 방화벽 룰 추가 0건 · 도메인·보안승인·신규 벤더 0 · 사외 사용 그대로 · 회사가 이미 운영 중인 패턴(ERP 서버 러너)
E (보완) Tailscale/WireGuard 게이트웨이 경로에는 쓸 수 없다(Edge 런타임에 클라이언트 설치 불가). 단 관리자 원격 운영(DSM·SSH) 에는 가장 심플 — D-98 포트 폐쇄와 묶어 검토
F 포트포워딩 + DDNS 비권고. Supabase Edge 의 출구 IP 가 고정이 아니라 IP 허용목록을 쓸 수 없다 → 전세계 공개 + 앱 인증만. 내부망·공인 대역이라 룰 실수의 대가가 특히 크다
G Synology QuickConnect 비권고. DSM 노출 전제가 §5.1 과 충돌 · 커스텀 포트 정식 지원 아님 · 서드파티 경유는 그대로인데 신원 게이트가 없다
H 터널 유지 + 별도 도메인 터널이 정말 필요해지면(N3 실측) 이 형태로. 회사 도메인 네임서버 이관 리스크가 0 이 된다

10. ADR-110 개정안 (요지)

  • 결정: Supabase = ERP 중간DB·권한·에이전트 설정의 정본(정합성 계층), 사내 NAS = 대화기록 장기분·생성 자료·부서 문서와 색인·백업의 정본(누적 계층).
  • 결정: 둘은 인바운드 없는 역방향 큐로 잇는다 — 사내 워커가 밖으로만 연결해 큐를 집어가고 데이터도 RPC 로 받아 간다. 공개 경로가 하나도 없다. 터널은 N3(문서 검색) 실측에서 지연이 문제일 때만 조건부로, 그때도 별도 도메인으로. 근거: NAS 가 사내 내부망·내부 방화벽 안이라 터널은 외부 세션을 내부존에 종단시키고, 공인 대역이라 룰 실수의 대가가 크며, 회사가 이미 같은 pull 구조를 운영 중이다(ERP 서버 러너).
  • 결정: 에이전트 두뇌(게이트웨이)는 하나(ADR-109). outbox 를 쓰지 않는다 — 커서 증분 pull 이면 행은 ack 전까지 Supabase 에 남아 유실이 구조적으로 불가능하고, 게이트웨이를 고칠 필요가 없다.
  • 대안(흡수): 아웃바운드 전용 창고(v1) — 안 D 가 그 확장형(배치 → 실시간 pull).
  • 대안(철회): 터널 + 데이터 API(v2 안 B) — 내부존 종단·도메인 이관 부담, outbox 의 pg_cron push 는 pg_net 부재로 실현 불가.
  • 대안(조건부): NAS 실행 엔진(PoC) — 장시간 작업이 실측될 때 게이트웨이 모듈로 편입.
  • 상태: Accepted(1단계) — 2026-09-30 D-105·D-106 확정 + N1 구현·라이브 검증 완료(REQ-0097). 전면 Accepted 는 D-104 조치 + 실제 NAS 경로 적재 확인 후.
