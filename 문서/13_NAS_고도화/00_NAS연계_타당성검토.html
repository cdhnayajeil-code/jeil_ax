00 · NAS 연계 타당성 검토 — "NAS 는 창고, 가게는 그대로"

관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-09-29 · 상태: 검토 완료(Draft) — 관리자 결정 D-N1~N6 대기 대상: 사내 NAS 에이전트 워커 PoC 결과 문서(이 폴더의 claude_…NAS-PoC_2026_09_28.md — 내부 IP·계정 포함, 커밋 제외 원본) 목적(관리자): 부서 에이전트가 만든 데이터와 에이전트가 쓰는 데이터를 사내 NAS 에서 관리할 수 있는가 기획(어떻게): 01_NAS_데이터계층_기획 · 관련: 11_제품기획/14_부서에이전트_운영기획.md(ADR-109) · 12_에이전트관리/00_현재상태.md · CLAUDE.md §1·§4·§17

⚠ 2026-09-30 전제 추가 — 연결 방식 교체: 안 B(터널) → 안 D(역방향 큐) · 1단계 구현·검증 완료 NAS 가 사내 내부망·내부 방화벽 안(DMZ 아님)이라는 사실이 확인됐다(§4.5 갱신). 터널은 포트를 열지 않아도 외부 세션이 내부존에서 종단되어 보안 승인·세그먼트 검토가 따라오고, 공인 대역이라 룰 실수의 대가가 크다. 그래서 인바운드를 아예 만들지 않는 역방향 큐로 갔다 — 사내 워커가 밖으로만 연결해 큐를 집어간다. 데이터 배치 판정(§3)은 그대로 유효하고, 연결 방식만 바뀌었다. 1단계(대화기록·ERP 스냅샷 적재)는 구현·라이브 검증 완료(REQ-0097 · 79,472행 내보내기·복원 대조 일치). 최신은 01 기획 v3.

⚠ 2026-09-29 전제 변경 — 판정 갱신: 「타당(조건부)」 · 권고 = 안 B(→ 2026-09-30 안 D 로 교체됨) 관리자 답변(터널 보안 승인 가능 · 사외 사용 필요 · 문서는 NAS 에 새로 정리 · IT담당 직접 운영)과 목적("Supabase = ERP 정합성, NAS = 대용량·누적 데이터")에 따라, 아래 v1 판정의 "밖 → NAS 경로 없음" 전제가 풀렸다. 대화기록·생성 자료·문서는 NAS 정본, 연결은 Cloudflare Tunnel + Access, 장애는 outbox 로 대비한다. 조건: 확인 7건 회신 · NAS 기반 보강(디스크 이중화·외부 사본·UPS·메모리). 최신 권고는 01 기획 v2 · 의사결정 자료는 02 브리핑. 이하 본문은 v1 검토 기록으로 보존한다(PoC 분석·문제점 8건은 그대로 유효).

비개발자용 한 줄 요약(v1) — NAS 는 "사내 창고" 로 쓰는 것이 맞다. 문서 원본을 두고, 에이전트가 만든 자료와 대화 기록의 사본을 오래 보관하는 곳이다. 직원이 질문할 때마다 답을 꺼내 주는 "가게"(Supabase 게이트웨이·DB)는 지금 자리 그대로 둔다. 창고(NAS)는 가게로 물건을 가져다 놓기만 하고, 밖에서 창고 문을 열고 들어오는 길은 만들지 않는다 — 그래서 방화벽 정책을 바꾸지 않아도 된다.

0. 결론 먼저

# 판단 한 줄 이유
1 조건부 타당 — NAS = 데이터 계층(원천·보관) 으로 한정 저장 여유(10.5TB 중 약 17GB 사용)와 사내 보관(데이터 주권)의 이점은 크고, 연산 부담은 없다
2 연결은 NAS → 클라우드 한 방향(아웃바운드 pull)만 클라우드(Vercel·Supabase)는 방화벽 안의 NAS 에 들어갈 수 없다. 들어오는 길(터널·포트 개방)을 여는 순간 보안 승인·인증서·인증이 전부 선행된다
3 실시간 정본은 Supabase 유지 — 에이전트 설정·대화기록·중간DB 게이트웨이와 관리 화면이 매 질문마다 읽는 데이터다. NAS 로 옮기면 들어오는 길이 필요해진다
4 데이터 4종 판정: 문서 = NAS 원본 · 생성 자료 = NAS 장기보관 · 대화기록 = NAS 백업 · ERP 복제 = 스냅샷만, ETL 이전은 보류 §3
5 PoC 의 실행 엔진(Agent SDK 워커)은 2단계로 미룬다 ADR-109(게이트웨이 하나)와 겹치고, 들어오는 길·HTTPS·JWT 가 선행돼야 한다. 붙이더라도 게이트웨이의 "장시간 작업 모듈"로 편입
6 가장 빠른 가치 = 백업 Supabase 가 Free 플랜이라 자동 백업이 없다. NAS 야간 백업만으로도 운영 위험이 크게 준다
7 착수 전 선결 과제 6건(§4) — 특히 PoC 포트 무인증 개방·NAS 운영 주체 창고로 쓰려면 창고 자체가 먼저 안전해야 한다

1. PoC 문서 분석 요약

항목 PoC 내용 검토 의견
목표 NAS Docker 에 Claude Agent SDK 워커를 두고 포털에서 다단계 작업(파일 생성·도구 호출)을 맡긴다 목표는 실행 엔진. 관리자 목적(데이터 관리)과는 초점이 다르다 → 이 검토에서 목적을 데이터 계층으로 재정렬
장비 DS923+ · Ryzen 2코어 · RAM 8GB(최대 32GB) · HDD 4TB×4, SSD 캐시 없음 저장소로는 충분. 메모리 8GB 를 itasset 과 공유 — 실행 엔진엔 빠듯, 데이터 워커엔 충분
네트워크 사내 방화벽에서 특정 IP 만 허용. NAS 의 인터넷 아웃바운드 확인 아웃바운드 가능 = 이 기획의 핵심 전제. 인바운드는 없음
구현 FastAPI + Agent SDK + Claude Code CLI, 사용자별 작업폴더, SSE 스트리밍 코드 품질은 PoC 로 양호(입력 검증·경로 이탈 차단·도구 허용 목록)
검증 범위 빌드·기동·입력검증·동시요청까지. API 키 미적용으로 실제 응답은 미검증 현재 부서 에이전트와 같은 선행 조건(회사 명의 API 키 발급)
포털 연결 안 포털이 5분 JWT 발급 → 브라우저가 NAS 로 직접 SSE 브라우저가 NAS 에 닿으려면 사내망 전용(재택 불가) 또는 터널(보안 승인) — 미결
로드맵 Phase 1 API 연결 → 2 ERP 도구 → 3 포털 연동 → 4 운영(ETL NAS 이전 검토 포함) Phase 2 의 "Supabase 읽기 전용 롤 조회"는 이미 게이트웨이에 24종 도구로 있다 → 중복 구축 위험

3. 데이터 4종 적합도 판정

데이터 판정 방식 근거 · 조건
① 사내 문서·양식·규정 ◎ 적합 — NAS 가 원본 NAS 색인 워커가 허용 폴더를 읽어 텍스트 조각 + 메타를 Supabase 로 올린다 → 게이트웨이 신규 모듈이 검색 에이전트 품질을 가장 크게 올리는 자료. 조건: 허용 폴더 화이트리스트(ai_document_scope 확장) · 민감 폴더 제외 · 조각 텍스트가 클라우드에 올라가는 것에 대한 관리자 승인(D-N2)
② 에이전트 생성 자료 ○ 적합 — 장기 보관 최근 30일은 Storage(화면 내려받기용) 유지, NAS 아카이브 워커가 사용자별 폴더로 가져간다 사내에서 SMB 로 본인 폴더 열람 가능. 조건: 폴더 권한 = 본인 + 관리자, 보존 기간(D-N4)
③ 대화기록·개선대장 △ 백업만 Supabase 가 정본. NAS 는 야간 백업(암호화 보관) 관리 화면이 실시간으로 읽는 데이터라 정본 이전 불가. 조건: 보존 180일(D-3)을 백업에도 적용 — 원본을 지워도 백업에 남으면 약속 위반
④ ERP 복제 데이터 △ 스냅샷만 / ETL 이전 보류 중간DB 정본 유지. NAS 에는 erp_ro 야간 스냅샷(복구용) ETL 이전은 ① 사내망↔IDC 경로 검증 ② §17(러너 EXE 하나)·§4.6(유니포인트 협의) 검토가 먼저. 급여 등 erp_secure 는 스냅샷에서도 제외

4. PoC 에서 발견한 문제점 · 선결 과제

# 문제 위험 조치(권고)
1 PoC 문서 본문에 내부 IP·NAS 관리 계정·점검 PC 정보가 평문 CLAUDE.md §1.1·§1.3 위반 요소 — 커밋 시 유출 원본은 커밋 제외(.gitignore 반영). 파생 문서는 별칭(사내NAS·NAS관리계정)만
2 이름 충돌 — NAS 컨테이너 jeil-agent ↔ 게이트웨이 운영 승격 이름 jeil-agent(14 기획 §1) 운영·장애 대응 때 대상 혼동 NAS 쪽을 jeil-nas-worker 로(D-N6)
3 워커 포트가 HTTP·무인증으로 열려 있다(방화벽 IP 제한에만 의존) 허용 IP 안의 누구나 호출 가능. API 키를 넣는 순간 비용·데이터 노출로 직결 키 적용 전 컨테이너 중지 또는 JWT 필수화(D-N5). 데이터 워커는 포트를 아예 열지 않는다
4 .env(API 키 자리)가 SMB 공유 폴더에 평문 공유 폴더 접근자 = 키 열람자 공유 폴더 권한 최소화 · 키 교체 절차 · 데이터 워커는 service_role 대신 전용 좁은 권한 키
5 NAS 주소 대역이 RFC1918 사설 대역이 아니다(공인 대역) + NAS 는 DMZ 가 아니라 사내 내부망·내부 방화벽 안(2026-09-30 관리자 확인) 두 사실이 겹쳐 위험이 커진다 — ① 인바운드를 만들려면 「외부 → 내부존 유입 허용」이라 방화벽 변경 중 승인 난이도가 가장 높고, 터널이라도 세션이 내부존에서 종단되어 세그먼트·VLAN 검토가 따라온다 ② 공인 대역이라 라우팅상 도달 가능한 주소여서 방화벽 룰 실수 한 줄이 곧 노출이다 인바운드를 아예 만들지 않는 설계로 갔다(안 D 역방향 큐 — 01 §8). 실수 내성이 높고 방화벽 룰 추가가 0건이다
5-1 (같은 확인) NAS 아웃바운드 HTTPS 는 가능 안 D 의 유일한 전제 확인 필요: 목적지 제한 여부 · SSL 인스펙션 · 프록시 강제 · 세션 idle timeout(롱폴링에 영향) — 지금 방식(20~60초 폴링)은 idle timeout 에 걸리지 않는다
6 운영 기반 미확인 — NAS 관리 주체가 정보전략팀 외부 · RAID/Hyper Backup/UPS 여부 미상 · itasset 과 자원 공유 · Download Station·P2P 포트·Python2·SNMP 점검 필요 창고가 한 대뿐(단일 장애점). NAS 가 백업처라면 NAS 자체의 백업이 있어야 의미 운영 주체·장애 대응 협의(D-N1), RAID 구성·Hyper Backup(외부 사본) 확인, 불필요 패키지·포트 정리
7 실행 엔진이 ADR-109(게이트웨이 하나)와 겹친다 엔진 둘 → 권한 판정·턴 기록·비용 집계 분기 2단계(N4)로 미루고 조건부 편입
8 Anthropic API 키 미발급 PoC·부서 에이전트 모두 실측 불가 부서 에이전트 남은 일 1번과 같은 작업 — 한 번에 처리

5. 기대 효과 · 비용

효과 설명
백업 공백 해소 설정·대화기록·개선대장·골든셋·중간DB 를 매일 사내 보관 — 실수 삭제·Supabase 장애 복구 가능
에이전트 품질 사내 규정·양식·부서 자료를 근거로 답하게 된다(지금은 OneDrive 허용 범위뿐)
데이터 주권 원본 문서·장기 보관본이 사내에 머문다. 클라우드엔 검색용 조각·최근 30일분만
Supabase 용량 절약 Free 500MB 한도(현재 약 91MB) — 파일 원본을 NAS 에 두면 증가 속도가 느려진다
추가 비용 거의 없음 — 기존 NAS, 컨테이너 1개(메모리 0.5GB 안팎 추정). 임베딩을 쓰면 토큰 비용 소액(01 기획 §8)

6. 종합 판정

  • 진행 권고(조건부): N0 선결 → N1 백업·아카이브 → N2 문서 색인 파일럿 순서로. 각 단계는 이전 단계가 검증된 뒤 착수한다.
  • 보류: ERP ETL 의 NAS 이전(N3 조사 결과에 따라), Agent SDK 실행 엔진(N4, 조건 충족 시).
  • 하지 않는다: 클라우드 → NAS 인바운드 경로 신설(이 기획 범위에서), NAS 로의 실시간 정본 이전.
  • 결정 요청 목록과 ADR-110 제안은 01 기획 §9·§10.
