# 15 · 챗봇과 부서 에이전트 — 역할 구분·적용 방식 가이드 (AX 관점)

> 관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-10-07 · 상태: **Proposed — 제안 ADR-113 · 관리자 결정 D-1~D-7 대기(§10)**
> 관련: [13 챗봇 모듈형](13_챗봇_모듈형_고도화_기획.md)(도구 모듈·등록부 · ADR-108) · [14 부서 에이전트](14_부서에이전트_운영기획.md)(프로필·버전·개선 루프 · ADR-109) · [11 요청접수](11_챗봇_데이터요청접수_설계.md)(ADR-011) · [06 ERP연계](06_ERP연계_챗봇활용_설계.md) · [09 ADR](09_ADR_의사결정기록.md) · 에이전트 관리 [12/00 현재상태](../12_에이전트관리/00_현재상태.md) · [12/06 템플릿](../12_에이전트관리/06_에이전트_템플릿_관리포인트.md) · 모델 설정 SSOT `실제구축준비 자료/06_챗봇_사용모델설정_SSOT.md` · `CLAUDE.md §1.6·§5.4·§10`

전사 챗봇(jeil-chat)과 부서 에이전트(1호 구매 · 2호 DRI)가 **각각 어디까지를 맡고, 그 경계를 어떻게 정하고 관리할지**를 정한다.
지금은 둘이 다른 게이트웨이·다른 화면·다른 관리 탭에서 돌아가서 "이 질문은 어디서 해야 하나", "새 기능은 어디에 넣나"가 매번 판단거리가 된다. 이 문서는 그 판단을 **규칙**으로 바꾼다.
코드·DB 변경은 §8 로드맵의 각 단계를 백로그 요청(REQ)으로 따로 열어 진행한다 — 이 문서 자체는 코드를 바꾸지 않는다.

> **비개발자용 한 줄 요약** — 챗봇은 **회사 정문의 안내데스크**, 부서 에이전트는 **부서 창구의 베테랑 담당자**다. 안내데스크는 누구에게나 열려 있고 간단한 일은 바로 처리하며, 깊은 일은 "구매 창구로 가세요"라고 안내한다. 창구 담당자는 부서 말을 알아듣고, 부서 자료를 깊게 다루며, **부서가 직접 가르쳐 키운다.** 둘은 다른 사람이 아니라 **같은 두뇌(게이트웨이)에 다른 명찰(프로필)을 단 것**이다. 관리자가 떠올린 "에이전트는 따로 관리하고, 필요할 때 챗봇에서 적용하면 그 기능이 되게"는 **명찰을 바꿔 다는 것(프로필 전환)** 으로 구현한다 — 도구를 챗봇에 섞어 넣는 것이 아니다.

## 0. 결론 먼저

| # | 결론 | 한 줄 이유 |
|---|---|---|
| 1 | 구분의 기준은 **기술이 아니라 「대상·책임·지식·개선 루프」 4축**이다(§2) | 같은 도구·같은 모델을 써도 전사 공통이면 챗봇, 부서 담당자가 책임지고 키우면 에이전트 |
| 2 | **챗봇 = 공통 에이전트 프로필(`common`)** 로 본다 — 별개 제품이 아니다 | 14 기획 §1 이 이미 예고한 방향(운영 jeil-chat 을 공용 게이트웨이의 공통 에이전트로 흡수). 관리 화면·비용·권한 판정이 한 곳이 된다 |
| 3 | 관리자 생각(에이전트는 따로 관리, 필요할 때 챗봇에서 적용)은 **맞다 — 단, 적용 단위는 도구가 아니라 프로필**이다(§5-3) | 도구만 섞어 넣으면 프롬프트가 비대해지고 부서 용어집·골든셋·담당자가 빠져 오답이 난다(09-30 실측 F-2·F-4 가 그 사례) |
| 4 | 챗봇 화면에 **「에이전트 선택」 + 「이어서 묻기」 핸드오프 카드**를 둔다 — **B안**(§4) | 사용자는 한 창에서 시작하고, 깊은 질문은 클릭 한 번으로 부서 에이전트로 넘어간다. 자동 라우팅(C안)은 측정값이 쌓인 뒤 조건부 |
| 5 | **도구는 공유, 지식·책임·루프는 부서** — 같은 도구를 두 번 만들지 않는다(§6-4) | 모듈 1개 = 코드 1곳(ADR-108). 에이전트는 도메인 묶음으로 고르기만 한다 |
| 6 | **담당자 없는 에이전트는 만들지 않는다** — 신설 게이트(§7) | 에이전트의 본질은 모델이 아니라 "부서가 키우는 루프"다. 담당자가 없으면 데모일 뿐이다 |
| 7 | 권한·실거래 금지선은 **둘 다 같다** | `perm_effective` 하나로 판정(ADR-010) · 조회·초안·접수까지(CLAUDE.md §1.6). 에이전트라고 더 많이 보거나 더 많이 하지 않는다 |
| 8 | 단계는 **0 규칙 선언 → 1 챗봇 흡수 → 2 선택·핸드오프 → 3 부서 확장 → 4 자동 라우팅(조건부)**(§8) | 각 단계는 백로그 REQ 로 열고 되돌리기 경로를 둔다 |

| 상태 | live(전사) | pilot(구매 설정 v4 · DRI 설정 v2) |

**문제는 둘이 다른 것이 아니라, 그 "다름"이 어디까지 의도된 것인지 적혀 있지 않다는 점이다.** 모델·도구·화면·관리가 모두 갈라져 있으니 새 기능이 생길 때마다 "어느 쪽에?"를 다시 묻게 된다.
이 가운데 **의도된 차이는 ③지식·②책임·④루프뿐**이고, 나머지(게이트웨이가 둘 · 모델 벤더가 갈림 · 화면 렌더 모듈 사본 · 관리 탭 두 곳)는 과도기의 중복이다. 14 기획 §1 은 이미 "검증 후 운영 `jeil-chat` 을 공통 에이전트로 흡수(별건)"를 예고했고, 이 문서는 그 별건의 **경계 규칙**을 정한다.

## 2. 구분의 축 — 기술이 아니라 「대상·책임·지식·루프」

| 축 | 전사 챗봇(= 공통 에이전트) | 부서 에이전트 | 판정 질문 |
|---|---|---|---|
| ① 대상 | 전 직원 · 부서를 가리지 않는 질문 | 그 부서 구성원(+관리자) | "누구나 물을 만한 질문인가?" |
| ② 책임 | 포털 관리자(플랫폼) | 부서 담당자(operator) + 관리자(reviewer) | "답이 틀렸을 때 고칠 사람이 **그 부서에** 있나?" |
| ③ 지식 | 공통 머리말 + 도구 설명 | 역할 안내 · 부서 답변 원칙 · 용어집 · 골든셋 | "부서 용어·맥락 없이 답하면 틀리는가?" |
| ④ 개선 루프 | 설정 수정(중앙 · 즉시) | 개선 대장 → 버전 → 회귀(부서 · 승인) | "이 기능을 누가 꾸준히 키우나?" |
| (파생) 모델 | 범용·경량(1·2단계) | 부서 업무 단계(3단계) | 모델은 **결과**이지 기준이 아니다 — 배정은 SSOT 의 단계별 권장을 따른다 |
| (파생) 비용 | 전사 한도 | 에이전트 예산 | 비용은 ②책임을 따라간다 |
| (파생) 기록 | 본인 대화(이어보기용) | 품질 개선 턴 기록 | 기록은 ④루프를 따라간다 |
| (파생) 화면 | 포털 챗 한 창 | 부서 전용 페이지(자료함·보관함·검증 탭) | 화면은 ③지식·작업형 여부를 따라간다 |

같은 도구 `get_erp_pur_order` 가 양쪽에 있어도 모순이 아니다. 챗봇에서는 "이번 달 발주 얼마야"에 집계 한 줄로 답하고, 구매 에이전트에서는 같은 도구를 PR·PU·PO 용어집과 함께 써서 "PU 번호로 발주 났어?"에 답한다.
**도구는 공유되고, 지식과 책임이 다르다.** 이 한 문장이 이 문서의 핵심이다.

## 3. 경계 판정 규칙 — 새 기능·새 질문이 어디에 속하나

질문(또는 기능) 하나를 놓고 위에서부터 묻는다. **처음 "예"가 나온 곳에서 멈춘다.**

```
Q1  실거래인가? (확정·결재·발주·송금·발송)                       → 예: 둘 다 하지 않는다(§1.6). 초안·접수까지만
Q2  전 직원이 물을 만한 질문인가?
    (내 권한·내 요청 · 문서 찾기 · 일반 초안·규정 · 전사 집계 한 줄)   → 예: 챗봇(공통)
Q3  부서 용어·맥락 없이 답하면 틀리는가?
    (PR·PU·PO 관계, 기안서 권-번호, DRI 폴더 구조 …)              → 예: 부서 에이전트
Q4  답 품질을 책임질 부서 담당자가 지정돼 있나?                   → 아니오: 에이전트로 만들지 않는다(§7 게이트)
                                                                 → 챗봇(공통)에 도구만 열어 두거나 보류
Q5  작업형인가? (파일 첨부 · 자료 생성 · NAS 저장 · 여러 단계 작업)  → 예: 부서 에이전트(전용 페이지)
Q6  두 부서 이상에 걸친 교차 조회인가? (영업 수주 ↔ 구매 발주)      → 예: 챗봇(공통 묶음에 read 도구 추가) — 「교차 에이전트」는 만들지 않는다
그 밖                                                            → 챗봇(공통)에서 시작해 사용 기록으로 승격 여부를 본다(§6-3)
```

### 3-1. 적용 예시

| 질문·기능 | 걸리는 질문 | 어디 | 비고 |
|---|---|---|---|
| "내가 볼 수 있는 화면이 뭐야" | Q2 | 챗봇 | `get_my_access` · 전원 |

| "발주 취소해줘" | Q1 | 둘 다 거부 + 초안·담당자 안내(S2) | |
| "자금일보 요약" | Q3 → Q4 | **보류** | 자금 담당자·도구가 아직 없다 — 챗봇에 집계 도구만 먼저(12/06 §5) |

> 판정이 애매하면 **챗봇(공통)에서 시작**한다. 챗봇은 전사에 열려 있어 사용 기록이 빨리 쌓이고, 그 기록(어느 부서가 무엇을 반복해 묻고 `no_tool` 로 끝나는가)이 다음 에이전트 후보를 알려 준다. 반대 방향(에이전트에서 시작해 챗봇으로 내리기)은 담당자 비용이 먼저 든다.

## 4. 구조안 3가지 — 무엇을 고를 것인가

| | **A안 분리 운영**(현상 고착) | **B안 공통 에이전트 + 선택·핸드오프**(권고) | **C안 자동 라우팅**(오케스트레이터) |
|---|---|---|---|
| 모양 | 챗봇과 에이전트를 별 제품으로. 게이트웨이 2개 유지 | 게이트웨이 하나(ADR-109). 챗봇 = `common` 프로필. 챗 화면 상단 「에이전트 ▾」(내가 쓸 수 있는 것만) + 「이어서 묻기」 카드. 부서 전용 페이지는 유지 | 챗봇이 질문을 분류 → 부서 에이전트를 자동 호출 → 답을 합성 |
| 사용자 경험 | "어디서 물어야 하지"가 계속 남는다 | 한 창에서 시작, 깊은 질문은 클릭 1회로 전환. 전환 뒤엔 그 에이전트의 칩·용어·도구 | 한 창에서 끝. 단, 분류가 틀리면 **오답이 조용히** 나간다 |
| 관리 | 관리 탭 2곳 · 모델 벤더 갈림 · 도구 코드 중복 위험 | `/admin/agents` 에 공통 프로필 포함 → **한 곳** | B + 라우터(분류 규칙·골든셋) 관리가 하나 더 |
| 권한·책임 귀속 | 명확(아예 다른 제품) | **사용자의 선택 = 책임 경계**. 턴은 `agent_key` 로 귀속 | 흐림 — 어느 담당자의 개선 대장으로 가나? |
| 비용 귀속 | 명확 | `agent_key` 별 집계 · 예산 그대로 | 라우터 호출 + 에이전트 호출 = 요청당 2회, 귀속 규칙 추가 필요 |
| 권한 판정 | `perm_effective` 하나(같음) | 같음 | 같음 — 단 합성 단계에서 권한 밖 결과가 섞일 틈이 생긴다 |
| 구현 | 없음 | 13 기획 P0~P1(모듈·흡수) + 화면 선택 UI + `my_agents` op + 핸드오프 카드 | B + 분류기 + 합성 규칙 + 지연 2배 |
| 되돌리기 | — | 선택 UI 를 숨기면 A 와 같다 | 라우터 끄면 B |
| 위험 | 전사 챗봇은 영원히 Claude·첨부·NAS 를 못 쓴다 · 중복이 자란다(13 기획이 해소하려던 문제의 재발) | 사용자가 한 번은 골라야 한다 · 흡수 작업의 동일성 확인 비용 | 분류 오류 · 책임 불명 · 토큰 2배 · 디버깅 어려움 |
| 판정 | ✗ | **✓ 지금 채택** | △ B 의 지표(§12)가 쌓인 뒤 조건부 |

**왜 B 인가** — 관리자의 직관("에이전트는 따로, 필요할 때 챗봇에서 적용")을 그대로 담으면서 기존 결정(ADR-108 모듈 · 109 프로필 · 010 권한 · 011 요청 카드)과 **충돌하는 것이 하나도 없다.** 새 뷰 타입도, 새 권한 판정도 필요 없다. 그리고 되돌리기가 가장 싸다.
C 는 "한 창에서 다 된다"는 매력이 있지만, 지금 가장 약한 고리는 **분류 정확도가 아니라 부서 지식과 담당자 루프**다(09-30·10-06 실측의 오답은 전부 용어·조건·잘림 문제였다). 분류기를 먼저 만들면 틀린 답이 더 빨리 전달될 뿐이다.

## 5. B안 상세 — 어떻게 보이고 어떻게 도나

### 5-1. 화면

```
┌ 사내 AI 포털 · jeil-chat ──────────────────────────────────────────────────────┐
│ 에이전트: [ 공통 ▾ ]   ← 내가 쓸 수 있는 것만: 공통 · 구매 에이전트 · (DRI)      │
│ ─────────────────────────────────────────────────────────────────────────────  │
│ 나) PU 결재 건 발주 났어?                                                       │
│ AI) [notice 카드] 결재번호(PU)로 발주 여부를 추적하는 일은 구매 에이전트가 맡습니다.│
│     ▸ 구매 에이전트로 이어서 묻기   ▸ 구매팀 운영페이지 열기                        │
│     (구성원이 아니면: ▸ 권한 요청 — ADR-011 요청 카드와 같은 자리)                   │
│ ─────────────────────────────────────────────────────────────────────────────  │
│ [에이전트: 구매 ▾] 로 바뀌면 → 칩 9개 · 용어집 · 도구 묶음 · 모델 · 기록 귀속이 바뀐다 │
└──────────────────────────────────────────────────────────────────────────────┘
      부서 카드 /work/purchase-agent 는 그대로 — 첨부·자료함·NAS 보관함·🧪 검증 탭 같은 작업형은 여기
```

- **선택 목록은 서버가 준다**(`my_agents` op): 상태 `live` 이거나 내가 구성원인 `pilot` 에이전트만. 목록에 없으면 고를 수 없고, 고른 척 보내도 서버가 거부한다(지금 구매 에이전트 화면과 같은 판정).
- **공통 프로필은 항상 있다.** 선택을 안 하면 공통이다.
- **부서 전용 페이지는 없애지 않는다.** 챗봇 안의 에이전트 전환은 "대화형 질의"까지이고, 첨부·자료함·NAS 보관함·검증 탭처럼 화면 요소가 필요한 작업형은 전용 페이지가 맡는다. 두 입구가 **같은 프로필·같은 기록**을 쓰므로 어디서 물어도 담당자에게는 하나로 보인다.
- Teams 앱 진입(실구축 02 기획)이 생기면 그 입구는 **공통 프로필**이 맡는다 — 부서 에이전트는 포털 카드로.

### 5-2. 요청 한 번의 흐름(목표 상태)

```
[포털 챗 /main]  body.agent = "common" | "purchase" | …   ─┐
[부서 페이지]    body.agent = "purchase"                   ─┤→ 공용 게이트웨이(jeil-chat-lab → 운영 승격 시 jeil-agent)
                                                            │   1) 인증 → perm_effective 1회(ADR-010)
                                                            │   2) 프로필 로드(ai_agent · 현재 버전) — common 도 같은 표의 한 행
                                                            │   3) 쓸 도구 = 프로필의 도메인 묶음 ∩ 등록부 enabled ∩ 사용자 권한(gate)
                                                            │   4) 프롬프트 = 공통 머리말 + 역할 안내 + 답변 원칙 + 용어집 + 모듈 prompt_hint
                                                            │   5) 모델 호출(버전의 모델·예비) → 도구 실행 전 권한 재판정 → 뷰 5종
                                                            │   6) 기록: agent_key 별 턴·비용 · 핸드오프 카드는 notice + actions
                                                            └→ 중간DB public.v_erp_* · 포털 DB · 사내 NAS(큐) — 전부 읽기 전용
```

### 5-3. "챗봇에서 에이전트를 적용한다"의 정확한 뜻

관리자 문장을 구현 언어로 옮기면 세 가지다.

| 관리자 표현 | 구현에서의 뜻 | 아닌 것 |
|---|---|---|
| "에이전트 관리를 별도 적용" | 에이전트 = `ai_agent` 프로필 + 버전 · `/admin/agents` 에서 담당자·관리자가 관리(지금 그대로) | 부서마다 별도 챗봇 함수·별도 코드(ADR-109 기각안) |
| "필요에 의해서 챗봇에서 에이전트를 적용" | **세션 단위 프로필 전환** — 챗 화면에서 에이전트를 고르면 그 요청부터 `body.agent` 가 바뀐다 | 챗봇 프롬프트에 구매 도구·용어를 **섞어 넣는 것** |
| "기능이 적용되도록" | 전환 순간 바뀌는 것: 칩 · 용어집 · 답변 원칙 · 도구 묶음 · 모델/예비 · 턴 기록 귀속 · 예산 | 바뀌지 않는 것: **권한**(`perm_effective`) · 실거래 금지 · 뷰 5종 · 인증 · 1인 1일 한도의 존재 |

왜 "도구 섞기"가 아닌가 — 09-30 실업무 실측에서 틀린 답 4개 시나리오는 **도구가 없어서가 아니라** 용어(PU↔PO)·조건 재조회·잘림 안내가 없어서였다. 그 셋은 전부 프로필(답변 원칙 R7·R10, 용어집, 골든셋)에 들어 있다. 도구만 챗봇에 옮기면 같은 오답이 전사로 퍼진다. 반대로 프로필째 전환하면 담당자가 고친 것이 그대로 따라온다.

### 5-4. 핸드오프 카드 — 언제, 무엇을 넘기나

| 항목 | 규칙 |
|---|---|
| 뜨는 조건 | ① 공통 프로필에서 `no_tool` 판정 + 질문에 부서 에이전트의 **칩·용어집 낱말**(PU·기안서·DRI …)이 있을 때 ② 권한 밖 도구를 가리키는 질문(지금의 권한 요청 카드 자리) ③ 사용자가 "구매 에이전트에게" 라고 직접 말할 때 |
| 넘기는 것 | **마지막 질문 1개** + 직전 카드의 조회 조건(기간·거래처) — 대화 전체 원문은 넘기지 않는다(ADR-009 · 공통 대화는 본인 것) |
| 자격이 없으면 | 전환 버튼 대신 **권한 요청 카드**(ADR-011 `portal_request`) — 에이전트 구성원 요청도 같은 원장에 접수한다(요청 유형 1개 추가) |
| 뷰 | 새 뷰 타입 없음 — `notice` + `actions.kind = "handoff"`(ADR-011 이 `request` 를 더한 방식과 같다) |
| 기록 | 카드 노출·클릭을 `chat_tool_call`(13 기획 P2) 또는 턴 `flags` 에 남긴다 → §12 지표 |

### 6-4. 중복 금지 5원칙

1. **게이트웨이 1개** — 부서가 늘어도 함수가 늘지 않는다(ADR-109).
2. **모듈 코드 1곳** — 같은 조회를 두 파일로 만들지 않는다(ADR-108). 에이전트는 묶음만 고른다.
3. **권한 판정 1개** — `perm_effective`. 에이전트·챗봇·운영페이지가 같은 답을 받는다(ADR-010).
4. **뷰 5종** — 새 카드가 필요하면 `actions` 를 늘린다(ADR-008).
5. **비용 집계 1곳** — `chat_log` + `agent_key` 로 구분. 두 집계표를 두지 않는다(ADR-111).

## 7. 에이전트 신설 게이트 — "에이전트로 만들 자격"

아래 10개를 **모두** 통과해야 `dev → pilot` 으로 올린다. 하나라도 비면 챗봇(공통)에 도구만 먼저 열고 기록을 쌓는다.

| # | 항목 | 확인 방법 | 없으면 |
|---|---|---|---|
| 1 | **담당자(operator) 2명** 지정 — 실작업 | `/admin/agents` 구성원 탭 | 만들지 않는다 |
| 2 | **관리자(reviewer)** 1명 이상 | 같음 | 만들지 않는다 |
| 3 | 대표 질문 **10개 + 기대 답** | 템플릿 골든셋 초안 | 담당자가 먼저 쓴다 |
| 4 | 필요한 **도구 도메인**이 있나 | `modules/` 목록 · 13 기획 인벤토리 | 모듈 REQ 먼저(코드) |
| 5 | **데이터가 적재**돼 있나(ERP 중간DB 뷰 · NAS 허용 폴더) | `문서/10_ERP_DB연계` · `etl_meta.nas_folder_scope` | ETL·폴더 등록 REQ 먼저 |
| 6 | **민감도** — 급여·인사평가·주민등록 도구를 묶지 않는다 | 도메인 묶음에 `hr`·`personal` 없음 | 범위를 줄인다 |
| 7 | 월 **예산**·1인 1일 한도 | 관리자 결정 | 공통 기본값(12/06 §2-1)으로 시작 |
| 8 | **공개 범위** — pilot 구성원·부서 | `ai_agent.status/pilot_*` | 구성원 등록 |
| 9 | **포털 카드·화면** — 구매 화면 복사 + 라우트 | 12/02 개발가이드 §3 | 전용 페이지 없이 챗봇 선택으로만 시작 가능(2단계 뒤) |
| 10 | **템플릿 세트**(칩·용어·골든셋·시나리오) | `app/agent-templates.json` 부서 키 | `_candidates` 골격 복사 |

> 지금 구매 에이전트는 **1번이 비어 있다**(구성원 1명 — 담당자 2명 미등록, 12/00 §1). 1호가 게이트를 통과하지 못한 채 2호(DRI)가 열렸다. 이 문서의 첫 적용은 **새 에이전트가 아니라 1호의 담당자 등록**이어야 한다.

## 11. 제안 ADR-113 (요지)

- **결정**: 전사 챗봇은 공용 게이트웨이 위의 **공통 에이전트 프로필(`common`)** 이다. 챗봇과 부서 에이전트의 구분은 기술이 아니라 **대상·책임·지식·개선 루프**로 하며(§2), 어디에 속하는지는 **경계 판정 규칙 Q1~Q6**(§3)으로 정한다.
- **결정**: "챗봇에서 에이전트를 적용"은 **세션 단위 프로필 전환**이다. 챗 화면의 에이전트 선택과 핸드오프 카드(`notice` + `actions.handoff`)로 구현하고, 도구를 공통 프롬프트에 섞어 넣지 않는다. 전환 자격(live 또는 구성원)은 서버가 판정한다.
- **결정**: 도구는 공유하고(모듈 1곳) 지식·책임·루프는 부서가 갖는다. 같은 도구·같은 용어를 두 에이전트가 각자 기르지 않는다.
- **결정**: 담당자(operator) 없는 에이전트는 만들지 않는다 — 신설 게이트 10항(§7).
- **대안(기각)**: 부서별 챗봇 분리 운영(A) — 중복이 자란다. **대안(보류)**: 자동 라우팅(C) — 핸드오프 클릭률·분류 정확도가 측정된 뒤 조건부.
- **상태**: Proposed — D-1~D-7 결정 시 Accepted 로 전이.

| 용어 | 뜻 |
|---|---|
