# 14 · 부서 에이전트 운영기획 — "에이전트는 프로필, 대화는 자산"

> 관리자: 최동혁(dh.choi@jeilm.co.kr) · 기준일: 2026-09-28 · 상태: **구현 1차 완료(파일럿 가동) — ADR-109 · 1호 에이전트 = 구매 · §11 구현 현황**
> 관련: [15 챗봇 ↔ 에이전트 역할 구분·적용 가이드](15_챗봇_에이전트_역할구분_적용가이드.md)(공통 에이전트 · 경계 판정 · 프로필 전환 · ADR-113 제안) · [13 챗봇 모듈형](13_챗봇_모듈형_고도화_기획.md)(도구 모듈 규격 · 실험실 `/chatdemo`) · [10 응답렌더링](10_챗봇_응답렌더링_설계.md)(뷰 5종) · [11 요청접수](11_챗봇_데이터요청접수_설계.md) · [08 보안](08_보안_데이터안정성.md) · [09 ADR](09_ADR_의사결정기록.md) · 모델 설정 SSOT `실제구축준비 자료/06_챗봇_사용모델설정_SSOT.md` · `CLAUDE.md §1.6·§1.7·§5.4·§13·§16.6`

사내 여러 부서가 **하나의 AI 게이트웨이를 공용으로 쓰면서**, 부서마다 자기 업무에 맞춘 **에이전트**를 두고,
에이전트별로 **모델·설정을 따로 관리**하며, 대화에서 쌓인 **질문·답변·관련 내용을 DB에 누적해 에이전트를 계속 고도화**하는 체계를 정한다.
1호는 **구매 에이전트**다. 이 문서는 설계와 결정 사항을 모은 것이고, 구현은 §8의 백로그 요청(REQ)으로 나눠 진행한다.

> **비개발자용 한 줄 요약** — 에이전트는 부서마다 새 프로그램을 만드는 게 아니라 **"설정 카드 한 장"** 이다(어떤 모델로, 어떤 자료를, 어떤 말투·규칙으로). 직원은 평소처럼 질문만 하고, 뒤에서는 질문과 답변이 **개선 대장**에 쌓인다. 담당자가 그 대장을 보고 "이런 질문엔 이렇게 답해야 한다"를 고치면 에이전트가 점점 똑똑해진다.

## 0. 결론 먼저

| # | 제안 | 한 줄 이유 |
|---|---|---|
| 1 | **에이전트 = 프로필**(`ai_agent`): 역할 안내 + 모듈 묶음 + 모델·설정 + 공개 범위 + 담당자 | 게이트웨이·권한 판정·화면 뷰는 공유하고, 부서 차이는 설정으로만 만든다 |
| 2 | **에이전트별 모델·설정은 관리자 페이지 `/admin/agents`에서** — 변경은 **버전**으로 남긴다 | "언제 무엇을 바꿨더니 답이 좋아졌나"를 추적하려면 답변마다 버전이 붙어야 한다 |
| 3 | **구매 에이전트 페이지 `/work/purchase-agent`** — 대화 + 생성 자료함, 구매 데이터 **12종 전부 연결** | 기존 도구 7종에 발주통합 LIST·기안서 대장·대사·거래처 프로필을 더한다 |
| 4 | **자료 생성은 "숫자는 서버, 문장은 모델"** | 표·합계는 조회 결과로 서버가 만들고, 모델은 해설만 쓴다 — 없는 숫자를 지어내지 않는다(§16.6) |
| 5 | **질의·응답 누적 DB**(`agent_turn`) + **개선 대장**(`agent_improve`) + **골든셋**(`agent_golden`) | 사용자는 대화만 보고, 담당자는 개선 대장을 백로그처럼 운영한다 |
| 6 | **바꾸기 전에 골든셋으로 회귀 시험** | 모델·프롬프트를 바꿀 때마다 "예전에 맞던 질문이 여전히 맞는가"를 자동으로 확인한다 |
| 7 | **Claude(Sonnet 5)는 회사 명의 API 키로** — 개인 구독 사용 불가 | 구독과 API는 별개 상품. 관리자가 키를 새로 발급해 Supabase 시크릿에 등록한다 |
| 8 | 챗봇이 하는 일은 여전히 **조회·초안·접수**까지(13 기획 범위) | 발주 확정·결재·발송은 사람이 누른다(CLAUDE.md §1.6) |

## 1. 전체 구조

```
 [직원]                      [관리자·에이전트 담당자]
   │ 대화                        │ 설정·개선
   ▼                             ▼
 구매 에이전트 페이지          /admin/agents  (에이전트 목록 · 모델·설정 · 버전 · 개선 대장 · 골든셋)
 /work/purchase-agent              │
   │                               │ ai_agent / ai_agent_version
   ▼                               ▼
 ┌──────────────── 공용 게이트웨이 (jeil-chat-lab → 검증 후 jeil-agent) ─────────────────┐
 │ 1) agent_key 로 프로필 로드 (모델·추론강도·프롬프트 버전·모듈 묶음)                      │
 │ 2) 권한 판정 perm_effective (ADR-010) → 모듈 묶음 ∩ 사용자 권한 = 이번에 쓸 도구         │
 │ 3) 프롬프트 조립 = 공통 머리말 + 에이전트 역할 안내 + 용어집 + 모듈 prompt_hint          │
 │ 4) LLM 어댑터 (openai.ts · anthropic.ts) 로 호출 → 도구 실행 → 뷰 5종으로 응답           │
 │ 5) 턴 기록 agent_turn (질문·답변·도구·건수·모델·버전·비용·지연) → 개선 대장 자동 후보    │
 └──────────────────────────────────────────────────────────────────────────────────────┘
   │ 읽기 전용                                  │ 생성 자료
   ▼                                            ▼
 중간DB public.v_erp_* · pur_proposal*       agent_artifact + Storage(agent-artifacts)
```

- **게이트웨이는 하나다.** 부서가 늘어도 코드가 늘지 않는다. 부서 차이는 `ai_agent` 행과 모듈 묶음뿐이다.
- 지금 가동 중인 실험실 `jeil-chat-lab`(REQ-0084)이 이 게이트웨이의 시험판이다. 검증 후 운영 이름(`jeil-agent`)으로 올리고, 운영 `jeil-chat`은 "공통 에이전트"로 흡수한다(별건).

## 2. 에이전트 프로필 — `ai_agent` · `ai_agent_version`

### 2-1. 프로필에 담는 것

| 구분 | 항목 | 예(구매) |
|---|---|---|
| 정체 | `agent_key` · 이름 · 설명 · 아이콘 · 담당 부서 · **담당자**(내용 검수 책임) | `purchase` · 구매 에이전트 · 구매팀 · 구매팀 담당자A |
| 공개 범위 | 상태 `dev / pilot / live / off` · 파일럿 사용자·부서 · 노출 페이지 | pilot · 구매팀 3명 |
| 모델 | 기본 모델 · 폴백 모델 · 추론강도(effort) · 최대 출력 토큰 · 캐싱 on/off | `claude-sonnet-5` · 폴백 `gpt-4.1-mini` · effort `medium` |
| 프롬프트 | 역할 안내 · 답변 원칙 · 금지선 · 용어집 참조 | "구매팀 실무자처럼, 금액은 원 단위 콤마…" |
| 도구 | 모듈 묶음(도메인 + 개별 on/off) | purchase 12종 + common 2종 + docs 2종 |
| 한도 | 1인 일일 질문 수 · 월 예산(USD) · 1회 도구 호출 상한 | 50회/일 · $150/월 · 6회 |
| 수집 | 턴 기록 on/off · 보존 기간 | on · 180일 |

**설정은 벤더에 따라 달라지는 항목이 있다.** 예) Claude Sonnet 5 는 `temperature` 를 받지 않고(보내면 400 오류) 추론강도(effort)로 조절한다. 관리자 화면은 선택한 모델의 벤더에 맞는 항목만 보여 준다.

### 2-2. 버전 관리 — 왜 필요한가

프롬프트·모델을 바꾸면 **답이 바뀐다.** 버전 없이 덮어쓰면 "지난주엔 맞게 답하던 질문이 왜 틀리지?"를 추적할 수 없다.

- 설정을 저장하면 `ai_agent_version` 에 **새 버전 행**이 생긴다(v1, v2, …). 되돌리기 = 예전 버전을 "현재"로 지정.
- 모든 대화 턴(`agent_turn`)은 **그 답을 만든 버전 번호**를 함께 저장한다 → 버전별 만족도·오류율 비교가 가능해진다.
- 새 버전은 먼저 **골든셋 회귀(§5-4)** 를 통과해야 "현재"로 지정할 수 있다(관리자가 결과를 보고 승인).

### 2-3. 테이블(안)

`ai_agent` — 에이전트 1개당 1행(정체·공개 범위·현재 버전 포인터)

| 컬럼 | 설명 |
|---|---|
| `agent_key` PK | `purchase`, `sales`, `finance` … (영구 불변) |
| `name_ko` · `summary_ko` · `icon` | 표시용 |
| `dept_nm` · `owner_upn` | 담당 부서 · 내용 검수 담당자 |
| `status` | `dev` / `pilot` / `live` / `off` |
| `pilot_upns[]` · `pilot_depts[]` | pilot 일 때 쓸 수 있는 사람·부서 |
| `current_version` | 지금 쓰는 버전 번호 |
| `daily_limit` · `monthly_budget_usd` · `collect_turns` · `retention_days` | 한도·수집 |

`ai_agent_version` — 설정 이력(저장할 때마다 1행, 수정 불가)

| 컬럼 | 설명 |
|---|---|
| `agent_key` · `version` PK | |
| `model_id` · `fallback_model_id` · `effort` · `max_tokens` · `temperature`(벤더 허용 시) · `prompt_caching` | 모델 설정 — `ai_model`(카탈로그) 참조 |
| `role_prompt` · `answer_rules` | 역할 안내·답변 원칙 |
| `modules` jsonb | `{"include_domains":["purchase","common"],"on":[…],"off":[…]}` |
| `golden_pass` · `golden_total` · `golden_run_at` | 회귀 결과 |
| `created_by` · `created_at` · `note` | 누가 왜 바꿨나 |

- 기존 `ai_gateway_config`(전역 기본값)·`ai_model`(모델 카탈로그)·`ai_routing_rule` 은 **그대로 둔다.** 에이전트에 값이 없으면 전역 기본값을 따른다.
- RLS: 읽기·쓰기 모두 **포털 관리자 + 해당 에이전트 담당자**. 게이트웨이는 service_role 로 읽는다.

   시험 : 「실험실에서 이 설정으로 대화」 → /chatdemo?agent=purchase&version=4(초안)

|---|---|
| 설정 | 모델·폴백·추론강도·토큰·캐싱·역할 안내·답변 원칙·한도. 저장 = 새 버전(초안) |

| 개선 대장 | §5 — 자동 후보 + 사용자 피드백을 백로그처럼 분류·처리 |
| 골든셋 | §5-4 — 대표 질문과 기대 답 요건. 새 버전 회귀 실행 |
| 버전 | 이력·차이·회귀 결과·현재 지정·되돌리기 |
| 사용량 | 질문 수·사용자 수·토큰·비용·지연·도구 오류율·👍율 (버전별) |

- 모델 목록은 `ai_model` 에서 **active + callable + 어댑터가 있는 벤더**만 보여 준다(실험실 `usableModels` 와 같은 규칙).
- 관리자 화면의 편집 표는 **표준 그리드**(§13)를 쓴다.

- 자세한 추적(도구·인자·토큰)은 **사용자에게 보이지 않는다.** 사용자에게는 답변·카드·자료·👍👎만 보인다.
- 구매 운영페이지들(발주통합 LIST 등)에는 나중에 **"에이전트에게 묻기" 버튼**을 달아, 지금 보고 있는 조회조건을 대화 맥락으로 넘긴다(2단계).

### 4-2. 연결할 구매 데이터 — 12종 (지금 연결돼 있는 자료 전부)

| 12 | **거래처 프로필**(발주·매입·납기 준수·미입고 한 장) | 1·5·9 조합 | `get_vendor_profile` | **신규** |

- 공통으로 품목 마스터(`get_erp_item`)·재고(`get_erp_inventory_status`)·내 권한(`get_my_access`)·문서 검색(`search_my_documents`)을 함께 묶는다.
- 권한은 지금처럼 **ERP 모듈 권한(`pur_order` 등)으로 서버가 판정**한다. 구매 에이전트를 열었다고 권한이 넓어지지 않는다(§5.4).
- 신규 5종은 13 기획 규격(`manifest` + `run`, 뷰 5종)을 따른다. 발주통합 LIST 는 행이 많으므로 **조건 필수 + 상한 200행**, 모델에는 요약·상위만 넘긴다.

### 4-3. 자료 만들기 — "숫자는 서버, 문장은 모델"

| 자료 | 만드는 법 | 형식 |
|---|---|---|
| 조회 결과 내보내기 | 직전 도구 결과를 서버가 그대로 표로 | CSV(UTF-8 BOM, §13.5) |
| 주간·월간 구매 보고서 | 도구 결과로 서버가 표·합계를 채우고, 모델은 **해설·특이사항 문단만** 작성 | HTML(인쇄·PDF 저장) + CSV 첨부 |
| 거래처 비교표 | 거래처 N곳 프로필을 서버가 나란히 | HTML + CSV |
| 기안서 미연결·대사 이상 목록 | 대사 RPC 결과 | CSV |
| 품의·검토 메모 **초안** | 모델이 초안 작성 → 사용자가 수정·복사 | 텍스트(초안 표시) |

- 생성 자료는 `agent_artifact` 에 기록하고 파일은 Storage `agent-artifacts/<upn>/…` 에 둔다. **본인만** 보고, 30일 후 자동 삭제(보관이 필요하면 내려받기).
- 자료 안의 모든 숫자에는 **기준시각과 원천 도구**를 각주로 단다. 모델이 쓴 문단 안의 숫자는 서버가 도구 결과와 대조해, 없는 값이면 경고 표시한다.
- 엑셀(.xlsx)·워드(.docx) 원본 생성은 2단계. 1단계는 CSV + HTML(인쇄)로 충분하다(외부 라이브러리 없이 가능).
- **발주 요청·기안 상신 같은 실거래는 하지 않는다.** 초안까지만 만들고 확정은 ERP·그룹웨어에서 사람이 한다(§1.6).

## 5. 질의·응답 누적과 고도화 — "대화는 자산"

사용자는 평소처럼 묻고 답을 받는다. 뒤에서는 턴마다 기록이 쌓이고, 그중 **고칠 거리**가 개선 대장으로 올라가며,
담당자가 이를 **백로그처럼** 처리한다. 고친 결과는 버전으로 남고 골든셋으로 검증된다.

```
 대화 1턴 ─▶ agent_turn (기록) ─▶ 자동 판정 ─▶ agent_improve (개선 대장)
                                   │  👎 · 도구 오류 · 0건 · 권한 차단 · "모르겠다" · 도구 없음
                                   ▼
              담당자 분류: 프롬프트 / 용어집 / 신규 모듈 / 데이터 누락(ETL) / 정답 예시 / 해당 없음
                                   ▼
              반영: 새 버전(v+1) · 용어집 추가 · REQ 등록(모듈·ETL)  ──▶ 골든셋 회귀 ──▶ 현재 버전 지정
                                   ▼
              좋은 답변은 agent_golden(골든셋)으로 승격 → 다음 변경의 시험 문항이 된다
```

### 5-1. `agent_turn` — 턴 기록(사용자는 보지 않음)

| 컬럼 | 설명 |
|---|---|
| `id` · `agent_key` · `agent_version` · `upn` · `dept_nm` · `created_at` | 누가·어느 에이전트·어느 버전 |
| `question` | 질문 원문 |
| `answer` | 최종 답변 텍스트(뷰 JSON 은 요약만) |
| `tools` jsonb | 호출한 도구·인자·건수·결과 유형(정상/0건/권한차단/오류)·ms — 결과 **행 데이터는 저장하지 않는다** |
| `model` · `prompt_tokens` · `completion_tokens` · `cache_read_tokens` · `est_cost_usd` · `latency_ms` | 비용·성능 |
| `rating` · `rating_note` | 👍/👎 + 사용자가 남긴 한 줄(선택) |
| `flags[]` | 자동 판정 결과: `tool_error`, `zero_rows`, `perm_denied`, `no_tool`, `refusal`, `slow`, `thumbs_down` |
| `chat_log_id` | 기존 비용 집계(`chat_log`)와 연결 |

- **민감값 최소화**: 도구 결과 행(금액 목록 등)은 저장하지 않고 **건수·결과 유형만** 남긴다. 답변 텍스트에는 금액이 들어갈 수 있으므로 열람은 관리자·담당자로 제한한다(RLS).
- **인사·급여 도구 결과가 들어간 턴은 질문만 남기고 답변은 저장하지 않는다**(§1.7). 구매 에이전트는 인사 도구를 묶지 않는다.
- 보존: 기본 180일, 골든셋·개선 대장으로 승격된 건은 그 항목이 보존한다.
- 기존 대화내역 저장(`chat_session`/`chat_message`, 사용자 opt-in · ADR-009)과는 **목적이 다르다** — 저것은 사용자 본인의 이어보기용, 이것은 품질 개선용. 둘을 섞지 않는다.

### 5-2. `agent_improve` — 개선 대장(백로그 형태)

| 컬럼 | 설명 |
|---|---|
| `id`(IMP-0001…) · `agent_key` · `status` | `inbox` → `triage` → `planned` → `applied` → `verified` / `wontfix` |
| `source` | `auto`(자동 판정) · `thumbs_down` · `owner`(담당자가 직접) |
| `turn_ids[]` | 근거 턴(비슷한 질문 묶음) |
| `category` | `prompt` · `glossary` · `new_module` · `data_gap`(ETL) · `golden` · `model` · `none` |
| `summary` · `proposal` | 무엇이 문제고 어떻게 고칠지 |
| `applied_version` · `req_id` | 반영한 버전, 또는 코드·ETL 변경이면 백로그 REQ 번호 |
| `owner_upn` · `created_at` · `resolved_at` | |

- **비슷한 질문 묶기**: 야간에 저렴한 모델(예: `claude-haiku-4-5`)로 inbox 후보를 주제별로 묶고 분류 초안을 단다 → 담당자는 **묶음 단위로** 판단한다. 수백 건을 하나씩 볼 필요가 없다.
- **자주 나왔는데 도구가 없던 질문**(`no_tool`)은 신규 모듈 후보가 된다 → 코드 변경이므로 백로그 REQ 로 연결한다.
- 관리자 화면에서 개선 대장은 **표준 그리드**로, 상태 전이는 버튼으로 한다.

### 5-3. `agent_glossary` — 용어집

구매팀이 쓰는 말과 ERP 용어를 잇는다. 예) "가발주", "PU번호 = 결재번호(`M_PUR_REQ.EXT1_CD`)", "입고대기 = 발주 후 미입고".
활성 용어는 프롬프트에 자동으로 들어간다(에이전트별). 개선 대장의 `glossary` 항목을 반영하는 자리다.

### 5-4. `agent_golden` — 골든셋(회귀 시험 문항)

| 컬럼 | 설명 |
|---|---|
| `id` · `agent_key` · `question` | 대표 질문 |
| `expect_tools[]` | 불러야 할 도구(예: `get_erp_pur_top`) |
| `expect_rules` | 답이 지켜야 할 요건(예: "발주번호별 총액 기준", "상위 5건", "원 단위") |
| `source_turn_id` · `active` | 어느 대화에서 승격됐나 |

- 새 버전 저장 → **「회귀 실행」**: 골든셋 전 문항을 새 설정으로 돌려 ① 기대 도구를 불렀는가 ② 요건을 지켰는가(저렴한 모델이 채점) ③ 비용·지연을 비교한다.
- 결과는 `ai_agent_version.golden_*` 에 남고, **통과율이 이전보다 떨어지면 "현재" 지정 전에 경고**한다.
- 회귀도 API 비용이 든다 — 문항 30개 기준 1회 약 $1~2(§7). 실행은 버튼으로만(자동 반복 없음).

## 10. 제안 ADR-109 (요지)

- **결정**: 부서 에이전트는 공용 게이트웨이 위의 **프로필(설정 + 모듈 묶음 + 버전)** 로 만든다. 부서별 별도 게이트웨이·별도 코드베이스를 만들지 않는다.
- **결정**: 대화 턴은 품질 개선용으로 별도 기록(`agent_turn`)하고, 개선은 **개선 대장 → 버전 → 골든셋 회귀**의 순서로만 반영한다.
- **결정**: 생성 자료의 숫자는 서버가 도구 결과로 채우고, 모델은 서술만 한다.
- **대안(기각)**: 부서마다 별도 챗봇 함수 — 권한·렌더링·비용 집계가 부서 수만큼 복제되어 어긋난다(13 기획이 해소하려는 문제의 재발).
- **상태**: Proposed — P1 착수 시 Accepted 로 전이.
