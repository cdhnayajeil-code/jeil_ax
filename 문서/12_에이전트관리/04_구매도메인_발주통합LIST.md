> 구매 에이전트가 **반드시 알아야 하는** 번호 체계와 발주통합 LIST 의 데이터 구조. 수치는 2026-09-29 중간DB 실측(`public.v_erp_pur_list`, 2026-01-06 ~ 09-25).
> 정본: 뷰 정의 `실제구축준비 자료/이관/sql/72_erp_pur_list_v4.sql` · 화면 `/work/purchase-list`(`pages/구매_발주통합LIST_2026.html`).

|---|---|---|---|---|---|

## 2. 흐름과 관계

```
 요청자                    결재(그룹웨어)                구매팀                     창고            회계
 PR 1줄 ─┐
 PR 1줄 ─┼──▶ PU 1건(평균 4.7줄 · 최대 111줄) ──▶ PO 1건(최대 134줄) ──▶ 입고(GR) ──▶ 매입(IV·송장)
 PR 1줄 ─┘                                   └▶ PO 여러 건(PR 1줄이 최대 3건으로 분할)
```

| 관계 | 실측 | 뜻 |
|---|---|---|
| PU → PR | 평균 4.7 · 최대 111 | 결재 1건에 요청 품목 여러 줄 |
| PO → PR | 최대 134 | 발주서 1건에 요청 여러 줄 |
| PR → PO | 최대 3 (분할 7줄) | 요청 1줄이 여러 발주로 나뉘는 경우가 드물게 있다 |
| PU → PO | 평균 1.33 · 최대 12 | 결재 1건이 발주 여러 건으로 |
| PO → PU | 최대 8 (176개 발주가 2건 이상) | 발주 1건이 여러 결재의 요청을 묶는다 |
| 결재번호 없는 줄 | 310줄(발주 라인 52 · 미발주 258) | 요청의 결재번호 칸이 비어 있다 |

**핵심: PU 와 PO 는 묶는 기준이 달라 1:1 이 아니다.** "결재 1건 = 발주 1건"이라고 답하면 틀린다.

## 3. 발주통합 LIST — 한 줄의 의미

- **한 줄 = 발주 라인**(PO+순번). 발주가 아직 안 난 요청은 **요청 1줄**(구분 PR, 상태 「미발주」).
- 전체 5,673줄 = 발주 라인 4,660 + 미발주 요청 1,013.

| 상태(화면) | 뜻 | 줄 수 | ERP 진행코드 |
|---|---|---|---|
| 미발주 | 발주 전 요청 | 1,013 | RQ(요청)·CF(확정) |
| 발주 | 발주 완료 · 입고 전 | 1,298 | PO |
| 부분입고 | 일부만 입고 | 0 | — |
| 입고완료 | 입고수량 ≥ 발주수량 | 167 | GR |
| 매입완료 | 송장까지 | 3,195 | IV |

> **2026-10-07 부터 상태·입고수량·미입고·납기경과는 실적 판정이다**(정본 SQL 91 · REQ-0110): 발주 사본의 진행코드·입고수량이 증분 적재에서 갱신되지 않아 끝난 발주가 「발주·미입고」로 나오던 것을, 입고·매입 사본으로 판정하는 `v_erp_pur_line_status` 로 바꿨다. 위 표의 줄 수는 09-29 실측이라 지금과 다르다(적용 당일 「발주」 1,123 · 「입고완료」 76 · 「매입완료」 3,671). 원값은 `po_sts_raw`·`rcpt_qty_raw`.

## 4. 에이전트가 이것을 아는 방법(3곳)

| 어디 | 무엇 | 반영 |
|---|---|---|
| **도구** `search_pur_list` v1.1 | `pr`·`pu`·`po` 번호로 조회하면 **연결된 PR·PU·PO 목록과 해석 문장**(예: "발주 PO… 에 구매요청 4줄, 결재번호 3건 — 여러 결재의 요청을 한 발주로 묶음")을 돌려준다. 번호를 키워드에 넣어도 알아본다. 목록 카드에 PR·PU·PO 세 열 | 코드(배포 v5) |
| **공통 프롬프트** 구매 도메인 문장 | 번호 형식에 PU 추가 · "PU 는 get_erp_po_pr 에 넣지 말 것" | 코드(`core/prompt.ts`) |
| **용어집** 10개 | PR · PU · PO · 관계 · 발주통합 LIST · 상태 · 입고요청일/발주납기 · 입고일/매입일 · 구분 · P-CODE/건명/도번 | DB — **즉시**(버전 불필요). 관리 화면 「용어집」 탭에서 고친다 |

도구 고르는 기준(모델에게 준 규칙)
- PU 번호 · 번호끼리의 연결 · 조건으로 여러 줄 → `search_pur_list`
- PO 한 건 · PR 한 줄의 단계별 상세(요청→확정→발주→입고→매입 수량) → `get_erp_po_pr`
- 금액 상위 → `get_erp_pur_top` · 품목 이력 → `get_erp_item_orders` · 거래처 요약 → `get_vendor_profile`

## 6. 기안서 ↔ 스캔본 ↔ 전표 ↔ 발주 연결(REQ-0092 · 2026-09-29)

기안서 대장(구매팀 Teams 엑셀, 830건)은 ERP 밖 자료라 발주번호 칸이 없다. 아래처럼 잇는다.

```
기안서(권-번호 9-830) ─┬─ 스캔본  문서중앙화 「권-번호.pdf」 — 파일명·존재 여부만(내용 미열람) · 매일 밤 자동 갱신
                       ├─ 전표    대장 선급·중도·잔금 칸의 TG(결의)·IV(매입) → ERP 전표(GL)·금액 대사 등급(REQ-0081)
                       │    └─ 세금계산서  국세청 승인번호·공급가·세액(REQ-0082)
                       └─ 발주    ① 확정: 전표 → 매입(IV) → 발주(PO)   ② 추정: JOB번호=P-CODE + 거래처 + 금액(공급가 ±2%)
                                  └─ 결재(PU) · 구매요청(PR) · 진행상태(발주통합 LIST)
```

| 연결 | 실측(830건) | 비고 |
|---|---|---|
| 스캔본 있음 | **821** · 없음 9 · 대장에 없는 스캔 17(9-831~ — 대장 적재가 09-22 이후 멈춤) | 파일명 규칙 「권-번호.pdf」 838개 전부 인식 |
| 전표번호 ERP 확인 | TG 818 중 785(96%) | 대사 등급은 기안서 대장 화면과 같다 |
| 발주 확정(전표 경유) | **479건** | 한 매입(IV)이 여러 발주를 묶어 기안 1건 → 발주 여러 건이 흔하다(평균 4.5) |
| 발주 추정 | 189건(프로젝트·거래처·금액 164 · 프로젝트·거래처 25) | 확정과 둘 다 되는 351건 중 345건(**98.3%**)이 같은 발주 — 추정도 믿을 만하다 |
| **합계** | **668건(80%)** | 나머지 162건은 전표 미기재·거래처명 불일치·후보 여럿 — 사람이 확인 |

- 정본: 뷰 `v_pur_proposal_po_link`(SQL 76 — 확정이 있으면 추정을 덧붙이지 않는다) · 대사 상세 래퍼 `agent_proposal_recon_detail(upn, 권, 번호)`.
- 도구 `get_proposal_chain`: 권-번호 또는 PO·PU·PR 번호로 한 장 카드(기안 → 스캔본 → 전표 → 세금계산서 → 발주 단계 표시 + 결재·요청·진행). 추정 연결은 "추정"이라고 밝히게 했다.
- `get_pur_proposal` v1.1: 목록에 스캔본 **파일명** 표시.
- ERP 전표에는 첨부파일이 없다(대사 대상 833장 모두 0) — 증빙 원본은 문서중앙화 스캔본뿐이다.

### 스캔 목록 야간 자동 갱신
- 모듈 `10_ERP_DB연계/etl/proposal_scan.py`(러너 서브커맨드 `jeil_runner scan` · 작업 종류 `proposal_scan`). 문서중앙화 드라이브는 **로그인된(잠기지 않은) PC 의 탐색기 창**에만 열리므로, 탐색기 창을 띄워 파일 **이름·크기·수정일만** 읽는다(복사·열람 없음).
- 이 PC 에 예약작업 **`JEIL_AX_ProposalScan`**(일반 권한 · 로그인 시에만 · 30분 간격, 등록 스크립트 `etl/deploy/register_scan_task.ps1`). 모듈이 스스로 **밤 20시 이후 첫 가능 회차에 1회** 갱신하고, 잠겨 있었으면 다음 날 아침 첫 회차에 따라잡는다. 로그 `logs/proposal_scan.log`.
- 안전장치: 파일 0개이거나 「스캔 있음」이 종전의 절반 미만이면 적재하지 않는다(부분 열람으로 전부 「없음」이 되는 사고 방지).
- ERP 서버 러너는 Destiny 가 없어 이 작업을 하지 않는다(능력 판정 `proposal_scan=False`).

## 7. 주의
- 중간DB 는 **2026-01 이후** 자료다. 그 전 번호는 "없음"이 정상일 수 있다.
- 결재번호(PU)가 빈 줄이 310줄 있다 — "결재 안 됨"이 아니라 **요청에 결재번호가 기입되지 않은 것**일 수 있다. 단정하지 않는다.
- 「부분입고」는 정의만 있고 현재 0줄이다(분할 입고가 곧 완료되거나 매입으로 넘어가서).
- 기안서 대장 자체는 Teams 엑셀 적재(`proposal_ledger`)가 09-22 이후 돌지 않아 9-831 이후 기안이 없다 — 스캔본은 있어도 "대장에 없음"으로 나온다(적재 작업 활성화 필요).
- 금액은 발주 라인 금액 합이다. 매입(송장) 금액과 합산·혼동하지 않는다(매입 집계는 `get_vendor_purchase`·`get_erp_purchase_monthly`).
