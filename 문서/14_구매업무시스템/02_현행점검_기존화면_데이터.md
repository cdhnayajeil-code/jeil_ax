# 02 현행 점검 — 기존 화면과 데이터가 8단계의 무엇을 덮고 있나

> 기준 2026-10-06 · 관리 최동혁 · 프로세스 정본은 [01 구매업무 프로세스 도식](01_구매업무_프로세스_도식.html), 만들 것은 [03 구매업무시스템 기획](03_구매업무시스템_기획.html)<br>
> 원천: 화면 5종의 코드와 정본 SQL, 중간DB 집계(2026년분 · 10-06 02시 적재), 구매팀 엑셀 2종, 실제 한 건 추적(비공개 보관)<br>
> 이 문서에는 실제 거래처·금액·문서번호를 적지 않는다. 수치는 전체 합계다.

## 1. 결론 먼저

1. **ERP 데이터는 이미 끝까지 이어져 있다.** 요청 → 발주 → 입고 → 매입 → 결의전표 → 부가세 → 국세청 세금계산서가 중간DB 에 다 있고, 실제 한 건으로 처음부터 끝까지 따라가 확인했다.
2. **화면은 조회 조각 다섯 개다.** 발주통합 LIST, 기안서 대장, 진행현황, 거래처별 매입, 구매 에이전트. 모두 읽기 전용이고 서로 이어지지 않는다. 구매팀이 무언가를 적을 수 있는 곳은 없다.
3. **비어 있는 곳은 사람이 일하는 바로 그 자리다.** 견적·NEGO·업체 선정(3·4단계), 결재가 끝났는지와 그 날짜, 계산서 발행요청(6단계 뒷부분).
4. **고칠 것이 나왔다.** 발주통합 LIST 가 전량 입고된 발주 51건(182줄 — 그중 177줄은 매입까지 끝남)을 「미입고」로 보여 줬다(결함 ① — **2026-10-07 수정 적용**, 아래 §4). 기안서 대장 적재는 9월 22일 이후 멈춰 있다(결함 ② — 이미 알려진 대기 항목).

## 4. 점검에서 나온 것

### 결함 ① 발주통합 LIST 가 끝난 발주를 「미입고」로 보여 준다

- **증상** — 전량 입고된(대부분 매입까지 끝난) 발주가 화면에서는 상태 「발주」, 미입고·납기경과 표시가 켜진 채로 나온다.
- **규모** — 전량 입고됐는데 「미입고」로 나오는 줄이 **182줄 · 발주 51건**이다(입고일 9월 1일~10월 1일). 그중 177줄은 매입까지 끝났고 5줄은 입고만 끝났다. 화면에 「납기경과 미입고」로 나오는 발주 줄 1,616줄 가운데 174줄(11%)이 실제로는 입고된 줄이다.
- **원인** — 뷰 `v_erp_pur_list` 가 상태·미입고·납기경과를 발주 사본의 입고수량(`pur_order_s.rcpt_qty`)과 진행코드(`po_sts`)로 정한다. 그런데 발주 사본은 밤마다 「발주 머리의 수정일」 기준으로 바뀐 것만 가져오고, 입고가 등록돼도 그 수정일은 바뀌지 않는다. 그래서 입고 뒤에도 발주 사본의 입고수량이 0 으로 남는다. 같은 뷰에 있는 실입고 합계(`rcpt_qty_sum`)와 매입 합계(`iv_qty_sum`)는 입고·매입 사본에서 직접 세기 때문에 맞다.
- **영향** — 화면의 「미입고만」·「납기경과 미입고」 필터가 끝난 건으로 채워진다. 같은 값을 쓰는 뷰가 둘 더 있다 — 진행현황 화면의 미입고 발주(`v_erp_pur_order_hdr`)와 구매 에이전트의 미입고·발주 상세 도구(`v_erp_po_pr_link`). 그래서 에이전트의 미입고 답변도 함께 틀린다.
- **고치는 길**
    - A안(빠름): 뷰에서 상태를 실적으로 정한다 — 매입 줄이 있으면 「매입완료」, 실입고 합계가 발주 수량 이상이면 「입고완료」, 일부면 「부분입고」. 위 뷰 세 개를 함께 바꾼다.
    - B안(근본): 발주 적재가 입고·매입이 있었던 발주를 다시 가져오게 한다 — 적재 프로그램 수정과 재빌드가 필요하다.
    - A안을 먼저 하고 B안은 뒤에 붙이는 순서를 권한다. 상태 정의는 한 곳에 두고 새 화면도 같은 것을 쓴다.
- **처리** — **2026-10-07 A안 적용(정본 SQL 91 · REQ-0110 · 결정 D-117).** 판정 뷰 `v_erp_pur_line_status` 를 두고 세 뷰가 그것을 쓰도록 재정의했다(컬럼은 그대로, 끝에 원값 `po_sts_raw`·`rcpt_qty_raw` 추가). 적용 뒤 전량 입고인데 「발주」인 줄 0 · 「발주」→「매입완료」 186줄·「발주」→「입고완료」 4줄·「입고완료」→「매입완료」 246줄 · 조회 시간은 종전과 같음(사내 권한 기준 0.25~0.3초). 발주 사본 자체는 여전히 뒤처지므로(원값 ≠ 실효값 439줄) B안(적재 증분 기준 보완)은 별건으로 남는다.

### 결함 ② 기안서 대장이 엑셀보다 2주 뒤처져 있다 (알려진 대기 항목)

- 중간DB 의 대장은 9월 22일 적재분이다. 그 뒤 엑셀에서 종결 처리되거나 전표번호가 적힌 줄이 포털에는 미종결·전표 없음으로 나온다. 새로 생긴 기안도 없다.
- 적재 재가동과 적재 프로그램의 파라미터 문제는 이미 백로그에 있다(REQ-0092 잔여 · REQ-0098). 새 요청을 만들지 않았다.

### 한계 ③ 기안과 발주가 80%만 자동으로 이어진다

- 대장에는 발주번호 칸이 없다. 포털은 전표를 거쳐 따라가거나(확정), 프로젝트 번호·거래처·금액이 맞는 발주를 찾아(추정) 잇는다. 830건 중 668건.
- 대장의 프로젝트 번호는 사람이 적는다. 확인한 한 건에서는 한 글자가 빠져 다른 프로젝트 번호가 돼 있었고, 그래서 연결이 비어 있었다.
- 프로그램 결함이 아니라 업무 기준의 문제다 — 대장에 발주번호를 적거나, 프로젝트 번호를 ERP 값에서 가져와야 한다. 기획서의 결정 항목으로 올렸다.

### 그 밖에 본 것

| 무엇 | 내용 |
|---|---|
| 화면끼리 이어지지 않는다 | LIST 에서 매입·전표·세금계산서로 넘어갈 수 없고, 기안서 대장에서 발주·요청으로 넘어갈 수 없다. 에이전트의 「기안서 연결 추적」 도구만 한 장으로 묶어 준다 |
| 전표·세금계산서는 좁게만 열린다 | 결의전표·부가세·국세청 사본은 서버 권한으로만 읽힌다. 화면에서는 「대장에 적힌 전표」와 「본인이 만든 전표」만 열린다(결정 C-15). 발주에서 출발해 전표를 보여 주려면 이 범위를 넓히는 결정이 먼저다 |
| 2026년분만 있다 | 중간DB 는 올해 자료만 적재한다. 단가를 견줄 과거가 없다 — 같은 품목의 이전 발주가 있는 줄이 17%뿐이다 |
| 입고일을 믿기 어렵다 | ERP 입고일과 매입일이 같은 날인 줄이 56%다. 입고를 매입 처리 때 한꺼번에 등록하면 실제 입고일을 알 수 없다(확인 필요) |
| 납기일이 비어 있다시피 하다 | 발주 납기가 발주일과 같은 날로 들어간 건이 있다. 견적서의 예상 납기가 ERP 에 들어가지 않으면 「납기경과」가 뜻을 잃는다 |
| 업체 연락처가 거의 없다 | 거래처 4,678곳 중 메일 주소가 있는 곳은 416곳. 메일 초안의 받는 사람을 채우기 어렵다 |
| 엑셀에 보이지 않는 공백 | ERP 화면에서 복사해 붙인 값 앞에 공백 문자가 섞여 있다. 번호로 찾거나 맞출 때 어긋난다 |

## 5. 번호 사슬 — 이어지는 곳과 끊긴 곳

| 이음 | 무엇으로 | 상태 |
|---|---|---|
| 요청 결재(PU) → 요청 줄(PR) | 요청 줄의 결재번호 칸(`pur_req_s.pu_no`) | 이어짐 — 채움 95% |
| 요청 줄(PR) → 발주 줄(PO) | 발주 줄의 요청번호(`pur_order_s.pr_no`) | 이어짐 |
| 발주 줄 → 입고(PG) | 발주번호 + 순번 | 이어짐 |
| 발주 줄 → 매입(IV) | 발주번호 + 순번 | 이어짐 |
| 매입(IV) → 결의전표(TG) | 전표의 참조번호 = 매입번호, 입력유형 매입 | 이어짐 — 매입 374건 전부 |
| 결의전표 → 부가세(VT) | 부가세 원장의 전표번호 | 이어짐 |
| 부가세 → 국세청 승인번호 | 공통 번호 없음 — 구분·작성일·사업자번호·공급가액 대조 | 약함 — 98% |
| 구매기안 ↔ 발주 | 잇는 칸 없음 — 전표 경유 또는 프로젝트·거래처·금액 짐작 | **끊김** — 80% |
| 요청 결재 · 구매기안 · 매입전표 결재의 상태와 날짜 | ERP 로 넘어오지 않는다 | **없음** |
| 견적 · 결정 · 계산서 요청 | 기록 자체가 없다 | **없음** |

## 6. 묶음 관계와 걸리는 시간(2026년 집계)

| 무엇 | 값 |
|---|---|
| 요청 결재가 발주 2건 이상으로 갈라지는 비율 | 18%(998건 중) |
| 매입이 발주 2건 이상을 묶는 비율 | 30%(373건 중) |
| 대장 기안이 발주 2건 이상과 이어지는 비율 | 49%(연결된 668건 중) |
| 나눠 입고된 발주 | 3% |
| 요청 → 발주 | 가운데 값 8일 · 느린 10%는 26일 이상 |
| 발주 → 첫 입고 | 가운데 값 14일 · 느린 10%는 31일 이상 |
| 입고는 됐는데 매입 전인 줄 | 80여 줄 |
| 매입은 됐는데 전표가 미승인인 건 | 40여 건(매입 374건 중) |
| 대장과 발주를 이은 쌍 가운데 발주일이 기안일보다 앞선 비율 | 45% |
| 엑셀 LIST 에 「선진행」·「선발주」가 적힌 줄 | 2,705줄(47%) |

한 건의 묶음이 단계마다 달라서 「구매 한 건 = 번호 하나」로 둘 수 없다. 요청은 결재 단위, 발주·입고는 발주 단위, 매입·전표는 매입 단위, 보관은 대장 단위로 묶이고, 이들을 실제로 잇는 것은 줄이다.

## 7. 구매 에이전트

- 도구 23종이 모두 조회용이다. 발주통합 LIST 검색, 발주·요청 상세, 미입고, 거래처 매입, 기안서 대장과 대사, 기안서 연결 추적, 사내 문서 검색.
- **없는 것**: 단가 이력(품목 이력 도구는 금액·수량만 낸다) · 견적 비교 · 웹 검색 · 메일이나 품의서 초안(초안 유형은 틀만 있고 도구가 없다).
- 지금은 예비 모델로 답하고 있어 첨부한 견적서 PDF 를 읽지 못한다.
