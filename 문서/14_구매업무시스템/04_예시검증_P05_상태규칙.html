04 · 예시 검증(P0.5) — 예외 건 4종으로 상태 규칙을 시험한 결과

작성 2026-10-07 · 로드맵 P0.5(기획서 §6) · 입력은 중간DB 스냅샷(발주 전량 재적재 직후)과 구매팀 엑셀 LIST · 기안서 대장(중간DB 10-07 적재분). 이 문서는 공개물이다 — 실거래 번호·거래처·금액을 적지 않는다. 건별 추적 화면(실데이터)은 비공개 사례 폴더(doc/…/P05_예시검증/01~04/구매건_추적.html)에 _build_case.py --keep-mismatch 로 만들었다. 목적: 8월 예시 1건(01 도식·02 현행 점검)으로 세운 「상태는 실적 문서의 존재로 판정한다」는 규칙이 예외 건에서도 맞는지 보고, 틀리는 곳은 규칙을 고친다.

1. 한눈에

# 예외 유형 고른 건 규칙이 맞았나 고친 것 · 남긴 것
① 선진행 + 외주 가공(입고 기록 없음) 9월 · 외주 가공 3줄 · 매입 1장 ✗ 6단계가 「아직」으로 멈춤 · 포털 LIST 미입고·납기경과 켜짐 규칙 추가: 입고 없이 매입이 발주 수량을 채우면 6단계 = 기록 없음(끝). LIST 는 별도 요청
② 계약금·중도금·잔금(월별 진행률 매입) 5월 · 외주 제작 2줄 · 매입 3장 · 전표 3장 ✗ 매입 한 장씩 비교하면 전부 「불일치」 · 한 장은 다른 발주와 묶임 규칙 변경: 매입이 여러 장이면 발주 순번별 수량 합으로 검산 · 전표·계산서는 매입 한 장 전체와 대조
③ 분할 입고 → 분할 매입 4월 · 자재 10줄 · 4일 입고 · 매입·전표·계산서 각 4장 ○ 합으로 보면 전부 맞음 화면: 「첫 입고 ~ 마지막 입고」·「매입 n장」 표시 · 대장 금액이 발주보다 큰 것은 다른 매입이 섞인 것
④ 요청 1건 → 거래처 6곳(발주 6건) + 미발주 줄 5월 · 요청 14줄 → 발주 8줄 · 미발주 6줄 △ 발주 단위는 맞음 · 요청 줄 단위가 안 보임 화면: 「발주 없이 남은 요청 줄」 표시 · 자동 연결 규칙의 한계 발견(아래 §3-3)

네 건 모두 ERP 안에서 번호 사슬(요청 → 발주 → 입고/매입 → 전표 → 부가세 → 국세청)은 끊기지 않았다. 틀린 것은 ERP 가 아니라 판정 규칙과 손으로 적는 자료였다.

2. 건별 관찰

① 선진행 · 외주 가공 (9월)

  • 일의 순서가 엑셀 「선진행」 표기(8월 말) → 매입·전표·세금계산서(9월 중순) → ERP 발주·구매기안(9월 말) 이다. 요청(7월 말)부터 ERP 발주까지 59일, 그 사이에 일이 다 끝났다.
  • ERP 발주일을 기준으로 납기를 따지면 아무 의미가 없다 — 발주일 = 납기일 = 기안일이 같은 날이다. 「ERP 발주일」과 「실제 발주(지시)일」은 다른 값이고, 후자는 지금 엑셀 글자 칸에만 있다.
  • 입고(PG)가 없다. 외주 가공은 입고 등록 없이 매입으로 끝난다. 추적 규칙은 6단계를 「아직」으로 두었다 → 「기록 없음」으로 고쳤다(끝나지 않은 것이 아니라 기록이 없는 것).
  • 포털 LIST 는 상태 「매입완료」를 맞게 내지만 미입고·납기경과 표시가 켜져 미입고 목록에 섞인다. 이 유형이 LIST 전체에 505줄이다(02 현행 점검 결함 ① 열린 질문).
  • 엑셀 LIST 의 「구매요청번호」 칸에 요청 줄 번호(PR)가 적혀 있다. 8월 예시는 요청 결재 번호(PU)였다 — 같은 칸이 건마다 다르다.

② 계약금 · 중도금 · 잔금 (5월 · 외주 제작)

  • 발주 수량을 50% · 30% · 20% 로 쪼갠 매입 3장(수량이 소수점)으로 들어간다. 입고 등록은 없다. 전표 3장(전부 승인), 세금계산서 3장.
  • 매입을 한 장씩 발주 줄과 비교하면 전부 「불일치」로 보인다. 발주 순번마다 수량 합으로 보면 맞다 — 검산 규칙을 바꿨다.
  • 한 줄은 마지막 매입의 단가가 발주 단가와 다르고, 두 줄의 차이가 서로 상쇄돼 합계만 맞는다. 줄 단위 검산은 이 차이를 남겨야 한다(금액 합만 보면 못 본다).
  • 잔금 매입 한 장이 다른 발주의 매입과 한 장으로 묶여 전표·부가세·세금계산서는 묶인 전체 금액으로 나온다. 「발주 → 전표 금액」을 바로 비교하면 틀린다 — 전표·계산서는 매입 한 장 전체와, 발주 몫은 매입 줄과 대조한다.
  • 기안서 대장의 지급 비율 합이 130%(계약금 50 + 중도금 30 + 잔금 50) 이고, ERP 에는 잔금 매입·전표가 있는데 대장 잔금 칸은 빈칸·종결 「N」 이다. 지급 단계는 ERP 매입(수량 비율)에서 가져오고, 종결은 「마지막 매입 = 발주 전량」으로 자동 판정할 수 있다.
  • ERP 발주 헤더 비고에 요청 결재번호 두 개가 적혀 있다 — 참고용이지 연결 키가 아니다.

③ 분할 입고 → 분할 매입 (4월 · 자재)

  • 4일에 걸쳐 입고 10건 → 그날그날 매입 4장 → 전표 4장 → 세금계산서 4장. 발주 1건이 매입 4장으로 끝났다. 발주 순번별 합으로 보면 입고·매입·전표·부가세·국세청이 전부 맞는다.
  • 세금계산서의 작성일(입고일)과 발급일(열흘 뒤 한꺼번에)이 다르다. 「계산서 수취」 완료 판정에 어느 날짜를 쓸지 정해야 한다.
  • 기안서 대장 한 기안에 생산번호가 다른 줄 두 개가 있고, 「전표번호」 칸에 TG 가 아니라 매입번호(IV) 여러 개가 줄바꿈으로 적혀 있다(그중 하나는 이 발주의 매입이 아니다). 대장 금액이 발주보다 큰 이유다. 칸의 뜻(전표인지 매입인지)을 정하고, 포털 대사는 매입번호로도 잇는다.
  • 엑셀 LIST 는 이 건은 ERP 와 맞다(발주일·입고일·금액).

④ 요청 1건 → 거래처 6곳 (5월 · 부자재)

  • 요청 결재 한 건 14줄 중 8줄이 6곳으로 발주되고(각각 기안), 6줄은 발주 없이 「확정」 상태로 남았다(그중 3줄은 수량 0). 수량이 있는 3줄은 넉 달째 어디에도 드러나지 않는다 — 접수함이 없어서다.
  • 발주 6건의 매입은 거래처마다 월말 묶음 매입(다른 발주 5~9건과 한 장)으로 들어갔다. 한 거래처의 매입 1장이 75줄 · 발주 9건이다.
  • 자동 연결의 한계: 포털의 기안 ↔ 발주 연결은 「전표 경유」가 「확정」인데, 월말 묶음 매입은 전표 1장이 기안 여러 건을 덮는다. 그 결과 기안 11건(프로젝트 5종)이 소액 발주 1건에 「확정」으로 붙는다. 연결은 「전표 → 매입 줄 → 발주 줄」로 내려야 하고, 전표만 같은 기안은 「같은 전표」로만 표시해야 한다.
  • 선결제 건(라이트)은 대장에 「선결제 100%」 전표가 있지만 ERP 매입은 없고 입고만 있다. 추적 규칙은 6단계에 멈춘다 — 상태 규칙에 「선결제 완료」 경로가 필요하다.
  • 한 발주에 이 요청 줄 2개와 다른 요청 줄 2개가 묶였다(발주 금액 대부분이 다른 요청 몫). 발주 단위 화면은 「이 요청 몫 / 발주 전체」를 나눠 보여 줘야 한다.
  • 엑셀 LIST 는 발주일이 ERP 보다 하루 뒤, 입고일은 6건 중 1건만, 한 발주는 금액 칸이 비어 있다.

3. 규칙에 반영한 것 · 반영해야 할 것

3-1. 추적 규칙(_build_case.py · 이번에 고침)

규칙 전 후
6단계(입고·계산서) 입고 수량 ≥ 발주 수량이어야 완료, 아니면 「아직」 입고 기록 없이 매입이 발주 수량을 채우면 「기록 없음」(외주 가공·용역·진척 매입)
7단계(매입·전표) 전표 1장의 승인 여부 전표가 여러 장이면 전부 승인이어야 완료
검산 「매입 줄 = 발주 줄」 매입 줄 하나 = 발주 줄 하나 발주 순번별 수량 합 = 발주 수량 · 단가는 줄마다
검산 「전표 = 매입」 전표 금액 = 이 발주의 매입 금액 전표 한 장 = 매입 한 장 전체(다른 발주 몫 포함) · 장마다
검산 불일치 빌드 중단 --keep-mismatch 로 관찰로 남기고 화면에 「불일치」 표시
화면 — 발주 없이 남은 요청 줄 · 매입 조각 표(이 발주 몫 / 전체 / 묶인 다른 발주) · 지급 단계(대장) · 같은 전표로 묶인 다른 기안 · 첫~마지막 입고

3-2. 상태 판정 뷰(v_erp_pur_line_status · 정본 SQL 91)에 반영할 것 — 별도 요청

  • 매입이 끝난 줄(po_sts = IV)은 미입고·납기경과에서 뺀다. 입고 기록이 없는 외주·용역 줄이 미입고 목록에 섞이는 것이 ①②④ 에서 반복됐다(전체 505줄).
  • 「선결제 완료」 경로: 매입 없이 선급 전표만 있는 줄의 상태 — 대장·전표로만 알 수 있어 ERP 뷰만으로는 안 된다(포털 기록 또는 대장 연계).

3-3. 기안 ↔ 발주 자동 연결(v_pur_proposal_po_link · 정본 SQL 76)에 반영할 것 — 별도 요청

  • 「전표 경유」를 매입 줄 단위로 내린다: 전표 → 매입(참조번호) → 매입 줄의 발주번호+순번 → 기안의 거래처·프로젝트·금액과 대조. 지금은 전표가 같으면 전부 「확정」이라 월말 묶음 매입에서 다른 프로젝트 기안까지 붙는다(④).
  • 대장 「전표번호」 칸의 매입번호(IV…)도 연결 키로 받는다(③).

3-4. 데이터·업무 기준(기획서 §4·§7 에 더할 것)

  • 「ERP 발주일」 ≠ 「실제 발주일」 — 선진행 날짜를 남길 칸(포털 기록)과, 납기경과 판정의 기준일 결정(①).
  • 지급 단계(계약금·중도금·잔금)는 ERP 매입의 수량 비율에서 자동으로 만든다. 대장의 비율·전표 칸은 손으로 적어 틀린다(②).
  • 접수함은 요청 줄 단위다. 「발주 없음 · 확정 상태 · 경과일」을 보여 주고, 수량 0 줄의 뜻(취소?)을 ERP 에서 확인한다(④).
  • 계산서 수취 완료의 기준 날짜(작성일 vs 발급일)를 정한다(③).
  • 엑셀 LIST 의 「구매요청번호」 칸은 PU/PR 이 섞여 있다 — 포털이 ERP 값으로 채우면 없어지는 문제(①).
